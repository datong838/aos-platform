# 经营分析启动 Context 与分阶段经营证据

基线545cf043。此方案补足CF3；不是运行许可或业务验收结论。

## 目标及事实

经营分析需要先建立可恢复任务，随后完成画像取证、诊断、方案和评审。当前DataRequirementHostService.revalidate必须读取已有CompilationReceipt并经RuntimeBinder取得暂停Checkpoint，因此不能通过该服务反向准备首次编译依赖。现行Compilation又必须有冻结ProductionContext。原v1 Brief引用环已由v2意图简报解决；这里解决的是证据用途与执行顺序。

真实画像服务portrait_prompt并不是旧Logic dry-run：它要求当前method、指标定义、查询结果、完整披露EvidenceBundle及frozen/ready Eval，逐指标验证唯一来源，并保留生成产物。启动Context不能替代这些检查。

## 采用的顺序

1. 当前安装蓝图显式声明startupContextPolicy：用途仅为analysis-start；要求原事件与本次Case/Run的关联证明，业务事实尚未完成。
2. 事件分析Host保持现有领取锁、原来源SourceOwner、原journal证明、当前installation/generation/epoch、控制/配置和Case重验。蓝图IPC在事务外，写前后仍复验；不能以持有一个Python快照等同当前授权。
3. 在上述同一事务中创建本次Run、Task、frozen v2 Brief。依据原始事件/Occurrence及Case/Run exact引用生成启动Evidence。来源时间、身份和hash只能来自实际读取，禁止从测试fixture或调用者自由文本推断。
4. 启动Evidence明确purpose=analysis-start、factIds仅为固定启动关联事实；保留领域requiredFactProfiles作为尚待取证清单，不得发布为画像指标证据。证据run_id为NULL，因为AIP TaskRun尚未创建；payload保留业务Run exactRef，绝不虚构AIP运行记录。
5. 通过现有build_evidence_bundle给本次Brief构建启动包，requiredFactIds由受当前安装约束的蓝图声明且Host仅支持固定用途集合。complete仅指已声明的启动关联事实覆盖，不能作为任何经营结论、业务质量或经营阶段完成依据。
6. Context的Eval引用须由蓝图首阶段的实际已发布技能唯一解析其PublicationEvent/ReleaseGate/Suite，并通过当前有效状态、hash、TTL和依赖重验。该合同若是isolated_skill_contract，只证明启动技能契约；记录用途，不能当作经营分析的质量评估。缺失/失效形成可恢复不可执行结果，不挑任意旧Eval。
7. 冻结本任务Context，派生L2 Profile，经真实CompileSaga建立Plan/CompilationReceipt，并创建/绑定真实AIP TaskRun。各步以原事件幂等键组合，统一外层事务，失败不留下孤儿或假运行回执。
8. 后续业务阶段继续用真实指标查询、来源披露、method/Eval及业务产物协议；缺数进入既有暂停/数据请求/恢复流。评审、交接与EffectReview/Wiki不得接受启动包替代其业务资料。

## SC2 当前来源存储细化

新增ecommerce_analysis_startup_evidence.py的AnalysisStartupEvidenceService，构造必须为精确ProductEventAnalysisService。record接受当前事务connection、claimed和明确业务runRef/领域profile/当前蓝图；内部重新进入分析service._phase（包含原SourceOwner/journal、claim及当前安装），再从同事务RunStore读取权威和当前状态。校验Case/profile/Run exact、triggerKey等于本次claim key、PREPARING/RUNNING及时间顺序。仅保存事件metadata和当前证明snapshotHash，不保存客户正文；已有reader已校验正文hash并移除payload。

Evidence采用tenant+业务runId稳定identity、完整payload hash；observedAt取不可变业务Run创建时间，created_at取DB时钟。单独aip_evidence.run_id=NULL，subject关联业务Run。ON CONFLICT只回读，全文/元数据/撤销检查任何不同拒绝；外围SourceOwner失败由外层事务回滚。此服务不接受外部自由snapshot，也不创建Bundle或声明业务完整。测试实际PG Case/Run/claim/evidence；来源/installed fixture明确替身。后续SC4负责在已取得installed蓝图的同一授权组合内调用，单独record不等于完整START。

### SC2 实库发现的初始Run状态格式兼容

真实RunStore.request触发biw4_006初始状态：原JSON不含三个可选null字段，hash按PostgreSQL jsonb::text生成；模型calculated_content_hash按Python规范计算，二者不同，旧纯合同fixture掩盖CF3 Task准备的误拒绝。新增RunStore.get_verified：同事务读取当前Run/state正文与投影列，Run按原规范hash核验；状态只接受现有Python规范或明确r1固定字段集的历史PG序列化，后者由SQL重算原jsonb正文hash并逐列比较，保留旧hash不改记录。其他未知格式拒绝。任务准备和SC2使用该权威读取对照输入，不能仅通过模型投影重hash；测试升级为真实PG Run，保留坏hash/租户拒绝。

## SC4-3a 启动门事务接入前置

复核发现AipProductionStartService.start/get/list直接使用全局connect，与已绑定的Context/Saga不共享事务，正式事件内调用会看不到未提交Plan或发生锁等待，且启动后外层失败不能回滚。先修改services/aos-api/aos_api/aip_production_start_service.py增加可选connect_factory，默认保持原connect，内部默认Contract/Action/Task Store复用同factory；所有start/get/list使用factory。原门禁、审批要求和状态机不改变，不直接调用底层create_run_from_production_start_gate。

在services/aos-api/tests/aip/test_w2d_start_gate.py追加原有隔离候选fixture的事务绑定测试（legacy fixture scope，与真实租户无关）：实际approved Proposal经原StartGate产生TaskRun，同事务get/list可见，同键重放一致；外层故障后StartDecision/TaskRun/Plan审批和Task状态完全回滚。未批准候选仍拒绝，保留原测试累计。SC4-3b随后准备启动ImpactPreview与当前受控Proposal；不能伪造审批或编造预算，经营建议exact评审仍独立。

## SC4-3b 初始输入检查点（先于启动审批组合）
