# 当前权威库 a0v_163→a0v_170 正式切换方案 r22

时间：2026-10-31（Asia/Shanghai）
状态：方案先行；执行前必须再次通过全部门

## 1. 业务目的

把当前权威命名卷从 `a0v_163` 受控迁移到已在一致物理副本中验证的 `a0v_170`，消除正式代码与数据库结构之间的版本差。迁移只准备后续配置保存通道，不开放配置 POST，不建立正式写身份，不启动 Host、worker 或 Provider，也不增加业务验收数字。

## 2. 已满足的前置

1. 已建立当前权威卷的干净停机物理备份；tar 可完整列出且 SHA-256 已固定；
2. 已从物理备份恢复独立副本，并证明恢复前与来源的系统标识、数据库 OID、角色、成员关系、结构和业务数据一致；
3. 独立副本已一次从 163 迁移到 170；新增表为空并强制 RLS，旧数据、旧角色属性和成员关系保持；
4. 后台配置专用身份的正向与越权矩阵已在副本通过并完整撤销；
5. 正式库仍为 163，正式 API 与 Web 在线，配置 POST 为 405，未产生同幂等键回执。

## 4. 切换前门

1. 复核当前容器、卷、系统标识、数据库 OID、迁移头和迁移文件 SHA；
2. 复核正式配置 POST=405、Host/worker/Provider OFF；
3. 复核无 prepared transaction、无非维护连接、无未对账写入；
4. 复核物理备份文件存在、大小和 SHA 不变，恢复副本已停止；
5. 复核正式库不存在隔离演练幂等键；
6. 停止正式 API 并确认 18080 不再监听；Web 可保持在线但不能触发写入；
7. 停止 API 后再次复核迁移头与关键目录，形成明确迁移 intent。

任一条件不满足则恢复正式 API，不执行迁移。

## 5. 单次迁移

只执行一次：

`AOS_DATABASE_URL=postgresql+psycopg://aos_app@127.0.0.1:18446/aos_meta_head alembic upgrade head`

迁移结果明确成功后才进入后验。命令超时、断联或结果 unknown 时禁止重跑，先只读查询 `alembic_version` 和 164—170 对象目录，再决定恢复服务或物理回退。

## 6. 迁移后验

必须同时满足：

1. 唯一迁移头为 `a0v_170`；
2. 新增 3 个治理角色、5 张治理表；5 张表均启用并强制 RLS、各有 2 个非内部触发器且行数为 0；
3. 排除 5 张新增表和迁移版本表后，旧业务数据摘要与迁移前一致；
4. 排除 3 个新增角色后，旧角色属性与成员关系摘要一致；
5. 没有专用配置保存角色、策略或隔离测试回执；
6. 正式 API 用原冻结启动器恢复，API 与 Web 为 200，配置 POST 仍为 405；
7. Host、worker、Provider 继续 OFF。

## 7. 失败保全与物理回退

- 迁移未开始：直接恢复原 API；
- 迁移结果 unknown：保留当前卷，不重跑；停止所有写入口，只读核对实际头与对象；
- 迁移明确失败且当前卷已部分变化：停止 API 和 PostgreSQL，保留失败卷不覆盖；从已校验物理备份解压到全新回退卷，先以新容器和新端口验证 163 身份及数据摘要，再经过独立切换方案替换正式指向；
- 禁止把备份直接解压到当前卷，禁止删除失败卷，禁止伪造 downgrade。

若正式 API 无法恢复，优先保持配置入口关闭并修复只读服务，不开放任何写通道。

本切换成功只说明权威数据库与最新代码结构对齐。它不是客户已配置，不是自然业务首链，也不改变 `runner 9/22、工程 2/8、业务 0/8`。
