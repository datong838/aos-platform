# 正式配置保存通道准备口径修正 r27

时间：2026-10-31 06:28（Asia/Shanghai）

## 修正原因

r26 方案预期“底层专用身份准备后，页面第五项显示已准备，同时 POST 继续 405”。对当前产品合同复核后确认，这两个状态不能同时成立：`配置保存通道` 的业务含义是运营人员现在可以提交保存，因此产品同时要求：

1. 专用数据库身份与最小权限探针通过；
2. `AOS_ROUTE_WORKER_CONFIGURATION_POST_ENABLED=1`；
3. 正式管理入口允许精确 configure POST。

只完成第 1 项时，底层保存能力已准备，但对运营仍必须显示“配置保存通道尚未安全开通”。这不是实现缺陷，而是防止把技术前置冒充可操作状态的门禁。

## 当前真实状态

- 专用 SCRAM 身份、精确 HBA、受保护 pgpass、0600 身份描述、目标表 SELECT/INSERT 和硬租户策略均已准备；
- 产品只读探针通过；
- 正式 API 的 `AOS_ROUTE_WORKER_CONFIGURATION_POST_ENABLED` 仍未设置；
- 正式 configure POST 精确返回 405；
- 正式库配置完成回执为 0；
- Host、worker、Provider 和全部业务执行继续 OFF。

因此运营页面第五项保持未通过是正确业务语义。不得为了让页面变绿而提前开放 POST。

## 后续开放门

首次开放必须绑定用户对具体配置内容的明确确认、唯一幂等键和预期配置摘要。开放后只允许保存配置；Host、worker、Provider 仍需另行授权。结果 unknown 时只读查询回执，不重发。

本修正替代 r26 中“POST 关闭但第五项已准备”的展示预期，不改变已完成的底层最小权限准备和回滚规则。
