# 后台配置保存通道当前业务库准备与回滚方案 r5

时间：2026-10-31（Asia/Shanghai）  
状态：方案先行；当前业务库继续只读，本方案本轮不执行

## 1. 业务目的

让运营人员未来点击“保存后台处理配置”时，系统只能为 `org-org/dev-project` 保存一笔可审计的配置命令回执。这个动作只表示配置已保存，不表示开始处理订单、库存、售后或内容任务，也不启动 Host、worker、Provider。

正式页面已经能如实显示：四项配置材料已齐，但“配置保存通道”尚未开通。本方案只定义该通道如何安全准备、验证和撤销，不改变当前页面结论。

## 2. 不可突破的边界

1. 当前业务库在获得后续明确执行条件前保持只读；
2. 正式 `configure POST` 开关保持关闭，HTTP 继续返回 405；
3. 不复用正式 API 的通用数据库登录，不扩大 `aos_runtime` 或 `aos_app` 权限；
4. 不删除、不改写既有回执，不重放旧 12 Run、失败或 unknown 结果；
5. 不启动 Host、worker、Provider，不产生外部业务效果；
6. 凭据只进入权限 `0600` 的受保护文件，不进入 Git、证据、命令输出或日志；
7. 任一步结果不明确时，只读对账，不重发写入步骤。

## 3. 第一阶段：只读现状核验

执行任何数据库变更前，先产生不含秘密的目录快照并逐项确认：

1. 当前数据库、命名卷、迁移头和正式 API 实际指向一致；
2. `public.bundle_installation_command` 的表 owner、列、约束、触发器和默认值与当前代码一致；
3. 表当前是否已经 `ENABLE ROW LEVEL SECURITY` 和 `FORCE ROW LEVEL SECURITY`；
4. 全部既有策略名称、目标角色、命令类型、`USING` 与 `WITH CHECK` 表达式；
5. `PUBLIC`、`aos_runtime`、`aos_app` 及其他角色对 schema、目标表、其他表和序列的实际权限；
6. 专用角色名 `aos_route_worker_lifecycle_command`、策略名 `route_worker_lifecycle_command_scope` 是否已存在；
7. 是否已有同名受保护身份文件、同名连接或未对账的配置保存结果。

只读核验出现以下任一情况即停止准备：

- 目标表结构与代码合同不一致；
- 同名角色或策略存在但内容不完全一致；
- 数据库、命名卷或迁移头身份不确定；
- 存在未对账的配置保存结果；
- 无法证明变更前备份和独立恢复可用。

## 4. RLS 兼容性门

产品连接校验要求目标表同时启用并强制 RLS。该要求不能通过一次窄授权盲目补齐：

- 如果目标表已经启用并强制 RLS，先证明新增专用策略不会改变任何既有角色的可见范围，再进入下一阶段；
- 如果目标表尚未启用或未强制 RLS，必须先建立独立兼容性方案，在隔离恢复库验证所有既有合法读写路径；未完成该验证前，不得在当前业务库切换 RLS；
- 不允许为了让专项校验通过而删除、放宽或替换既有策略。

因此，“当前表未强制 RLS”是单独的数据库兼容性缺口，不得伪装成普通角色创建步骤。

## 5. 第二阶段：隔离恢复库演练

在当前权威库的独立、可校验恢复副本中演练完整准备与撤销：

1. 建立 `LOGIN NOINHERIT` 专用角色，明确关闭 superuser、bypass RLS、create role/database 和 replication；
2. 保证该角色不属于任何其他角色；
3. 只授予 `public` schema 的 `USAGE`；
4. 只授予 `bundle_installation_command` 的 `SELECT, INSERT`；
5. 不授予任何序列权限；业务写入必须提供自身标识，不依赖序列；
6. 创建只面向该角色、`FOR ALL`、permissive 的 `route_worker_lifecycle_command_scope` 策略；
7. `USING` 与 `WITH CHECK` 都必须硬编码为 `org_id='org-org' AND project_id='dev-project'`；
8. 使用产品的只读探针证明最小权限合同通过；
9. 证明正向租户可插入和读取，跨租户、更新、删除、其他表写入均被拒绝；
10. 撤销角色、策略和身份文件后，再次证明原有路径与演练前一致。

演练证据只保存角色名、策略、权限矩阵和结果，不保存密码或完整 DSN。

## 6. 第三阶段：当前库受控准备

只有只读核验、RLS 兼容性门、备份恢复门和隔离演练全部通过，才可在单独维护窗口执行：

1. 再次核对当前数据库、命名卷、迁移头和目标表目录摘要；
2. 在一个可回滚事务内创建专用角色、最小授权和精确策略；
3. 事务提交前用目录查询核对角色无继承、无成员关系、无额外表写权和无序列权限；
4. 提交后创建当前进程所有、权限 `0600`、非符号链接的受保护身份文件；
5. 保持配置 POST 关闭，只运行产品只读探针；
6. 只读探针必须返回通过，页面第五项才可显示“保存通道已准备”；
7. 此时仍不执行配置保存，不产生任何回执或配置文件。

数据库变更与身份文件创建必须分别记录明确结果。任一步结果 unknown 时，不重做；先只读核对角色、策略、文件 inode/权限和探针结果。

## 7. 回滚规则

### 7.1 尚未产生配置回执

如果 POST 从未开放且目标表不存在该专用通道产生的回执，可按反向顺序：

1. 停用并移走受保护身份文件；
2. 撤销目标表 `SELECT, INSERT` 和 schema `USAGE`；
3. 删除精确命名策略；
4. 删除专用登录角色；
5. 复核所有既有角色、策略和权限与变更前摘要一致。

不得为了回滚本专用通道而关闭表级 RLS、删除其他策略或修改既有业务数据。

### 7.2 已产生配置回执

一旦存在真实配置回执，不删除、不改写回执。回滚只允许：关闭 POST、移走身份文件、将专用角色设为 `NOLOGIN` 或撤销其权限，并保留完整审计记录。后续恢复必须先对账，不得重复提交同一配置命令。

## 8. 后续保存入口开放门

数据库通道准备完成仍不等于可以保存。首次开放正式 POST 还必须另行满足：

1. 页面五项条件全部真实通过；
2. 用户对本次具体配置内容作出明确确认；
3. 请求幂等键、预期配置摘要和目标租户完全匹配；
4. 保存前后同时核对数据库回执和受保护配置文件；
5. 返回 unknown 时只读对账，不重发；
6. 保存完成后 Host、worker、Provider仍保持 OFF，另行授权后才能处理业务。

## 9. 本方案验收口径

本方案完成只代表安全实施路径已经定义，不计入客户配置完成、自然业务首链或八阶段业务验收。当前验收数字保持 `runner 9/22、工程 2/8、业务 0/8`。
