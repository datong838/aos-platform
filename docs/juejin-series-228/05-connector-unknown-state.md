# 接入社交平台最难的不是 OAuth：Connector 的能力快照与未知态

很多平台接入做到 OAuth 回调成功，就认为连接器已经完成。真实工程里，授权只解决“谁允许你做什么”的一部分。平台能力会变化，账号权限有差异，回调可能重放，发布请求可能超时但实际成功。最棘手的问题往往是：系统不知道外部世界究竟发生了什么。

## 不要把平台适配写进业务逻辑

业务层应该表达“生成内容草稿”“查询指标”“请求发布”，而不是直接处理某平台的签名、限流和字段。Connector 用统一调用信封隔离差异：

```yaml
operation: content.publish
installation_ref: "连接实例"
capability_snapshot_ref: "能力快照"
input_ref: "不可变内容版本"
idempotency_key: "业务幂等键"
deadline_at: "截止时间"
```

每个 operation 还要声明是否只读、是否有外部副作用、是否可逆、是否需要动作审批、超时、并发、限流桶和隐私等级。

这样，运行时可以在调用前做统一检查，而不是相信模型或前端传入的 `safe=true`。

## 为什么需要能力快照

同一平台的不同账号、地区和授权范围，能力可能不同；今天可用的接口，未来也可能被收回。调用不能只绑定“平台类型”，还应绑定一次服务端获取并签名/哈希的 capability snapshot。

批准和执行之间如果能力快照变化，原批准应失效并重新评估。否则，一个原本只读的授权升级或降级后，旧任务可能在错误边界上继续运行。

## 密钥永远只用引用

业务数据库和任务载荷不应保存 Token，只保存密钥系统中的不透明引用、scope、过期时间和 key version。日志也不能输出原始请求头或完整错误响应。

Token 刷新需要单飞锁和 CAS，避免多个 Worker 同时刷新并互相覆盖。账号撤销后应立即阻断新调用，已经排队的任务也不能凭旧快照继续执行。

## Webhook 先验签，再解释

正确顺序是校验签名、时间窗、nonce 或事件 ID、原始 body 哈希，通过后再解析业务字段。验签前解析甚至触发业务逻辑，会给重放、格式混淆和资源消耗攻击留下空间。

回调处理还要幂等。未知账号、过期签名、重放事件和不兼容 Schema 应进入隔离队列，而不是不断重试污染主流程。

## 发布能力应该分级开放

一个稳妥的演进路径是：

1. 只生成适配渠道格式的本地草稿；
2. 人工在平台发布，系统登记回执；
3. 通过官方只读接口拉取状态和指标；
4. 经审批创建平台草稿或预约；
5. 最后才评估直接发布、回复或私信。

每一级都依赖官方能力、账号授权和风险评测，不能因为网页端能操作就默认存在稳定自动化接口。

## 超时不等于失败

这是连接器设计中最容易制造事故的地方。请求发送后连接断开，外部平台可能已经成功，只是响应没有回来。如果系统把它标记为失败并自动重试，就会重复发布或重复触达。

更准确的状态机是：

```text
accepted → pending → confirmed / rejected / unknown
```

进入 unknown 后，优先使用平台 request token、业务幂等键或对象 ID 查询状态。只有确认外部不存在该动作，才允许在同一语义幂等键下重试。没有可靠查询或幂等能力的写操作，unknown 只能转人工核验。

## 指标与评论回流也需要治理

不同平台的“播放”“互动”“点击”定义未必一致。应保留原始 metric ID、时间粒度、时区、窗口和更新时间，不能简单同名合并。

评论和弹幕进入系统前，要做内容安全、隐私、密钥和提示词注入检查；它们可以形成受控意图或线索候选，但不能直接进入长期记忆。客户同意状态未知时，只能人工核验，不能自动触达。

Connector 的成熟度，不取决于适配了多少平台，而取决于是否能准确描述能力、权限、状态与不确定性。
