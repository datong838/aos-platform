# 企业级 Agent 如何从对话走向执行：身份、逻辑与工具的三层架构

很多 Agent 项目的起点都是一个对话框：写一段系统提示词，接入大模型，再配置几个函数。它足以验证模型能否理解问题，却很难直接进入业务流程。

原因并不神秘。企业需要的不只是“给出一个回答”，还要知道它读取了什么数据、经过哪些步骤、为什么调用某个工具、谁批准了写操作，以及失败后如何定位和恢复。

在一套智能体平台方案中，我们把负责构建、编排和治理的中枢称为 AIP 决策引擎。本文不罗列页面功能，而是从工程视角拆解它的核心设计：如何用 Agent Definition、Logic Pipeline 和 Tool Registry 三层结构，把一次模型调用变成可运行、可治理、可审计的业务链路。

## 一条分界线：回答问题，还是参与流程

对话机器人通常围绕输入和输出工作：

```text
用户问题 → 拼接上下文 → 调用模型 → 返回文本
```

企业级 Agent 的运行链更长：

```text
业务事件
  → 读取授权范围内的数据
  → 执行确定性规则
  → 调用模型完成适合推理的步骤
  → 生成结构化决策
  → 请求工具或业务动作
  → 人工审批或策略校验
  → 执行并记录结果
  → 进入效果观察
```

两者最大的差别不是模型，而是控制面。模型只负责它擅长的理解、生成和归纳；身份、权限、分支、审批、幂等和审计仍由确定性系统负责。

## 第一层：Agent Definition 定义“谁在工作”

一个 Agent 不能只有名称和提示词。更完整的定义至少包含五部分：

```yaml
identity:
  role: "订单异常协调员"
  purpose: "分析异常并形成处理草案"
context:
  allowed_object_types: ["订单", "履约事件", "服务工单"]
model_policy:
  task_type: "classification_and_draft"
tool_policy:
  allow: ["读取订单摘要", "创建处理提案"]
safety:
  write_mode: "approval_required"
  forbidden_scopes: ["支付凭据", "无关客户数据"]
```

这里有三个关键点。

第一，上下文采用白名单，而不是让 Agent 自由查询数据库。它看到的是经过权限裁剪的业务对象和字段，不是底层表结构。

第二，模型选择是一条策略，不是写死的供应商名称。分类、摘要和复杂推理可以根据质量、延迟和成本使用不同路由，同时保留版本记录。

第三，安全等级描述“允许做到哪一步”。只读分析、生成草稿、需人工确认的写操作和有限自动执行，不应该共用一套模糊权限。

Agent Definition 的产物不是一个人格说明，而是一份可校验的运行契约。

## 第二层：Logic Pipeline 定义“按什么步骤工作”

只依赖提示词控制流程，会遇到两个问题：模型可能遗漏步骤，流程变化也难以做版本比较。Logic Pipeline 的做法是把业务过程拆成类型化节点：输入、读取属性、创建变量、模型推理、工具调用、数据变换、条件分支、动作提案和结果交接。

一个异常处理流程可以表示为：

```text
Input
  → Get Property
  → Transform
  → Use LLM
  → Branch
      ├─ 信息不足 → Request Clarification
      ├─ 低风险   → Create Draft
      └─ 高风险   → Handoff to Human
```

这种编排不是为了把所有业务做成拖拽界面，而是建立四个不变式：

1. 每个节点都有明确输入输出 Schema；
2. 分支条件可复现，不能只藏在自然语言里；
3. 每次运行绑定 Pipeline revision；
4. 下游只能消费已完成节点的结构化输出。

模型节点也不应直接返回一段无人约束的文本。更稳妥的方式是要求它输出结构化结果，再由 Schema 校验器检查字段、枚举和长度。校验失败进入重试或人工处理，而不是把错误数据继续传下去。

## 第三层：Tool Registry 定义“可以使用什么能力”

Tool Registry 位于推理层与执行层之间。每个工具除了名称和参数，还要声明：

- 输入输出 Schema；
- 只读还是存在外部副作用；
- 所需角色、数据范围和用途；
- 是否支持幂等、状态查询和补偿；
- 超时、并发与频率限制；
- 是否必须产生审批提案。

模型提交工具请求的语义应当是“提出请求”，而不是“获得平台管理员权限”。真正执行时，平台使用当前用户或服务身份重新校验权限，并重新读取不可变输入引用。

对于写操作，至少要绑定目标对象、载荷哈希、Agent revision、Pipeline revision 和批准记录。网络重试时使用同一幂等键，避免一次超时演变成两次业务动作。

这一层把 Agent 从“能描述怎么做”推进到“能在边界内请求执行”，同时避免工具权限被提示词放大。

## Evals 和可观测性不是附加模块

三层结构解决了构建问题，质量门禁和运行追踪解决“能否发布”与“出了问题如何解释”。

发布前的 Evals 至少应覆盖：

- 正常输入能否得到符合 Schema 的结果；
- 缺字段、冲突数据和过期数据如何处理；
- Agent 是否尝试读取白名单以外的字段；
- 未注册工具是否明确失败；
- 高风险分支是否稳定转人工；
- 更换模型或提示词后，事实性和安全性是否退化。

运行时 Trace 则串联事件、节点、模型调用、工具请求、审批和结果。它不需要记录模型隐藏推理过程，但必须记录输入引用、输出摘要、版本、延迟、Token、错误和状态变化。

当一次结果出现偏差时，团队才能区分：是数据过期、规则错误、模型输出不稳定、工具失败，还是审批后输入发生变化。

## 一个脱敏虚构的订单异常链路

为了说明三层架构如何协作，下面使用一个不对应真实客户和生产数据的虚构示例。

某笔订单出现履约延迟，同时客户反馈商品说明不够清楚。系统的处理链可以拆为八步：

1. 数据分析 Agent 发现异常事件，只读取聚合指标和订单摘要；
2. 服务协调 Agent 对反馈做结构化分类，判断需要哪些专业角色参与；
3. Logic Pipeline 分成履约核查、内容检查和客户回复三个分支；
4. 各分支通过只读工具获取当前状态，并携带数据 revision；
5. 模型生成原因摘要、说明优化草案和回复草案；
6. Handoff 节点合并三路结果，只传递完成审批所需的最小字段；
7. 内容修改和客户触达形成独立提案，由相应负责人确认；
8. 执行结果回到工作台，后续观察处理时效与重复反馈是否改善。

这条链路里，多 Agent 的价值不是“六个角色同时说话”，而是每个角色拥有独立上下文、工具和验收标准；跨角色协作通过结构化 Handoff 完成。

## 落地时，建议按成熟度逐级推进

一个稳妥的实施顺序是：

1. 先开放只读查询和运行追踪；
2. 再让 Agent 生成结构化草稿；
3. 接入人工审批后的低风险写操作；
4. 用真实运行结果扩充 Evals；
5. 最后才评估小范围、可撤回的自动执行。

每升一级，都需要明确通过标准、回退条件和人工接管路径。自动化不是默认终点；对于不可逆或影响客户权益的动作，长期保留人工决策可能是更合理的设计。

## 结语

企业级 Agent 平台真正要解决的，并不是“怎样再包装一个聊天窗口”，而是如何把模型放进一套清晰的工程秩序：身份有边界、流程有版本、工具有权限、发布有评测、运行有追踪、写操作有责任人。

Agent Definition、Logic Pipeline 和 Tool Registry 构成了从对话到执行的三层骨架；Evals、审批与可观测性则让这副骨架能够进入长期运行。

当每一次模型调用都能回答“基于什么、经过什么、允许什么、由谁确认”，Agent 才真正从演示能力变成可治理的业务能力。
