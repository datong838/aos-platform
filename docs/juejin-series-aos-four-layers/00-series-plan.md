# AOS 四层架构与产品设计系列写作方案

## 1. 系列定位

本系列面向企业 AI 平台架构师、技术产品经理和智能体工程师，解释一个企业 AI 操作系统为什么需要四个职责独立、又能形成闭环的层次：

```text
Workshop 工作台
  ↕
AIP 决策层
  ↕
本体数字孪生层
  ↕
数据操作系统层
```

系列不介绍某个具体客户项目，不按产品菜单罗列功能，也不披露内部实施状态。所有例子均为合成场景，重点公开可复用的架构边界、对象契约、状态机和失败路径。

## 2. 四层职责

| 层次 | 解决的问题 | 核心技术对象 | 明确边界 |
|---|---|---|---|
| 数据操作系统 | 外部数据怎样变成可追踪、可恢复、可查询的数据资产 | Connector、Sync、Pipeline、Dataset、MediaSet、Lineage | 不直接承担业务语义和 AI 决策 |
| 本体数字孪生 | 数据怎样变成业务对象、关系和允许执行的动作 | Object、Property、Link、Action、Function、Funnel | 不允许模型或界面绕过 Action 直接写入 |
| AIP 决策层 | 模型怎样在业务上下文中形成可评测、可审批的决策 | Model Gateway、Logic、Tool、Agent、Draft、Evals、Trace | 模型置信度不能替代权限和批准 |
| Workshop 工作台 | 人怎样查看、选择、审批并操作业务对象 | Module、Layout、Widget、Variable、Selection、Event | 不是任意脚本低代码平台，不直连底层存储 |

横切治理不是第五层，而是贯穿四层的共同脊柱：组织与工作区、用途和权限、Marking、版本、Lineage、幂等、审计、发布与回滚。

## 3. 发布顺序

### 01 企业 AI 平台的四层运行时：数据资产、本体、决策与工作台

- 核心问题：为什么企业 AI 不能由数据平台、聊天机器人和低代码页面简单拼装。
- 技术重点：四层职责、读链与写链、控制流与数据流、共同引用对象。
- 关键失败路径：跨层直连、语义漂移、模型直写、界面越权。

### 02 Agent 为什么不能直连数据库：Connector、Pipeline 与 Lineage

- 核心问题：进入平台的数据怎样具备来源、版本、新鲜度和恢复能力。
- 技术重点：插件化 Connector、同步状态、Pipeline DAG、Dataset/MediaSet 路由、Lineage、DLQ。
- 关键失败路径：Schema 漂移、半批成功、结果未知、原件与结构化结果失联。

### 03 本体为什么是数字孪生的核心：Object、Link、Action 与版本治理

- 核心问题：数据库表为什么不足以直接成为 Agent 的业务世界。
- 技术重点：ObjectType、LinkType、ActionType、Function、Funnel、Wiki、分支和图谱健康。
- 关键失败路径：多源冲突、悬空关系、直接写库、草稿污染生产对象。

### 04 AIP 如何把模型接入业务决策：Logic、Tool、Draft 与 Evals

- 核心问题：AIP 为什么不是一个更大的聊天机器人。
- 技术重点：模型网关、Logic Runtime、Tool Registry、Agent、Draft、Trace、Evals 和熔断。
- 关键失败路径：工具越权、证据过期、模型路由不可用、评测未通过却扩大自治。

### 05 Workshop 工作台的运行时设计：Module、Variable、Selection 与受控 Action

- 核心问题：业务工作台为什么不应退化成静态看板或任意脚本低代码工具。
- 技术重点：Module、Layout、Widget、Variable、Selection、Event、Marking 和分页。
- 关键失败路径：选择集失控、组件越权、大表拉全量、连点动作重复执行。

### 06 一条业务决策如何穿过 AOS 四层：查询、推理、审批与写回

- 核心问题：四层怎样通过稳定引用形成一条可以回放的决策链。
- 技术重点：Snapshot、ObjectSet、Decision Draft、Selection、Action Proposal、Result Reconciliation。
- 关键失败路径：版本错位、执行时权限变化、外部超时、动作完成但效果未知。

### 07 四层架构如何共享同一条治理脊柱：租户、Marking、Lineage 与 Release

- 核心问题：为什么安全、审计和交付不能分别由四层各自实现。
- 技术重点：组织/工作区隔离、字段标记继承、用途绑定、全链路谱系、版本发布和回滚。
- 关键失败路径：跨工作区引用、摘要错误降级、旧版本批准复用、无法撤销的发布。

## 4. 单篇结构

每篇使用统一结构：

1. 首屏提出工程问题并展示最小架构或状态协议；
2. 解释该层拥有的核心对象；
3. 说明与上下层的输入、输出和禁止直连；
4. 用一个完全合成的场景串起主流程；
5. 展示至少三个失败状态及系统处理方式；
6. 说明人工责任、自动化边界和可审计证据；
7. 引出下一篇，但不使用营销承诺。

## 5. 公开边界

- 不出现真实客户、业务数据、账号、内部路径、服务地址、密钥或部署拓扑。
- 不出现内部阶段编号、提交、分支、实施进度和交付结论。
- 不把目标架构描述成已经投入生产的事实。
- 不复制内部表结构和私有接口，只使用通用化对象与伪契约。
- 不使用具体商城、渠道或企业名称；案例与真实项目不存在一一映射。
- 不以对标产品作为标题和主叙事，文章只讲自身架构方法。

## 6. 掘金发布检查

- 标题采用“工程对象 + 技术机制”，不以收益或客户结果作为卖点。
- 首屏直接出现架构、协议、状态机或技术冲突。
- 分类和标签使用“人工智能”。
- 每写完一篇先做脱敏、结构、格式和标题检查，再提交。
- 提交成功后回文章管理页确认审核状态；未通过时立即暂停。
- 相邻文章实际提交时间间隔不少于 60 秒。
