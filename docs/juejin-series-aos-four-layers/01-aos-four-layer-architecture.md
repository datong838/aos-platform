# 企业 AI 平台的四层运行时：数据资产、本体、决策与工作台

企业 AI 平台最危险的架构，不是模型能力不够，而是每个组件都能绕过其他组件直接访问数据：工作台自己拼 SQL，Agent 自己读取原始表，模型生成结果后直接调用外部接口。系统看起来集成得很快，却无法稳定回答数据来自哪里、业务语义由谁定义、动作是否被批准，以及结果出了问题该回滚哪一版。

这套四层划分，本质上是在分配四种不同的系统责任：

```text
Workshop 工作台：人如何查看、选择、审批和操作
        ↕
AIP 决策层：模型如何推理、调用工具并生成决策草案
        ↕
本体数字孪生：业务对象、关系、规则和动作如何表达
        ↕
数据操作系统：外部数据如何接入、加工、版本化和追踪
```

四层不是四组菜单，而是四个拥有不同事实来源、状态机和失败边界的运行时。

## 分层的依据是“谁拥有最终解释权”

判断一项能力属于哪一层，不能只看它出现在哪个页面，而要看谁拥有最终解释权。

数据操作系统拥有数据资产的解释权。它负责连接来源、同步状态、Schema、加工过程、数据集版本和血缘，但不负责定义“这个字段在业务上代表什么”。

本体数字孪生拥有业务语义的解释权。它把数据集映射成对象、属性和关系，定义哪些动作可以改变对象状态，以及动作必须满足什么条件。

AIP 拥有决策过程的解释权。它负责选择模型、装配上下文、执行逻辑、调用工具、生成草案，并记录评测与决策谱系，但不能给自己授予数据权限或动作权限。

Workshop 拥有人机交互状态的解释权。它管理页面布局、组件、变量、选择集、事件和审批入口，却不能把界面按钮变成绕过 Action Runtime 的数据库写入器。

这条原则能解决大量边界争议：一个“查询订单”的按钮显示在工作台里，但业务查询语义属于本体；一个 Agent 调用了数据工具，工具返回的仍应是受权限约束的对象，而不是原始数据库连接。

## 读链和写链必须分开设计

四层之间至少存在两条方向相反的链路。

读链把外部事实变成用户和 Agent 可以理解的上下文：

```text
外部来源
  -> Connector / Sync
  -> Pipeline / Dataset
  -> Object / Link 水合
  -> Object Query / Tool
  -> AIP 推理或 Workshop 展示
```

写链把人的意图或模型建议变成受控业务动作：

```text
Workshop 选择集或 AIP 建议
  -> Action Proposal
  -> Criteria 与权限检查
  -> Draft / 人工审批
  -> Action 执行
  -> 对象状态与外部结果核对
  -> Lineage / Audit
```

读链追求的是来源可信、版本一致和最小披露；写链追求的是精确授权、幂等执行、结果核对和可补偿。把两条链压缩成一次模型调用，会同时失去数据治理和动作治理。

## 数据操作系统回答“事实能不能用”

数据进入平台，不等于已经成为可信事实。连接可能失效，Schema 可能漂移，一批同步可能只成功一半，文件解析也可能只有部分页面成功。

数据操作系统需要把这些状态显式化：

- 来源和连接版本；
- 同步游标、时间窗与新鲜度；
- Pipeline 使用的输入版本和变换版本；
- Dataset 或 MediaSet 的物化结果；
- 失败记录、死信和重试状态；
- 从输出回到来源的 Lineage。

上层读取的不是“某张表现在的内容”，而是一个有范围、有时间、有状态的数据快照。

## 本体数字孪生回答“事实代表什么”

数据库知道一行记录有哪些列，却不知道它在业务中可以与谁关联、处于什么生命周期，以及允许执行什么动作。

本体层把稳定业务语义建模成四类核心对象：

- ObjectType：业务实体及其属性；
- LinkType：对象之间可以验证的关系；
- ActionType：改变对象状态的受控入口；
- FunctionType：默认只读、可复用的业务计算。

数字孪生不是复制数据库，而是建立一个可查询、可行动、可治理的业务世界。数据变化先经过合并、索引和水合，AI 产生的高价值结论也只能通过 Draft 与 Action 成为新对象或属性。

## AIP 回答“如何形成一项可审查的决定”

AIP 不应该把所有逻辑藏在一段提示词里。一次可靠决策至少需要模型路由、逻辑版本、工具调用、输入对象引用、证据、输出草案和评测结果。

```yaml
decision_ref: "决策追踪引用"
object_refs:
  - "本体对象版本"
logic_version: "逻辑版本"
model_route: "模型路由快照"
tool_calls:
  - "受控工具调用摘要"
output: "建议或动作草案"
eval_status: "评测状态"
```

模型可以提出建议，但不能用置信度替代权限。涉及外部副作用时，AIP 输出的首先是 Draft，而不是“成功执行”的自然语言描述。

## Workshop 回答“人怎样在上下文中采取行动”

工作台把对象、决策和动作装进可操作的业务界面。Module 组织应用单元，Widget 负责展示与交互，Variable 连接对象查询和组件状态，Selection 表达当前选择范围，Event 把用户意图转换成查询、导航或 Action 提案。

工作台必须理解运行时权限：没有对应 Marking 的用户看不到受限组件；大对象集必须分页；批量选择要有限额；按钮连点也只能产生一次动作。

它不是四层之上的“万能前端”，而是四层闭环中负责人工判断和操作体验的一层。

## 四层需要共享稳定引用，而不是共享全部上下文

跨层协作的最小信封可以包含：

```yaml
organization_ref: "组织引用"
workspace_ref: "工作区引用"
data_snapshot_ref: "数据快照"
ontology_version: "本体版本"
policy_version: "权限策略版本"
trace_ref: "全链路追踪引用"
```

这些引用让系统能够重新检查权限、回放决策和定位版本。原始数据、完整提示词和界面状态不应无条件跨层扩散。

## 四种跨层直连必须被禁止

第一，Workshop 不能直接写数据库。否则按钮权限、Action Criteria、幂等和审计都会失效。

第二，AIP 不能绕过本体读取全部原始表。否则业务语义、字段 Marking 和对象权限无法保持一致。

第三，本体不能悄悄承担数据清洗。多源 Join、Schema 处理和质量修复应在数据操作系统完成，否则对象语义会和加工逻辑混在一起。

第四，数据层不能因为某列名称看起来像业务概念，就自动决定 Action 和权限。技术 Schema 发现可以自动化，业务语义发布仍需要治理。

## 四层平台的价值来自闭环，而不是层数

四层都可以独立产生价值：数据层可以提供可信资产，本体层可以统一业务语义，AIP 可以形成可评测决策，工作台可以交付业务应用。但企业 AI 真正难以替代的能力，来自四层共同维护同一条证据链。

当一个界面上的动作能够追到选择集、决策草案、本体对象、数据快照、批准版本和外部执行结果时，AI 才从“会回答问题”变成“可以在边界内参与业务运行”的系统能力。
