# Agent 为什么不能直连数据库：Connector、Pipeline 与 Lineage

让 Agent 直接连接业务数据库，看起来是最短的数据路径，却会立刻失去三个关键答案：模型读取的是哪个时间点的数据、Schema 变化是否已经影响判断，以及一条结论能否回到原始来源核验。

数据被复制进平台，也只能证明“有一份副本”，不能证明它可以支持 Agent 决策。来源可能已经断连，Schema 可能发生漂移，一次同步可能只完成了一部分，Pipeline 也可能使用了不同时间点的输入。

数据操作系统需要维护的不是文件和表的集合，而是一条资产状态机：

```text
Connector 已配置
  -> Schema 已发现
  -> Sync 已建立检查点
  -> Pipeline Build 已完成
  -> Dataset / MediaSet 已物化
  -> 质量与新鲜度已评估
  -> Lineage 可回放
```

只有状态、版本和来源都能被引用的输出，才有资格成为 Agent 工具返回的数据上下文。这也是数据操作系统与“给模型一个数据库账号”之间最根本的区别。

## Connector 是协议适配器，不是一次性导入脚本

一个可靠的 Connector 至少需要声明配置结构、能力、版本和生命周期，而不是把连接逻辑写进业务服务。

```yaml
connector_id: "连接器类型"
version: "适配器版本"
kind: "source | destination"
capabilities:
  - discover_schema
  - incremental_sync
  - health_check
config_schema: "公开配置结构"
secret_refs:
  - "密钥引用"
```

密钥值不应进入普通配置、日志或任务消息；运行时只读取受控引用。新增来源也不应要求修改 Connector Host 的核心代码，而应通过统一协议完成注册、配置、发现、同步、健康检查和卸载。

这种插件边界还有一个重要价值：上层只依赖 `discover`、`sync` 和 `health` 等稳定能力，不依赖某个数据库、SaaS 或文件系统的私有语义。

## Schema 发现只是候选，不是自动真理

来源报告了一组表和字段，并不意味着平台可以立即把它们当成稳定契约。Schema 发现结果需要形成版本，并与上一次结果比较：

- 新增、删除或重命名了哪些字段；
- 类型是否从可兼容变更变成破坏性变更；
- 主键、游标或分区字段是否仍然有效；
- 下游 Pipeline 和 Dataset 是否会受到影响；
- 是否需要人工确认新的敏感标记。

```text
发现 Schema
  -> 与已批准版本做 diff
  -> 兼容性检查
  -> 下游影响分析
  -> 自动接受、人工批准或阻断
```

如果来源把金额字段从数值改成自由文本，正确行为不是继续运行并把错误留给下游，而是停止受影响的 Build，保留最后一版可信资产，并明确暴露阻断原因。

## Sync 的核心是检查点和可恢复状态

同步任务不能只有“成功”和“失败”两个状态。一次长任务可能读取完成但写入未确认，也可能部分分区成功、部分分区进入重试。

一个同步运行至少需要记录：

- 使用的连接器与配置版本；
- 本次读取范围、游标或时间窗口；
- 上一次已确认检查点；
- 读取、转换和写入的分阶段状态；
- 重试次数、错误分类和人工处置结果；
- 产出的资产版本及校验摘要。

```yaml
run_ref: "同步运行引用"
source_snapshot: "来源范围"
checkpoint_before: "上次确认位置"
checkpoint_after: "本次候选位置"
write_status: "committed | partial | unknown"
output_version: "产出版本"
```

只有写入被确认后，候选检查点才能成为新的正式检查点。连接超时产生的是 `unknown`，不是可以直接重试的 `failed`；系统应先核对目标端，再决定继续、回滚或转人工。

## Pipeline 是版本化的数据程序

Pipeline 不应被理解为一张静态拖拽图。它是一段需要发布、执行和回放的数据程序：输入引用、节点配置、代码或表达式、运行环境和输出 Schema 都属于版本的一部分。

```text
Source / Dataset / MediaSet
  -> Filter / Join / Expression
  -> 可选解析或模型节点
  -> 质量检查
  -> Dataset / MediaSet 输出
```

画布保存成功，只代表定义已经持久化；Build 成功，才代表某个精确版本在一组精确输入上完成运行。上层引用的应是 Build 产物，而不是“当前画布”。

对于耗时任务，编排器还要处理超时、退避、断点恢复和取消。一个节点失败时，应根据副作用决定重试范围，不能默认从头重复所有写入。

## Dataset 和 MediaSet 解决不同资产问题

结构化记录适合进入 Dataset，保留原件、页面、图像、音视频或复杂文档布局的内容则更适合进入 MediaSet。二者不能互相冒充。

```text
表格或稳定半结构化数据 -> Dataset
需要保留原件与预览的内容 -> MediaSet
Dataset 中的结构化结果 -> MediaReference -> 原件
```

例如，文档解析后的字段可以进入 Dataset，但原始文件、页码和区域坐标仍需通过 MediaReference 指回 MediaSet。否则，Agent 得到一个抽取结果时，无法回到原文核验。

解析失败也不应阻塞整批资产。单个文件可以进入死信队列，记录解析器版本、失败阶段和重试状态；其余成功文件继续形成有范围说明的产物。

## Lineage 回答的不是“谁创建了这张表”

真正可用的 Lineage 需要从一个输出字段回到它的来源、变换和运行：

```text
输出字段
  -> Dataset 版本
  -> Pipeline Build
  -> 节点与表达式版本
  -> 输入资产版本
  -> Connector Sync
  -> 外部来源范围
```

这条链既服务故障定位，也服务影响分析。当来源字段即将删除时，系统可以提前找出受影响的 Pipeline、本体属性、工作台组件和 AIP 工具，而不是等页面报错后逐层排查。

## 数据质量必须和使用范围绑定

一个数据集很少是绝对“可用”或“不可用”。更合理的质量输出是说明哪些用途可以继续、哪些需要降级、哪些必须阻断。

```yaml
asset_ref: "数据资产版本"
freshness: "新鲜度状态"
completeness: "完整性状态"
schema_compatibility: "兼容状态"
allowed_uses:
  - "趋势观察"
blocked_uses:
  - "精确金额决策"
reasons:
  - "部分成本字段尚未闭合"
```

上层 Agent 不应只接收一个 `ready=true`，而应获得数据快照、质量范围和限制条件。质量状态发生变化后，尚未执行的决策任务也需要重新校验。

## 数据操作系统必须处理六类失败

1. **连接失效**：停止新同步，保留最后一版可信资产并标记新鲜度下降；
2. **Schema 漂移**：运行兼容性与影响检查，破坏性变化默认阻断；
3. **部分成功**：明确成功范围，不把半批结果标成完整快照；
4. **结果未知**：先对账再重试，避免重复写入；
5. **解析失败**：单文件进入死信，不阻塞整批；
6. **血缘断裂**：禁止资产晋升到受治理的上层用途。

这些状态是数据操作系统与普通 ETL 工具之间最重要的差别：系统不仅搬运数据，还对资产何时可以被引用负责。

## 上层得到的是资产契约，不是数据库入口

数据操作系统向本体层交付的最小契约，可以包含资产版本、Schema 版本、主键候选、质量状态、Marking 和 Lineage 引用。它不替本体决定业务对象，也不把数据库凭据暴露给 AIP 和工作台。

当数据资产具备稳定版本和可回放来源后，下一步才是把“字段和记录”转换成“业务对象、关系与动作”。下一篇将讨论本体为什么是数字孪生的核心，以及 Object、Link、Action 和 Function 如何共同建立可行动的业务语义。
