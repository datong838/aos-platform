# Agent 为什么需要业务本体：Object、Link、Action 与数字孪生

让 Agent 读取数据库表，并不等于让它理解业务。一行记录可以告诉模型有哪些字段，却不能稳定说明这条记录代表什么对象、与其他对象有什么关系、当前状态允许执行哪些动作，以及一次修改会产生什么副作用。

业务本体的作用，是在数据资产和 AI 决策之间建立一个可查询、可行动、可治理的数字孪生层：

```text
Dataset 版本
  -> Mapping 与发布校验
  -> Object / Property
  -> Link
  -> Action / Function
  -> Agent Tool 与工作台
```

Agent 读取的是有类型、有关系、有权限的对象；它提出的写操作也必须经过本体定义的 Action，而不是直接修改底层数据。

## Object 不是换了名字的数据库行

一个 ObjectType 至少要定义身份、属性、显示语义、生命周期和权限标记。对象实例可以来自数据集，但对象的业务含义不能由表名和列名自动决定。

```yaml
object_type: "业务对象类型"
identity:
  key: "稳定业务标识"
properties:
  status:
    type: "enum"
  updated_at:
    type: "timestamp"
backing_asset_ref: "数据资产版本"
markings:
  - "字段或对象访问标记"
```

同一个数据集可能映射出多个对象类型，一个对象类型也可能通过受治理的合并规则吸收多个来源。关键不在于复制多少行，而在于能否为上层提供稳定身份和清晰语义。

如果主键不稳定、来源版本不明确或必需属性缺失，对象类型就不应发布。让错误身份进入数字孪生，会导致关系重复、历史断裂和 Action 写错对象。

## Link 把孤立记录变成业务图

Agent 的很多判断依赖关系，而不是单个对象。例如，一个服务事件关联哪个对象版本，一份内容引用哪些商品事实，一个设备属于哪个位置。

LinkType 需要声明两端类型、方向、基数、来源和验证规则：

```yaml
link_type: "对象关系类型"
from_type: "来源对象"
to_type: "目标对象"
cardinality: "one-to-many"
source_ref: "关系来源或计算版本"
validity: "生效与失效范围"
```

关系不能只因为两个字段名称相似就自动发布。多源冲突、缺失目标和高基数扩张都需要在进入生产图之前检查。

对于高频查询，关系可以通过上游 Join 或预聚合形成；对于需要保留独立生命周期的对象，则可以使用 Link。选择依据是语义和访问模式，而不是图结构看起来更先进。

## 数字孪生需要水合状态机

数据资产发生变化后，本体不能直接覆盖当前对象。一个可观察的水合流程至少包括四个阶段：

```text
Changelog
  -> Merge
  -> Index
  -> Hydration
```

Changelog 记录进入本体的候选变化；Merge 按身份和冲突策略收敛；Index 更新检索与图索引；Hydration 生成上层查询可以读取的对象状态。

每个阶段都应保存输入版本、输出版本和错误范围。如果索引失败，Merge 结果不能冒充完整可查询版本；如果部分对象水合失败，系统也要说明可用范围。

Funnel 解决的是数据到对象的水合，不是把模型产生的所有结论自动写进长期知识。Agent 的推理结果要成为对象，仍需经过独立的 Draft、评测和 Action。

## Action 是唯一受控写入口

如果每个工作台按钮、Agent 工具和自动化流程都拥有自己的写库逻辑，本体很快会失去一致性。ActionType 应成为改变业务状态的统一协议。

```yaml
action_type: "状态变更动作"
target_type: "目标对象类型"
criteria:
  - "服务端前置条件"
parameters:
  - "受类型约束的输入"
side_effects:
  - "声明式外部副作用"
idempotency: "幂等规则"
approval_mode: "直接、单人或多人批准"
```

Criteria 必须在服务端重新检查。界面显示按钮可用、模型判断动作合理，都不能替代执行时校验。

涉及外部副作用的 Action 还要区分对象状态更新和外部调用结果。外部超时时，系统进入未知态并先对账；不能为了得到一个成功响应而无限重试。

## Function 默认只读，不能伪装成 Action

Function 用于可复用计算，例如根据对象属性计算一个评分、聚合一组对象或生成结构化比较。它应绑定输入输出类型、运行资源和超时边界，并默认只读。

需要改变对象或外部系统状态时，Function 只能返回候选结果，再由 Action 执行。允许 Function 隐藏写操作，会绕过 Criteria、审批、幂等和审计。

```text
Object 输入
  -> Function 计算
  -> 结构化结果
  -> 可选 Action Proposal
  -> 审批与执行
```

这条边界也让 Agent Tool 更容易治理：查询和计算工具可以只读，真正写操作统一进入高风险通道。

## 版本和分支保护业务语义

本体结构会变化：属性需要重命名，关系需要调整，Action Criteria 也会升级。直接修改当前版本，会让正在运行的 Agent、工作台和历史 Trace 同时失去解释基础。

更稳妥的方式是把变更作为提案：

```text
当前本体版本
  -> 创建变更分支
  -> 修改 Object / Link / Action
  -> Diff 与影响分析
  -> 校验与审批
  -> 合并并发布新版本
```

历史任务继续引用旧版本，新任务在明确生效点后使用新版本。合并时不仅检查 Schema，还要检查工具、工作台组件、策略和数据映射是否兼容。

## Wiki 和推理结论不能绕过本体治理

业务说明、规则解释和操作手册可以通过 Wiki 与对象双向关联，但 Wiki 文本不是直接写库接口。文本中提出的修改应先转换为 Action Proposal，并由相应权限和审批流程处理。

Agent 产生的高价值推理结论也不应直接变成对象属性。它需要携带证据、适用范围、模型和逻辑版本，通过 Draft 进入受治理对象，并具备过期、撤销和重新评测机制。

## 图谱健康度需要持续检查

数字孪生不是建模完成后就永远可信。平台至少要持续发现：

- 指向不存在对象的悬空 Link；
- 同一属性的多源冲突；
- 长期没有访问或来源的孤立对象；
- Function 结果与 Action Criteria 的冲突；
- 已过期但仍被 Agent 引用的语义版本；
- 没有数据血缘或权限标记的对象字段。

健康检查的产物应是可处理的问题对象，而不只是一个总分。高风险问题可以阻断相关 Tool 或 Action，低风险问题则进入治理队列。

## 本体向上交付的是可行动语义

数据操作系统向本体提供有版本的数据资产；本体向 AIP 和 Workshop 提供的则是 Object Query、Link Traversal、只读 Function 和受控 Action。

这意味着 Agent 不需要理解底层表结构，也不需要拥有数据库凭据。它只在被允许的对象世界中查询、推理和提出动作，所有输入和结果都能回到本体版本与数据来源。

下一篇将进入 AIP 决策层，讨论模型网关、Logic、Tool、Draft 和 Evals 如何把这种可行动语义变成一项可以评测、审批和回放的 AI 决策。
