# Agent 决策层如何连接模型与业务：Logic、Tool、Draft 与 Evals

把大模型接进企业系统，最简单的方式是给它一段提示词和几个 API。问题是，一次回答究竟使用了哪个模型、读取了哪些业务对象、调用了哪些工具、为什么产生这个结论，以及结论是否有资格触发动作，往往无法稳定复现。

Agent 决策层需要把一次生成过程变成一条版本化、可评测的决策运行：

```text
输入对象与任务目的
  -> 模型路由
  -> Logic 运行
  -> Tool 调用
  -> 建议或 Draft
  -> Evals 与策略门控
  -> 人工审批或返回结果
  -> Trace 与效果回流
```

模型负责生成和推理，但模型之外的运行时负责权限、版本、工具边界、失败处理和是否允许继续。

## 模型网关解决的是可替换性和运行边界

业务逻辑如果直接依赖某个模型供应商的 SDK，就会同时绑定认证、参数、错误语义、流式协议和模型名称。更稳妥的方式是通过统一模型网关，把供应商连接与上层决策逻辑分开。

```yaml
provider_ref: "供应商连接引用"
route_id: "模型路由"
model_class: "能力类型"
limits:
  timeout: "最大等待时间"
  token_budget: "本次预算"
  concurrency: "并发限制"
fallbacks:
  - "允许的备选路由"
```

路由不是简单的模型名称映射。它还需要考虑能力、数据区域、成本、延迟、配额和任务风险。处理敏感对象的任务不能因为主模型不可用，就自动切换到不满足数据边界的备选路由。

模型预热、健康状态和容量也应成为运行时事实。网关可以拒绝、排队或降级任务，但不能返回一段看似成功的占位文本，让上层误以为决策已经完成。

## Logic 把提示词变成可检查的决策程序

复杂任务不应全部藏在一段提示词中。Logic Runtime 可以把决策拆成有类型的步骤：读取输入、查询对象、执行 Function、调用模型、分支判断、生成草案和等待审批。

```text
Input
  -> Object Query
  -> Function
  -> LLM
  -> Guard
  -> Draft
  -> Output
```

每个节点都应声明输入输出类型、超时、允许的工具和失败策略。Logic 版本需要与运行 Trace 绑定；画布后来发生修改，不能改变历史运行的解释。

分支条件也不能只依赖模型自由文本。关键判断应转换成结构化结果，再由确定性 Guard 检查。例如，模型可以输出风险原因和候选等级，但是否进入高风险 Action 通道，应由服务端规则决定。

## Tool Registry 是 Agent 的能力边界

Agent 不应直接保存数据库连接、外部凭据或任意 HTTP 地址。它只能调用注册表中经过描述和授权的 Tool。

```yaml
tool_id: "工具标识"
version: "工具版本"
purpose: "允许用途"
input_schema: "结构化输入"
output_schema: "结构化输出"
required_roles:
  - "角色要求"
required_markings:
  - "数据标记要求"
risk_level: "只读、草稿或受控动作"
```

读取类 Tool 优先返回本体对象和稳定引用，而不是暴露底层表。计算类 Tool 默认只读；有副作用的 Tool 只负责生成 Action Proposal 或进入受控执行服务。

工具描述也是安全边界。外部内容中的文字不能修改工具权限，模型生成的参数也必须经过 Schema、范围和策略校验。

## Agent 配置不是一份提示词文件

一个可管理的 Agent 至少需要绑定角色、任务范围、Logic、允许的模型路由、Tool 集合、本体上下文、数据标记和升级规则。

```yaml
agent_id: "角色型 Agent"
logic_ref: "决策逻辑版本"
model_route: "允许的模型路由"
tools:
  - "工具版本引用"
ontology_scope:
  - "允许访问的对象类型"
escalation:
  - "转人工条件"
```

任务目的发生变化时，应重新判断工具和对象范围，而不是复用上一次对话中已经装配的全部上下文。

Agent 的运行状态也需要显式化：准备中、运行中、等待工具、等待审批、已完成、已阻断、结果未知和已取消。只有这样，工作台才能准确展示下一步，而不是只显示一个不断旋转的聊天气泡。

## Draft 把建议和生产状态隔离

模型输出一项修改建议时，系统首先得到的应是 Draft，而不是已经改变的业务对象。

```yaml
draft_ref: "草案引用"
target_object_ref: "目标对象版本"
proposed_change: "结构化变更"
evidence_refs:
  - "证据引用"
logic_version: "Logic 版本"
tool_versions:
  - "工具版本"
expires_at: "草案失效时间"
```

Draft 需要和生产对象物理或逻辑隔离。审批人看到的对象版本、参数和证据必须与最终执行版本一致；任何关键内容变化都会使旧批准失效。

只读问答可以直接返回结果，但只要输出准备改变对象或外部系统状态，就应进入风险分级后的 Draft 或 Action Proposal。

## Trace 记录的是决策谱系

普通日志告诉工程师发生了哪些调用；决策 Trace 还要回答为什么做出这个判断。

一条可回放的 Trace 至少关联：

- 任务目的和调用角色；
- 输入对象、数据快照和本体版本；
- Logic、提示模板和模型路由版本；
- 每次 Tool 的输入摘要、输出引用和耗时；
- Guard 的判断结果；
- Draft、审批和 Action 结果；
- 最终输出与后续效果观察。

原始敏感内容不应无限进入 Trace。系统可以保存受控引用、校验摘要和脱敏片段，并按照任务与合规要求设置保留期限。

## Evals 是发布门，而不是上线后的排行榜

Agent 的评测不能只比较回答是否流畅。不同风险层需要不同指标：

- 事实引用是否正确；
- Tool 选择和参数是否合法；
- 遇到缺失数据时是否愿意阻断；
- Draft 是否越过允许范围；
- 相同输入和版本是否具有可接受的一致性；
- 对抗性内容能否改变系统权限；
- 成本、延迟和失败率是否满足运行边界。

```text
Logic 或模型变更
  -> 离线测试集
  -> 工具与权限回归
  -> 影子运行
  -> 小范围发布
  -> 持续监测
  -> 扩大、回滚或冻结
```

评测未通过时，系统可以停留在只读或 Draft-only 阶段。模型置信度提高，不等于自动化权限可以扩大。

## 决策层必须为失败设计出口

模型不可用时，可以在满足数据边界的路由中降级；没有合规备选时应明确失败。

Tool 超时时，要区分只读查询失败和外部动作结果未知。前者可以按策略重试，后者必须先核对外部状态。

证据过期时，尚未执行的 Draft 应失效；本体版本变化导致目标对象不一致时，应重新生成或要求人工处理。

评测或运行指标触发熔断时，系统可以暂停某个 Logic、模型路由、Tool 或 Agent，而不必关闭整个平台。

## 决策层向工作台交付可操作状态

Agent 决策层向上交付的不只是聊天文本，还包括结构化结果、引用对象、决策 Trace、Draft 状态、所需审批和失败原因。

工作台据此决定展示什么、谁可以审批，以及 Action 完成后如何刷新对象。下一篇将进入 Workshop 运行时，讨论 Module、Widget、Variable、Selection 和 Event 如何把对象与决策组织成一个受权限约束的业务应用。
