# Agent 工作台如何组织业务操作：Module、Variable、Selection 与 Event

企业把 Agent 接进业务系统后，最先出现的界面通常是对话框。但真正进入日常经营时，只有对话框并不够：人需要看见业务对象、缩小范围、比较证据、修改参数、审批建议，并确认动作是否真正完成。

这意味着 Agent 工作台不是给模型套一层聊天外壳，也不是把几十张报表拼成大屏。它更像一个受控的交互运行时：把页面状态、对象选择和业务事件转换成可验证的决策上下文，再把 Agent 的建议送进正式动作链。

一个最小运行协议可以写成：

```text
ModuleVersion
  + Variables
  + ObjectQuery
  + Selection
        ↓
DecisionContext
        ↓
Agent / Logic
        ↓
Draft or ActionProposal
        ↓ 人工确认
Ontology Action
        ↓
ExecutionReceipt → Refresh
```

其中最重要的边界是：页面只能提出意图，不能绕过业务动作直接修改底层数据。

## 工作台为何不是静态看板

静态看板回答的是“发生了什么”，而工作台必须继续回答三个问题：

1. 当前操作针对哪些对象；
2. 这些对象为何被选中；
3. 接下来允许执行哪些动作。

如果页面只展示聚合指标，用户仍要到另一个系统里重新寻找对象；如果页面允许组件直接调用数据库，又会失去权限重验、幂等和审计。工作台的职责，是在“观察”和“行动”之间保存一条稳定、可追踪的上下文链。

## 六个核心对象

### 1. Module：可发布的业务单元

Module 不是一个 URL，而是带版本的业务应用单元。它声明页面使用哪些对象类型、变量、布局、事件和允许触发的动作。

同一模块的编辑态与发布态应当分离。运行中的用户访问固定版本，设计者可以继续修改下一版；只有通过校验和发布后，新版本才替换旧版本。这样才能避免一个组件调整导致所有正在处理的任务突然改变语义。

### 2. Layout 与 Widget：负责呈现，不拥有业务真相

Layout 描述区域、层级和响应式关系；Widget 负责表格、指标、关系图、详情面板或对话入口。组件读取的是对象查询结果，而不是自己拼接底层表。

组件可以声明需要哪些字段，却不应决定字段是否可见。真正的字段裁剪必须由服务端根据用户、工作区、用途和数据标记完成。前端隐藏一列从来不等于权限控制。

### 3. Variable：显式保存页面输入

日期范围、区域、对象状态和策略版本都属于 Variable。变量应有类型、默认值、约束和序列化格式，而不是散落在组件内部的临时状态。

类型化变量带来两个好处：一是页面可以被分享和回放；二是 Agent 收到的是结构化条件，而不是一段含义不稳定的自然语言。例如：

```json
{
  "timeWindow": "P7D",
  "objectStatus": ["active", "at_risk"],
  "strategyVersion": "published"
}
```

### 4. Selection：把“我看到的”变成“我正在处理的”

Selection 是工作台与 Agent 之间最关键的桥梁。它不能只保存表格行号，而要保存对象类型、对象引用、查询快照和选择时间。

当用户说“分析这些对象”时，系统传递的是一个受限的 SelectionRef。Agent 再根据权限读取必要属性，而不是让前端把整页数据塞进提示词。这样既降低上下文体积，也能在决策时重新检查对象是否仍然有效。

对于巨大选择集，系统不应传递数万个 ID。更合理的方式是保存“查询条件 + 快照版本 + 排除项”，并设置最大规模、过期时间和采样预览。

### 5. Event：描述用户意图

筛选变化、选择变化、按钮点击和审批决定都可以表示为 Event。事件至少应包含：

```text
event_id
module_version
actor
event_type
selection_ref
variable_snapshot
occurred_at
```

`event_id` 是幂等键。用户连续点击两次“生成方案”，服务端可以识别为同一请求，而不是创建两份任务。事件只声明“用户想做什么”，不直接承诺业务结果。

### 6. ActionProposal：建议与执行之间的隔离带

Agent 基于 Selection 和 Variables 形成建议后，先输出 Draft 或 ActionProposal。提案必须说明目标对象、动作类型、参数、依据、风险、有效期和所需审批。

用户点击确认时，系统不能直接复用几分钟前的授权结果，而要重新检查：对象版本是否变化、权限是否仍有效、提案是否过期、动作是否满足业务约束。通过后，提案才能进入本体动作层执行。

## 一次完整交互怎样运行

假设用户打开一个异常处理模块，过程可以拆成八步：

1. 工作台加载已发布的 ModuleVersion；
2. 服务端根据 Variables 生成对象查询；
3. 返回经过权限和字段标记裁剪的分页结果；
4. 用户勾选若干异常对象，形成 SelectionRef；
5. Agent 读取有限上下文，生成带证据引用的处理草案；
6. 用户修改参数并批准，产生 ApprovalEvent；
7. 本体动作层重新校验并执行，返回 ExecutionReceipt；
8. 工作台依据回执刷新相关对象，而不是乐观假设成功。

这条链里，页面、Agent 和动作执行者各自只拥有一种责任。页面管理交互状态，Agent 管理推理和建议，动作层管理业务不变量与写入。

## 五类不能忽略的失败状态

### 选择已经过期

用户选中对象后停留很久，对象可能已被别人处理。执行前必须比较对象版本或快照引用；若发生变化，应提示重新加载，而不是静默覆盖。

### 权限在审批前发生变化

用户能看到建议，不代表此刻仍有执行权限。所有高影响动作都应在提交时重新鉴权，并记录授权策略版本。

### 大表被组件拉成全量

表格组件只能使用服务端分页、排序和过滤。导出、批量选择和聚合查询应走独立限额，不能用前端遍历分页伪装成全量接口。

### 连续点击造成重复动作

按钮禁用只能改善体验，不能保证一致性。Event 和 Action 都需要幂等键；遇到网络超时，客户端应查询原事件状态，而不是自动创建新动作。

### 执行结果处于未知态

外部系统超时不等于失败。回执应区分 `SUCCEEDED`、`FAILED`、`UNKNOWN` 和 `RECONCILING`。处于未知态时，工作台展示“正在对账”，禁止用户盲目重试高风险动作。

## Agent 对话怎样进入工作台

对话不是独立页面，而可以成为 Module 中的一个 Widget。它自动继承当前模块版本、变量快照和选择集，但只接收策略允许的字段。

反过来，Agent 也不应该用一段文本“控制界面”。它可以返回结构化的 UI Intent，例如建议高亮某组对象、打开某个详情区域或生成一个新筛选条件；工作台验证该 Intent 是否在模块声明范围内，再决定是否执行。

这种双向契约让自然语言具有操作力，又不会让模型获得任意前端控制权。

## 断网和降级时如何保持诚实

工作台可以缓存已授权的只读快照，但必须展示数据时间和离线标记。断网期间生成的内容只能保存为本地草稿，不能伪装成已经提交的业务动作。

恢复连接后，系统重新验证 ModuleVersion、Selection、权限和对象版本。任何一个条件发生变化，都应要求用户再次确认。离线能力解决的是连续工作，不是绕过治理。

## 衡量工作台的不是页面数量

真正有意义的指标包括：

- 从发现问题到形成可审批提案的时间；
- 过期 Selection 被执行前拦截的比例；
- 重复事件被幂等机制吸收的比例；
- 未知态动作完成对账的时间；
- 每次决策能够回放到的证据完整度。

一个成熟的 Agent 工作台，不是组件越多越好，而是能否让人、模型和业务动作通过稳定契约协作。
