# 电商数字同事协作系列写作方案

## 1. 系列定位

本系列面向关注企业智能体、多智能体协作和 AI 工程落地的技术读者。

前一系列解决的是“能力怎样被装进可组合资产并安全接入企业平台”；本系列转向“多个专业智能体怎样围绕同一个经营目标协作”。文章不介绍某个具体项目，也不按产品功能逐项说明，而是使用虚构电商经营场景讲解可复用的人工智能工程方法。

系列主线：

```text
经营问题
  -> 数据与证据
  -> 经营方案草案
  -> 人工批准
  -> 多智能体任务图
  -> 最小化交接
  -> 专业角色执行
  -> 结果观察与归因
  -> 受治理的经验候选
```

其中，“数据参谋”是观察、诊断、规划、协调和复盘角色；内容、导购、客服、客户运营和活动策划是专业执行角色。人类经营负责人始终保留目标、预算、风险边界和高风险动作的最终批准权。

## 2. 公开写作边界

### 2.1 严禁披露

- 真实客户、商家、员工、账号、渠道身份和业务关系。
- 真实订单、客户、转化、预算、毛利、库存、投诉和经营指标。
- 仓库路径、内部模块名、内部代号、分支、提交、版本和实施进度。
- 真实接口地址、数据库结构、密钥、权限配置、部署拓扑和故障记录。
- 能够通过组合信息反推出当前项目、客户或团队的信息。
- 未公开的截图、界面、流程图和内部术语映射。

### 2.2 允许公开

- 经过抽象的架构模式、状态机、任务契约和交接原则。
- 业界通用的人工智能、多智能体、评测、可观测性和安全概念。
- 完全虚构的企业、角色和事件。
- 与真实数据不存在比例映射关系的合成示例。
- 明确标注为“设计方法”“目标架构”或“经营推演”的内容。

### 2.3 公开术语

| 内部素材类型 | 公开文章表述 |
|---|---|
| 具体平台或项目名 | 企业智能体平台 |
| 内部阶段编号 | 建设阶段或成熟度阶段 |
| 内部领域对象名 | 经营方案、任务、交接对象、效果复盘 |
| 客户最小对象 | 最小客户上下文 |
| 内部适配模块 | 受控数据或渠道适配器 |
| 生产写回模块 | 受控业务动作 |
| 内部工作台名称 | 经营指挥台或数字同事工作台 |

## 3. 叙事原则

1. 每篇只解决一个核心问题，不堆叠完整平台能力。
2. 以经营事件驱动故事，不以角色功能列表驱动故事。
3. 每个判断都说明数据来源、证据边界和不确定性。
4. 每个多智能体协作场景都展示任务依赖、交接字段和失败路径。
5. 每个公开动作都保留人工批准，不暗示无限自动化。
6. 每篇至少包含一个技术结构：流程、状态机、契约、伪代码或验证清单。
7. 案例数字能少则少；必须出现时使用明显的合成示例，不模拟真实经营数据。
8. 不写“已经上线”“生产验证”等结论，除非存在可公开核验的证据。

## 4. 系列文章规划

### 01 经营 Agent 如何编排一次可审计闭环：数据快照、方案版本与任务 DAG

- 核心问题：经营 Agent 如何把数据判断转换为可追踪、可批准、可复盘的任务图。
- 故事：一次虚构的经营晨会，从异常信号到任务分派和效果复盘。
- 技术重点：数据就绪、证据对象、方案版本、任务图、观察窗口和归因。
- 安全重点：证据不足时阻断；方案批准不等于批准具体外部动作。

### 02 从内容信号到订单归因：多 Agent 接力中的契约、状态与版本

- 核心问题：内容、咨询、推荐、订单和服务结果如何通过版本化契约形成可归因链路。
- 故事：内容草稿产生线索，导购完成需求诊断，客服承接体验反馈。
- 技术重点：内容事实包、线索信号、推荐草稿、服务工单和结果回流。
- 安全重点：不虚构库存、价格、功效、优惠和平台能力。

### 03 复购 Agent 如何安全协作：同意状态、频控与最小客户上下文

- 核心问题：多个 Agent 如何在用途授权、频率限制和最小披露下协作处理复购机会。
- 故事：识别复购窗口、安排触达、生成分群内容、推荐适配商品。
- 技术重点：最小客户上下文、同意状态、频控、生命周期和退出机制。
- 安全重点：不使用敏感属性推断购买力，不绕过退订和渠道限制。

### 04 活动不是发优惠券：活动策划师如何在毛利、库存和投诉之间做决策

- 核心问题：活动智能体怎样避免用促销掩盖经营问题。
- 故事：在库存、毛利和履约约束下形成活动方案并拆分任务。
- 技术重点：预算模拟、护栏、跨角色任务图、暂停条件和增量归因。
- 安全重点：价格、库存、预算和公开发布均需要精确版本批准。

### 05 一次投诉如何改变内容和推荐：客服反馈驱动团队反向学习

- 核心问题：多智能体协作为什么必须有反向反馈链。
- 故事：客服聚合问题，数据参谋判断规模，内容和导购修正表达与承诺。
- 技术重点：问题标签、聚合阈值、影响评估、修订任务和效果验证。
- 安全重点：只传递脱敏聚合信息，不扩散客户原始会话。

### 06 六个 Agent 为什么不能共享全部上下文：数字同事之间如何安全交接

- 核心问题：共享越多是否协作越好。
- 故事：一条高意向线索在多个角色间传递时如何做最小披露。
- 技术重点：交接契约、用途绑定、字段白名单、标记继承和过期时间。
- 安全重点：跨租户、跨用途、过期和越权交接必须失败关闭。

### 07 数字团队怎样越做越聪明：经验为什么必须经过治理才能成为记忆

- 核心问题：任务历史为什么不能直接变成长记忆。
- 故事：一次有效推荐如何从任务经验变成待审查的方法候选。
- 技术重点：四层记忆、候选晋升、评测回归、冲突和撤回。
- 安全重点：客户信息不进入共享记忆，一次成功不形成长期规律。

### 08 从建议到真实动作：数字同事什么时候才可以自动发布、触达和改价

- 核心问题：什么时候可以从草稿辅助进入有限自动执行。
- 故事：内容发布、客户触达和业务写操作的不同风险等级。
- 技术重点：动作提案、精确批准、幂等、审计、补偿和人工接管。
- 安全重点：从低风险、可逆动作开始，不把模型置信度当作授权。

## 5. 第一篇结构

标题：经营 Agent 如何编排一次可审计闭环：数据快照、方案版本与任务 DAG

1. 首屏定义经营闭环的状态协议，避免以营销故事开场。
2. 展示从数据快照到效果复盘的最小闭环。
3. 解释数据参谋的五项职责：观察、诊断、规划、协调、复盘。
4. 展示方案对象和任务对象的最小字段。
5. 用内容、导购、客服三角色说明任务图和最小交接。
6. 说明失败路径：数据不新鲜、证据冲突、任务阻塞、效果无结论。
7. 说明人工责任和自动化边界。
8. 以“让组织形成可验证经营循环”收束。

## 6. 发布前四道检查

### 6.1 泄密检查

- 搜索真实项目名、客户名、内部代号、目录、接口、版本和数字。
- 检查虚构情节是否仍与真实项目形成一一映射。
- 检查图表、代码块和对象字段是否暴露内部实现。

### 6.2 事实检查

- 不把设计目标写成已实现能力。
- 不声称拥有未经核验的平台接口和自动发布能力。
- 不使用无来源的转化率、行业排名和绝对效果结论。

### 6.3 技术自洽检查

- 方案、任务、交接、执行和复盘的版本引用一致。
- 未批准方案不能生成可执行任务。
- 数据缺失、权限不足和外部未知状态有明确失败路径。
- “任务完成”和“业务有效”严格分开。

### 6.4 平台审核风险检查

- 标题不夸大、不承诺收益、不使用攻击性比较。
- 正文不包含引流信息、账号、二维码和隐蔽推广。
- 技术术语有解释，不堆叠无法理解的内部名词。
- 虚构案例明确用于方法说明，不包装成真实客户背书。
- 标题优先使用工程对象与技术机制，不以成交、增长或客户结果作为主要卖点。
- 首屏前置状态机、契约或任务图，经营故事仅用于解释技术设计。
- 连续文章先单篇验证审核结果；未通过且平台未给原因时，不批量重复提交。
