# 经营 Agent 如何编排一次可审计闭环：数据快照、方案版本与任务 DAG

经营 Agent 的核心能力不是生成晨报，而是维护一条可审计的判断链：每个结论引用哪个数据快照，哪一版方案获得批准，哪些任务因此被创建，最终结果又如何回到同一条证据链。

如果这些对象之间没有稳定引用，模型即使解释正确，也无法回答四个工程问题：输入是否仍然有效、执行是否经过授权、并行任务是否属于同一方案，以及指标变化能否归因于真实动作。

可以把最小闭环表示为一条状态协议：

```text
数据快照
  -> 就绪检查
  -> 证据化诊断
  -> 方案草案
  -> 精确版本批准
  -> 任务 DAG
  -> 受控交付
  -> 观察窗口闭合
  -> 效果结论
```

其中任何一步失败，系统都应进入明确的阻断、降级或待人工处理状态，而不是继续生成更长的自然语言。下面以一个合成经营场景说明这套协议。

## 第一关是冻结可引用的数据快照

经营系统发现咨询量保持稳定，但从咨询到支付的转化出现异常。直接调用模型生成建议，会让后续任务依赖一组持续变化的数据。

可靠的做法恰恰相反：先判断数据是否有资格支持决策。

经营 Agent 应先冻结快照引用，再检查三个问题：

- 新鲜度：订单、商品、库存、咨询和售后数据分别更新到什么时间；
- 完整性：关键渠道、商品或客户阶段是否缺失；
- 一致性：支付、退款、库存和价格等事实是否来自同一个可追溯版本。

检查结果不应只是一个 `ready=true`。更合理的输出是带快照引用和分析范围的就绪状态：哪些判断可以继续，哪些只能降级，哪些必须阻断。

```yaml
status: degraded
snapshot_ref: "经营快照版本"
allowed_analysis:
  - consultation_funnel
blocked_analysis:
  - channel_profit
reasons:
  - "部分渠道成本数据尚未闭合"
```

这一步看似保守，却决定了后面所有建议是否可信。缺少成本数据时，系统可以研究咨询漏斗，但不能假装知道哪个渠道更赚钱。

## 诊断对象必须区分事实、证据和假设

内部数据告诉系统“发生了什么”，外部信息帮助解释“为什么可能发生”。两者不能混成一段自然语言后直接交给模型。

外部趋势、平台规则和公开讨论应先变成证据对象，至少记录来源、时间、支持的判断、适用范围和失效时间。网页里的文字是待验证材料，不是可以指挥 Agent 的运行指令。

```yaml
source: "公开来源"
retrieved_at: "采集时间"
claim: "它支持的具体判断"
scope: "适用渠道与场景"
confidence: "置信等级"
expires_at: "重新核验时间"
```

在这个合成场景中，经营 Agent 可能发现异常主要集中在某类咨询；与此同时，公开渠道出现了新的用户疑问。但这仍然只能形成“待验证假设”，不能直接得出“应该降价”或“应该加大投放”。

一个合格的机会判断至少要区分：

1. 已被内部事实支持的现象；
2. 被外部证据支持的解释；
3. 尚未验证的假设；
4. 可能推翻结论的数据缺口。

## 自然语言建议必须编译成方案版本

自然语言建议很难承担责任。“优化内容”“提升转化”既没有边界，也无法验收。数据参谋应该生成一个版本化的经营方案草案。

方案至少包含：

- 要解决的问题和当前基线；
- 目标指标、观察窗口和成功条件；
- 毛利、库存、体验与合规护栏；
- 使用的数据快照和外部证据；
- 待验证假设及其不确定性；
- 涉及的数字同事、任务依赖和预算上限；
- 暂停条件、回滚方式和复盘时间。

人类经营负责人批准的不是一句“可以做”，而是这份方案的精确版本。方案内容、预算、目标或证据发生变化后，旧批准不能自动覆盖新版本。

这条规则把责任边界说清楚了：模型可以提出方案，人类决定是否采用；批准一个经营方向，也不等于批准所有后续发布、触达和价格动作。

## 批准后的方案才能生成任务 DAG

方案获批后，数据参谋将它拆成有依赖关系的任务图。对于这次咨询转化异常，可以形成如下协作链：

```text
数据参谋：定位异常范围并冻结证据
  -> 内容官：检查内容是否造成错误预期，生成修订草稿
  -> 导购顾问：分析用户约束，生成推荐与对比草稿
  -> 客服专员：聚合高频问题，形成服务反馈
  -> 数据参谋：观察咨询、支付、退款与投诉变化
  -> 效果复盘
```

每个任务都需要负责人、输入引用、依赖、允许的数据域、允许的工具、预期产物、验收条件和失败状态。

例如，内容官不能只收到一句“最近转化不好，重写文案”。它应该得到经过授权的商品事实、聚合后的问题标签、渠道约束和目标指标，但不需要客户姓名、联系方式或完整咨询记录。

这就是最小化交接：下游只获得完成当前任务所必需的信息。

```yaml
from: data_advisor
to: content_specialist
purpose: "修订容易引发误解的内容"
allowed_fields:
  - product_fact_refs
  - aggregated_question_tags
  - channel_constraints
forbidden_fields:
  - customer_identity
  - raw_conversations
expires_at: "任务截止时间"
```

导购顾问同样不能凭内容互动就猜测客户需求。信息不足时，它应输出“需要澄清”，而不是为了提高成交概率强推单一商品。客服专员也不能因为模型判断合理，就承诺系统中不存在的退款、补偿或到货时效。

## “交付完成”和“经营有效”是两种状态

内容草稿写完、推荐建议生成、客服反馈提交，只能证明任务交付了。它们是否改善经营，要等观察窗口闭合后才能判断。

数据参谋需要把结果分成至少五类：

- 有效：目标改善，且护栏未恶化；
- 无效：动作完成，但目标没有可信变化；
- 有害：局部指标改善，却带来退款、投诉或毛利恶化；
- 证据不足：样本、时间或对照不足；
- 未执行：任务交付了，但真实动作没有发生。

归因时应优先使用分组、分批、前后对照或其他可解释方法，并记录价格、库存、节日和渠道流量等干扰因素。如果没有足够证据，系统必须允许输出“暂时无结论”。

这比生成一份充满确定语气的复盘报告更有价值。

## 经营 Agent 真正管理的是判断链

一个可靠的数据参谋并不替代人类经营负责人，也不直接接管所有专业工作。它管理的是五件事：

1. 观察：确认数据是否足以支持判断；
2. 诊断：区分事实、证据、假设和未知；
3. 规划：生成带目标、护栏和版本的方案草案；
4. 协调：把批准方案拆成可追踪的专业任务；
5. 复盘：判断动作是否执行、是否有效，以及经验能否进入下一轮。

真正成熟的多智能体系统，不是让六个 Agent 同时发表意见，而是让每个角色在明确职责和权限内接力，并让每一次关键判断都能追到数据、证据、批准、任务和结果。

数据参谋也因此不再是一块更聪明的看板。它更像数字团队的参谋长：不替专业同事完成所有工作，但确保整个组织围绕同一目标形成一条不会失控、能够验证、可以复盘的经营循环。
