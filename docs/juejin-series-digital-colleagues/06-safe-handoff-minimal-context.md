# 多 Agent 如何安全交接：最小上下文、用途绑定与权限重验

多智能体协作有一个很自然的误区：为了让下游 Agent 更聪明，把上游的完整对话、客户资料、工具结果和历史记忆一起传过去。

上下文确实变多了，风险也同时变大了。无关隐私、过期事实、错误判断和外部内容中的操控性指令会沿协作链扩散；出现问题后，也很难回答下游到底使用了哪部分信息。

可靠协作追求的不是最大共享，而是最小充分交接。

## 交接对象不是聊天记录

仍以完全虚构的内容获客场景为例。内容官识别到一条高意向互动，需要交给导购顾问继续处理。

导购真正需要的是来源内容、关注商品、意图摘要、客户主动提供的约束、同意状态和过期时间。它不需要内容官的系统提示词、完整评论区、平台凭据或其他客户资料。

```yaml
source_task: "内容线索识别任务"
target_role: "导购顾问"
purpose: "响应客户主动提出的选购问题"
allowed_fields:
  - content_ref
  - product_refs
  - intent_summary
  - consent_state
forbidden_fields:
  - platform_credentials
  - unrelated_conversations
  - other_customer_data
expires_at: "交接失效时间"
```

这种结构化对象明确了来源、接收者、用途、字段和生命周期。自然语言可以描述任务目标，但权限不能靠自然语言猜测。

## 最小客户上下文应该按用途组装

同一个客户，在不同任务中需要的上下文并不相同。

- 内容官只需要匿名化人群特征和内容效果，不需要个体身份；
- 导购顾问需要当前咨询约束和商品事实，不需要完整售后历史；
- 客服专员需要受控订单引用、问题摘要和适用政策，不需要营销画像；
- 私域管家需要同意状态、触达节奏和关系信号，不需要详细地址；
- 数据参谋优先读取聚合结果和产物引用，不读取原始自由文本。

最小化不是简单删除字段，而是服务端根据接收者和目的重新组装上下文。

## 授权不能沿链路自动继承

上游有权读取某项数据，不代表下游自动拥有相同权限。每次交接都要重新验证：

1. 来源任务已经批准且仍然有效；
2. 产物存在、未撤回且没有过期；
3. 接收角色有权为当前用途读取这些字段；
4. 来源和目标属于相同的组织与项目边界；
5. 数据标记没有被降低；
6. 客户同意状态没有发生变化。

任一条件不满足，交接应该失败关闭。系统不能让模型通过“为了更好服务客户”这样的理由自行扩大权限。

## 数据标记要向下游传播

交接对象的敏感等级，至少继承所有输入中的最高等级。即使生成的是摘要，只要摘要仍可能识别个人或推断敏感事实，就不能自动降级。

```text
订单引用：受限
咨询摘要：受限
公开商品事实：公开

交接对象最终标记：受限
```

只有经过专门的去标识、聚合和重新评估流程，数据才可能进入更宽的共享范围。

## 过期、撤回和冲突必须是一等状态

客户可能在任务执行中撤回同意，商品可能变价，内容可能被撤回，订单状态也可能变化。交接对象因此必须带版本和失效时间。

下游开始工作前需要重新确认关键引用。执行过程中发生变化时，应进入 `BLOCKED`、`NEEDS_REFRESH` 或 `REVOKED`，而不是继续使用旧上下文。

还要测试这些负向场景：

- 跨组织或跨项目交接；
- 为售后目的收集的数据被用于营销；
- 客户撤回同意后任务仍尝试触达；
- 下游请求未在白名单中的字段；
- 上游产物已过期或被撤回；
- 外部内容中的提示词注入进入交接摘要；
- 两个任务并发修改同一交接状态。

负向测试通过，才说明交接边界真实存在。

## 共享记忆也要遵守相同原则

一个 Agent 的完整工作记忆不应直接暴露给其他角色。团队共享区只适合保存经过治理的商品事实、品牌规范、政策、平台规则、协作契约和脱敏经营知识。

个体客户会话、临时推理和未经验证的经验，应保留在受控范围内，并按生命周期清理。

## 安全交接反而让协作更清楚

限制上下文并不会让数字同事变笨。相反，它迫使系统明确每个角色需要什么、为什么需要、能用多久，以及产出应该交给谁。

多智能体协作的质量，不取决于共享窗口有多大，而取决于任务契约、字段边界、授权检查和失败状态是否足够清楚。
