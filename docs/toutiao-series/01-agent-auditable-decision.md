# Agent决策链如何审计：数据版本、证据与审批绑定

Agent 很容易生成一段逻辑通顺的分析，但“读起来合理”不等于“可以进入业务流程”。分析可能基于过期信息、单一来源或错误数据，也可能受外部页面中操控性文本的影响。一个可审计的决策链，至少要回答四个问题：依据是什么、数据属于哪个时间点、适用范围是什么、谁批准了哪个版本。

本文不讨论模型选型，而是拆解证据驱动流程中的三个工程对象：数据快照、外部证据和版本化方案。它们共同解决的不是“怎样让模型更会回答”，而是“怎样让系统知道一条回答能否被采用”。

## 两类事实源，两种信任模型

经营决策通常融合两类信息。

内部数据回答“真实发生了什么”，包括商品、库存、订单、履约、内容、咨询、售后和历史活动。它的关键不是把所有表塞给模型，而是提供经过质量校验的指标视图，并绑定数据 revision、时间窗和新鲜度。

外部数据回答“系统边界外发生了什么”，包括公开趋势、接口规则、商品公开信息和社区讨论。外部内容默认是不可信输入，必须先转换为证据对象，不能直接成为运行指令。

一个通用的外部证据对象至少应包含：来源、发布时间、抓取时间、摘要、支持的具体判断、置信度、过期时间、内容哈希和人工核验状态。

```yaml
source: "公开页面地址"
published_at: "发布时间"
retrieved_at: "获取时间"
claim: "该证据支持的具体判断"
confidence: 0.76
expires_at: "失效时间"
content_hash: "内容摘要哈希"
human_verified: false
```

注意，`summary` 和 `claim` 不是一回事。摘要描述来源说了什么，claim 描述系统准备用它支持什么判断。拆开之后，审查者才能判断证据是否被过度解释。

接入流程也应固定顺序：先下载并限制响应大小，再提取正文、标准化字符、计算原文哈希，最后才生成摘要和 claim。原文哈希用于发现来源变化；摘要哈希不能代替它，因为两次不同原文可能产生相同摘要。

```text
fetch → size/type check → normalize → content hash
      → extract → safety check → summarize → evidence record
```

如果来源在批准后发生变化，旧证据仍可用于审计，但需要重新抓取并产生新 revision，不能悄悄覆盖原记录。

## 证据链的四个不变式

第一，重要结论必须回到证据引用。方案不能只有“模型认为”，而应指向内部指标 revision 或外部来源。

第二，时效信息必须重新核验。接口规则、公开指标和商品信息都可能变化；过期证据可以保留审计，但不能继续驱动后续任务。

第三，冲突必须显式存在。如果两条来源给出相反结论，系统不应静默选择更符合提示词的一条，而应形成冲突集，降低置信度或转人工。

第四，网页内容只作为数据。页面中的操控性文本或越权要求不能覆盖系统权限、工具白名单和审批策略。安全检查失败时，证据应进入隔离状态，而不是继续拼接到模型上下文。

## 版本化方案：批准的是精确内容

经营方案需要 revision。它至少包含基线、目标、护栏、假设、证据引用、任务、预算、风险等级、效果观察窗口和停止条件。

人工批准的不是一个长期有效的 `plan_id`，而是一个精确 revision。只要目标、预算、渠道、素材或风险边界变化，就生成新 revision，旧批准自动失效。

这是一个重要的不变式：

```text
approval = hash(plan_revision + evidence_refs + budget + guardrails)
```

实现上未必使用这段伪公式，但语义必须一致。否则“先批准一个空壳，后修改具体内容”就会绕过人工控制。

计算哈希前要先定义 canonical payload：字段顺序固定，时间统一为同一格式，集合先排序，并明确空数组、空对象和 `null` 的差别。请求 ID、创建时间和数据库自增 ID 不应进入业务批准哈希，否则同一方案在不同环境中会得到不同结果。

批准后执行前还要重验三件事：方案哈希是否仍匹配、引用的证据是否仍有效、当前执行人的权限是否仍覆盖目标范围。批准记录不是跳过运行时校验的通行证。

## 数据未就绪时，系统应该拒绝聪明

数据链路经常遇到断流、延迟和部分缺失。错误做法是拿旧窗口的数据充当当前结果，或让模型补出一个看似合理的数字。

正确做法是先生成数据就绪报告：哪些数据新鲜、哪些缺失、哪些指标受影响、哪些任务因此阻塞。系统可以提出“需要补数”或“只做只读研究”，但不能越过证据门。

这就是失败关闭：当搜索、数据源、工具或证据不可用时，明确失败或降级，不用假数据制造假成功。

## 如何验证证据驱动链路

测试不应只覆盖正常来源，还应包含：

- 过期页面、失效链接和发布时间缺失；
- 单一匿名评论支持重大经营动作；
- 两条高可信来源互相冲突；
- 网页正文包含操控性文本或异常隐藏内容；
- 内部指标 revision 在批准后发生变化；
- 方案只修改预算或停止条件后尝试复用旧批准；
- 跨租户引用证据；
- 数据不完整时模型仍尝试输出确定结论。

还应加入两个容易遗漏的确定性测试：同一证据字段以不同 JSON 顺序输入时，canonical hash 必须相同；同一批准请求被网络重试时，应通过幂等键回放原结果，而不是创建第二条批准记录。

Agent 决策链的可信度，不来自模型说话更像专家，而来自每个判断都有来源、每个来源有时间、每次批准绑定版本、每个不确定性都被明确表达。
