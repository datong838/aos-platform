# 多智能体如何可靠协作：任务DAG与最小交接

最省事的多智能体协作方式，是把一段完整对话交给下一个 Agent。它也最危险：客户隐私、无关指令、过期事实和上游错误会一起扩散；出了问题，也很难知道下游究竟使用了哪一部分。

可靠协作的核心不是“共享更多上下文”，而是建立显式任务契约，并坚持最小披露。

## 任务不是一句自然语言

一个可执行任务至少需要这些字段：

- 所属方案及其 revision；
- 负责人、协作方和人工 owner；
- 目标、输入引用、前置依赖和验收指标；
- 允许的数据域、工具、渠道、预算和最长时间；
- 风险等级、审批策略和禁止动作；
- 预期产物、产物版本和证据引用；
- 效果观察窗口、停止条件和回滚说明。

自然语言仍然可以描述目标，但权限和边界必须是机器可校验的结构化字段。

## 用 DAG 表达业务依赖

任务图要保持无环。每个节点只有在依赖满足后才能进入运行态，失败、暂停、撤回和超时都要有明确传播规则。

```text
PLANNED → PENDING_APPROVAL → APPROVED → ASSIGNED
        → RUNNING → DELIVERED → ACCEPTED → OBSERVING
        → REVIEWED → CLOSED

任一阶段都可能进入：BLOCKED / REJECTED / PAUSED / FAILED
```

“交付”和“验收”必须分开。内容 Agent 生成文案，只代表交付；事实性、品牌和合规检查通过后，才算验收。类似地，产物被业务使用后还要进入效果观察，不能在文件生成时就宣布任务成功。

## Handoff 是能力边界，不是聊天记录

Agent 之间的交接对象应包含：来源任务、目标任务、用途、输入引用、允许字段、禁止字段、过期时间、风险等级和预期输出 Schema。

例如，内容互动产生一条高意向线索后，导购角色只需要知道来源渠道、关注商品、用户意图和同意范围，不需要手机号、地址或完整聊天记录。

服务端在交接前至少验证：

1. 来源任务已经批准，产物存在且未过期；
2. 目标角色有权接收该用途的数据；
3. 字段在客户授权和任务允许范围内；
4. 来源与目标属于同一租户和项目；
5. 风险等级没有被下游降低。

任一条件不满足，都应该失败关闭。

## 为什么要做职责分离

多智能体的审批不能简化成一个 `approved=true`。中高风险动作至少要区分请求者和批准者，且批准绑定精确 revision 与哈希。

职责分离解决的是“自己提出、自己批准、自己执行”的单点风险。即使调用方拥有管理员角色，也不应该绕过主体分离、数据标记和用途限制。

一个常被忽略的细节是：上层经营方案获批，不代表所有具体动作自动获批。方向、预算获批之后，真实发布仍可能需要对具体素材、账号、时间和载荷再次批准。

## 并发和幂等同样属于协作协议

两个 Worker 同时领取同一任务时，必须通过 CAS 或执行租约保证只有一个成功。每次变更都携带幂等键；同一个键与同一请求应回放原结果，同一个键与不同请求必须冲突。

否则，一次网络重试可能产生两个优惠、两条公开内容或两次客户触达。

## 负向测试比顺滑 Demo 更重要

协作链至少应测试：

- 环形依赖和超深依赖；
- 上游产物过期或被撤回；
- 下游请求超出允许字段；
- 跨租户、跨用途、跨数据标记；
- 旧方案 revision 的任务尝试继续执行；
- 请求者批准自己的高风险任务；
- 两个 Worker 并发领取；
- 工具未注册、超时或返回未知状态；
- Handoff 中混入提示词注入。

多智能体协作的工程质量，不由 Agent 之间的对话有多自然决定，而由任务、交接、状态和责任是否可验证决定。
