# Agent 记忆不是向量库：四层记忆与经验晋升治理

给 Agent 接一个向量库，然后把所有对话、结果和网页都写进去，常被称为“长期记忆”。它确实能让系统召回更多文本，也会同时放大过期事实、客户隐私、偶然经验和恶意指令。

Agent 真正需要的不是无限存储，而是受治理的经验系统。

## 先区分四类记忆

第一层是 Working Memory：当前任务的输入、中间结果和临时判断。它的生命周期应该与任务一致，过期后清理，不参与长期召回。

第二层是 Episodic Memory：一次任务或活动的受控经历摘要。例如“在某类条件下，一次活动没有达到目标”。它必须带上下文、结果和 TTL，不能泛化成永恒规律。

第三层是 Semantic Memory：经多次证据支持的稳定事实，如品牌规范、商品事实和常见业务知识。它仍需版本化和定期重验证。

第四层是 Procedural Memory：怎样更好完成任务的方法，例如“推荐前先检查库存和替代项”。它最可能改变 Agent 行为，因此需要最严格的评测和批准。

四层的区别不是标签，而是生命周期、召回范围和治理强度不同。

## 一次成功只能产生候选

任务经验不能直接进入长期记忆，应该先形成 Memory Candidate，并经历：

```text
候选草稿
  → 提交
  → 去敏与安全检查
  → 质量评测
  → 人工审查
  → 批准
  → 激活
  → 过期 / 替代 / 撤回
```

晋升前至少要有任务、产物、业务结果、效果复盘和证据引用；正文要声明适用条件、不适用条件、反例、置信度和有效期。

共享记忆和流程记忆还要满足 Maker-Checker：创建人不能独自批准自己的候选。

## 记忆正文要结构化

只保存一段自由文本，会让检索器和模型难以区分事实、建议和限制。更稳妥的结构是：

```yaml
claim: "被验证的结论"
when_to_use: ["适用条件"]
when_not_to_use: ["反例和禁用条件"]
steps: ["建议步骤"]
evidence_refs: ["证据引用"]
confidence: 0.71
expires_at: "重验证时间"
```

向量索引只是检索副本，权威正文仍应保存在支持事务、revision 和撤回的存储中。索引可以重建，治理状态不能只存在索引元数据里。

## 检索前先做策略过滤

推荐的检索顺序是：身份与用途校验 → 租户/项目/数据标记过滤 → 只保留激活且未过期的 revision → 按层级和适用范围筛选 → 关键词/向量召回 → 证据新鲜度与冲突重排 → 按 token 和最小披露预算装配上下文。

这意味着“相似度最高”不是第一原则。一个高度相似但跨租户、过期或用途不符的记忆，得分再高也不应被召回。

每次运行还要记录实际使用的记忆 ID 和 revision。这样出现错误时，才能判断是模型问题、检索问题，还是记忆本身有害。

## 冲突、过期和投毒必须是一等状态

同一结论出现互相矛盾的证据时，应形成冲突集并默认降权或阻断。平台规则、价格和商品事实超过 TTL 后进入过期状态，不能继续作为硬事实。

网页、用户输入和外部评论只能成为证据候选，不能直接晋升为流程记忆。异常高频候选、单一来源自证、循环引用和指标异常跃升都应进入隔离区。

发现隐私或密钥后，必须立即禁用对应 revision，并清理派生索引；审计历史可以保留，但新任务不能再召回。

## 怎么证明 Agent 真的“变聪明”

记忆上线前后应做基线 A/B，至少比较任务完成率、事实准确率、人工修改率、延迟、token 成本、错误复用和安全违规率。

只有质量有显著改善且安全不退化，才扩大召回比例。积累更多文本、命中更多相似片段，都不能单独证明能力提升。

可治理的记忆必须能解释从哪里来、为什么适用、何时失效、被谁批准、影响了哪些运行，并且能立即撤回。做到这些，记忆才是能力资产，而不是一个越来越难清理的数据沼泽。
