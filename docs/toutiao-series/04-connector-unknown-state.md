# 连接器超时后为什么不能重试：未知态与幂等设计

系统调用外部平台发布内容，等待数秒后超时。此时最危险的处理不是报错，而是立即重试：第一次请求可能已经成功，只是确认响应没有回来，第二次请求会制造重复发布。连接器要解决的核心问题，因此不只是完成授权和接口适配，而是准确表达外部动作的能力边界、执行状态和不确定性。

## OAuth 成功不等于连接器完成

OAuth 解决的是“某个账号授权了哪些范围”，但一次可靠调用还要回答更多问题：当前账号是否真的具备目标能力，授权是否过期，接口是否限流，这个动作是否产生外部副作用，超时后能否查询，以及重复请求会不会生成第二个对象。

业务层不应直接处理不同平台的签名、字段和限流规则。更稳妥的做法，是由 Connector，也就是连接器，接收统一的调用信封：

```text
operation: content.publish
installation_ref: 连接实例引用
capability_snapshot_ref: 能力快照引用
input_ref: 不可变内容版本
idempotency_key: 业务幂等键
deadline_at: 截止时间
```

这个信封不保存真实令牌，只描述本次动作使用哪个连接实例、哪份能力快照、哪个输入版本和哪一个业务意图。

## 为什么要保存能力快照

同一平台的不同账号、地区和授权范围，能力可能不同；同一账号的能力也会随授权变更、接口升级或平台策略调整而变化。调用如果只绑定“平台类型”，审批时看到的能力边界就可能和执行时不同。

能力快照应该由服务端获取并带版本或哈希，至少记录可用操作、授权范围、读取时间和失效条件。批准与执行之间一旦快照变化，高影响动作就应重新评估，而不是继续沿用旧批准。

快照不是为了复制平台文档，而是为了回答一个审计问题：这次动作执行时，系统依据的能力边界究竟是哪一版。

## 超时之后只有三种确定结果和一种未知态

连接器不要只返回成功或失败。更实用的状态机是：

```text
accepted → pending → confirmed
                   → rejected
                   → unknown
```

confirmed 表示已经拿到可核验的外部成功证据；rejected 表示平台明确拒绝且没有产生目标动作；unknown 表示请求可能已经到达外部系统，但当前证据不足以判断结果。

进入 unknown 后，处理顺序应是：先用平台请求标识、业务幂等键或外部对象标识查询；如果能确认动作已存在，就补登记回执；如果能确认动作不存在，再决定是否重试；如果平台既不能查询也不支持可靠幂等，就转人工核验。

未知不是一种失败，而是一种需要专门处置的事实状态。

## 一个合成案例：发布请求超时了怎么办

假设一个完全合成的内容平台接入场景：系统准备发布内容版本 V7，并为这次业务意图生成幂等键 K42。请求发出后连接断开，本地没有收到平台响应。

错误流程是把任务标记为 failed，重新生成幂等键 K43 后再次发布。若第一次请求已经成功，平台最终会出现两份内容，而本地审计记录只认识第二份。

正确流程是把任务标记为 unknown，并保留 V7、K42、能力快照版本和请求时间。后台先按 K42 或平台请求标识查询：

1. 查询到外部对象：转为 confirmed，保存对象标识和可核验证据。
2. 明确查询到不存在：在风险策略允许时，继续使用同一语义幂等键重试。
3. 无法查询：暂停自动动作，交给人工在平台后台核验。

这套流程牺牲了“看起来立即恢复”的速度，却避免把网络不确定性放大成真实业务事故。

## 三类常见失败

第一类是无条件自动重试。它把超时当成失败，却没有证明外部动作不存在。对发布、回复、私信、支付和改价等有副作用的操作，这种重试尤其危险。

第二类是幂等键绑定请求，而不是绑定业务意图。同一内容因为网络错误生成多个新键，平台就无法识别它们其实是同一次动作。

第三类是审批后不再检查能力。账号权限、授权范围或接口能力已经变化，任务仍凭旧快照执行，导致动作越权或在错误边界上运行。

还要警惕把平台完整错误响应、请求头或令牌写入日志。业务数据库只应保存密钥引用、授权范围、过期时间和密钥版本；敏感凭据由专门的密钥系统管理。

## Webhook 和回流数据也要进入同一治理链

外部平台通过 Webhook 回传状态时，应先校验签名、时间窗、事件标识和原始正文哈希，再解析业务字段。重复事件要幂等处理，未知账号、过期签名和不兼容结构进入隔离区，不能反复重试污染主流程。

指标回流同样不能只按名称合并。不同平台的“播放”“互动”“点击”可能使用不同时间窗口和统计口径，至少要保留原始指标标识、时间粒度、时区和更新时间。

## 一份可直接执行的连接器检查清单

准备上线一个会产生外部动作的连接器时，可以逐项核对：

1. 每个操作是否明确只读、有副作用、可逆性和审批要求。
2. 执行是否绑定服务端生成的能力快照及版本。
3. 业务数据和日志是否只保存密钥引用，不保存真实令牌。
4. 幂等键是否绑定稳定业务意图，而不是绑定某次网络请求。
5. 状态机是否区分 confirmed、rejected 和 unknown。
6. unknown 是否优先查询，无法确认时是否转人工核验。
7. Webhook 是否先验签、去重，再进入业务处理。
8. 是否记录本次动作使用的输入版本、能力版本和外部回执。
9. 账号撤销或能力变化后，排队任务能否立即停止。
10. 没有官方查询或幂等能力时，是否限制自动化等级。

连接器的成熟度，不取决于接入了多少平台，而取决于系统能否准确说明：当时具备什么能力、执行了哪个业务意图、外部是否确认，以及证据不足时为什么选择等待而不是盲目重试。
