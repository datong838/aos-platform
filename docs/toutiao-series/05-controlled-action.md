# 从AI建议到生产动作：受控Action的七道安全门

生成一份营销文案和把它发布到真实账号之间，隔着一条巨大的工程鸿沟。前者失败通常只是内容不好，后者可能造成重复触达、违规承诺、预算损失和客户投诉。

生产动作不能是一次普通工具调用。它需要一个独立的 Action 控制面。

## 第一门：服务端风险分级

只读查询、创建草稿、公开发布、营销触达、价格库存和支付退款的风险完全不同。风险等级必须由服务端根据已注册的 Action 类型计算，调用方只能声明更高风险，不能主动降级。

高风险且不可逆的动作，不应因为模型置信度高就开放自动执行。

## 第二门：精确版本批准

一个 Action Proposal 应绑定方案、任务、逻辑版本、产物 revision、连接器能力快照、目标账号和规范化载荷哈希。

批准的语义是“这个人同意在这个时间窗内，用这个账号执行这份精确内容”，而不是“同意 Agent 以后发内容”。任何素材、账号、能力、客户同意状态或载荷变化，都应让批准失效。

中高风险动作还应执行 Maker-Checker；批量动作逐项保存哈希和状态，不能用一次模糊批准覆盖无限对象。

## 第三门：持久化幂等

幂等键至少绑定租户、项目、Action 类型和请求哈希。相同键与相同请求回放原结果，相同键与不同请求返回冲突。

幂等记录必须与业务状态在同一事务提交。否则进程在“外部调用成功、幂等记录未落库”之间崩溃，恢复后仍可能重复执行。

## 第四门：执行租约与 fencing

多个 Worker 竞争时，通过 CAS 获取带 owner、epoch 和过期时间的执行租约。只有当前 epoch 能提交结果，旧 Worker 即使恢复，也不能覆盖新 Worker 的状态。

这类 fencing token 对慢请求和网络分区尤其重要，仅有一个布尔锁远远不够。

## 第五门：预算、频控与 kill switch

预算和频控应按全局、租户、账号、Action 类型、活动和客户用途多层计算，并取最严格值。执行前先 reservation，成功后结算，确定失败后释放；unknown 状态继续占用，直到对账或人工处理。

Kill switch 也要分层，并在提案、预留、真正调用三个阶段重复检查。这样即使任务已经批准并排队，事故发生后仍能阻断它。

## 第六门：外部未知态对账

网络超时不能直接变成 `failed`：

```text
调用超时
  → unknown
  → 按平台 token 或幂等键查询
  → 确认成功 / 确认不存在 / 仍未知
```

只有确认不存在才允许重试。没有查询能力的写操作进入人工队列。宁可暂时不知道，也不要用一次重复发布换取状态“看起来完整”。

## 第七门：补偿与事故模型

数据库回滚无法撤销已经发到外部世界的内容。删除、撤回、纠正或停播都应该是新的补偿 Action，拥有独立审批、状态和回执，并与原动作双向关联。

如果平台不支持撤回，就必须诚实记录不可逆和事故状态，进入人工处置；不能把本地状态改成 `compensated` 来伪造闭环。

## 自动化不是无限循环

自动化只能绑定不可变的方案、逻辑和策略版本，并明确触发条件、时间窗、输入 Schema、最大运行次数、预算、允许的 Action 类型、是否仍需人工批准、人工 owner 和 kill switch。

必须禁止任意脚本、动态下载代码、自动扩大权限、自动批准自己、从记忆文本生成新权限和无预算循环。

## 一组必须通过的故障演练

- 批准后素材 revision 改变；
- 两个 Worker 同时领取同一动作；
- 外部成功但响应超时；
- Worker 租约过期后迟到写回；
- Kill switch 在任务排队后开启；
- 同一幂等键携带不同载荷；
- 补偿动作再次失败；
- 账号授权被撤销但能力快照尚未刷新；
- 预算已经预留，动作长期处于 unknown。

受控 Action 的目标不是把所有风险变成零，而是让每个副作用都有明确授权、唯一执行、实时制动、可查状态和诚实的事故出口。
