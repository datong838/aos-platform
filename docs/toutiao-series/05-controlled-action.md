# AI建议为什么不能直接执行：生产动作的七道安全门

让 AI 生成一份方案，和让它把方案执行到真实账号、库存、价格或支付系统，是两类完全不同的问题。前者出错通常只需修改内容，后者可能造成重复发布、错误触达、预算损失或无法撤回的外部影响。可靠的 Agent 系统必须把“建议”和“生产动作”分开，中间设置独立的 Action 控制面。

Action 可以理解为会改变外部世界的受控动作。它不是普通工具调用，而是一份需要风险判断、精确授权、唯一执行和结果核验的生产请求。

## 第一、二道门：风险分级与精确批准

只读查询、创建草稿、公开发布、批量触达、调整价格和发起退款，风险不能使用同一标准。Action 类型应在服务端注册，由服务端计算风险等级；调用方可以主动提高风险等级，但不能把高风险动作声明成低风险。

审批也不能只记录一句“同意执行”。一份 Action Proposal，也就是动作提案，至少要绑定：

```text
方案与任务版本
产物版本和载荷哈希
目标账号与对象范围
连接器能力快照
审批人和有效时间窗
```

批准的准确含义应是：“同意在这个时间窗内，用这个账号，对这份精确内容执行这一次动作。”素材、账号、授权范围、对象清单或载荷发生变化，旧批准都应失效。

中高风险动作还应采用 Maker-Checker，也就是制单人与复核人分离。创建提案的人或 Agent，不能独自批准自己的高风险动作。

## 第三道门：幂等必须跨进程保存

幂等的目标，是同一个业务意图无论被请求多少次，都只产生一次外部效果。幂等键至少绑定租户、项目、Action 类型和规范化请求哈希。

处理规则应明确：相同键加相同请求，返回第一次结果；相同键加不同请求，返回冲突；不能把后一次请求当成新动作继续执行。

幂等记录还要与业务状态可靠提交。否则进程可能在“外部调用已经成功、幂等结果尚未落库”之间崩溃，恢复后再次执行，最终形成重复动作。

## 第四、五道门：执行租约、预算与紧急制动

多个 Worker 同时领取同一动作时，仅靠一个布尔锁不够。执行租约应包含 owner、epoch 和过期时间，并通过条件更新获取。只有当前 epoch 的 Worker 能提交结果；旧 Worker 即使网络恢复，也不能覆盖新执行者的状态。这类机制通常称为 fencing token，即隔离令牌。

动作执行前还要计算预算和频控。限制可以同时来自全局、账号、Action 类型、活动和对象用途，实际执行采用其中最严格的值。

对消耗预算的动作，先做 reservation，也就是预算预留；确认成功后结算，明确失败后释放。处于 unknown 的动作仍应占用预留，直到完成对账，避免不确定动作不断挤入系统。

Kill switch，即紧急停止开关，要在提案、预算预留和真正调用前重复检查。这样即使任务已经批准并排队，事故发生后仍能阻断尚未执行的动作。

## 第六、七道门：未知态与补偿动作

网络超时不能直接记为失败。外部平台可能已经完成动作，只是响应没有返回。更可靠的处理是：

```text
调用超时
  → unknown
  → 按平台标识或幂等键查询
  → confirmed / rejected / 仍然 unknown
```

只有确认外部不存在目标动作，才允许重试。平台没有查询或可靠幂等能力时，未知态进入人工核验队列。

外部副作用也不能依靠数据库回滚撤销。删除、撤回、纠正和停播都应建模成新的补偿 Action，拥有自己的审批、幂等键、状态和外部回执，并与原动作双向关联。

如果平台不支持撤回，系统应明确记录“不可逆”和事故状态，交给人工处置，不能只把本地字段改成 compensated 来伪造闭环。

## 一个合成案例：自动发布如何被七道门约束

假设一个完全合成的场景：Agent 生成了一份内容草稿，运营人员希望在某个公开账号发布。系统首先把它识别为“公开发布”，风险高于创建草稿；随后将内容版本 V12、目标账号 A、能力快照 C3 和载荷哈希 H8 绑定到动作提案。

复核人批准后，执行器为业务意图生成幂等键 K9，并预留一次发布额度。Worker W1 获得 epoch 41 的租约后调用平台，但请求超时；与此同时，W1 的租约过期，Worker W2 获得 epoch 42。

此时系统不能让 W2 直接重新发布，也不能接受 W1 的迟到写回。正确处理是：

1. 将动作标记为 unknown，并继续占用预算预留。
2. 拒绝 epoch 41 的迟到结果覆盖当前状态。
3. 由 W2 使用 K9 或平台请求标识查询外部状态。
4. 查询到已发布后转为 confirmed，登记外部对象和回执。
5. 如果内容需要撤回，创建新的补偿 Action，而不是修改原动作结果。

这个案例说明，七道门并非七个孤立开关，而是一条围绕同一动作身份和证据链运行的控制流程。

## 三类容易被忽略的失败

第一类是“模型置信度很高，所以自动执行”。置信度衡量的是模型对输出的判断，不等于业务授权、风险可接受或外部动作可逆。

第二类是“一次批准覆盖后续修改”。内容或目标对象变化后，原载荷哈希已经失效，继续使用旧批准会让审批记录失去意义。

第三类是“本地状态完整，就代表外部世界一致”。如果系统把超时强行改成 failed，或把不可撤回动作标成 compensated，界面看起来整齐，真实风险却被隐藏了。

还要禁止自动化任意下载代码、扩大权限、批准自己、从记忆文本生成新权限，或者在没有预算和运行次数上限的情况下无限循环。

## 一份可直接执行的 Action 上线清单

1. 动作类型是否由服务端注册并计算风险等级。
2. 批准是否绑定账号、对象、内容版本、载荷哈希和有效时间窗。
3. 中高风险动作是否实现制单与复核分离。
4. 幂等键是否绑定稳定业务意图，并能识别同键不同请求。
5. 多 Worker 执行是否使用带 epoch 的租约和隔离令牌。
6. 预算、频控和紧急停止是否在真正调用前再次检查。
7. unknown 是否优先对账，而不是直接自动重试。
8. 补偿是否建模为独立动作，并关联原动作和新回执。
9. 是否能立即停止授权撤销、能力变化或超过预算的排队任务。
10. 是否演练重复请求、迟到写回、外部超时、补偿失败和紧急停止。

受控 Action 的目标不是承诺风险为零，而是让每个生产副作用都有明确授权、唯一身份、实时制动、可核验状态和诚实的事故出口。
