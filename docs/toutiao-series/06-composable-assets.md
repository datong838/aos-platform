# 行业能力怎么避免复制粘贴：可组合资产的版本与回滚

很多行业方案从第一个项目开始，也停在第一个项目：平台字段混入通用模型，客户阈值写进代码，增长流程直接调用某个渠道协议。第二个项目出现时，团队复制整套代码继续修改，短期交付很快，长期却无法统一升级、审计和回滚。解决这个问题的关键不是多建目录，而是把行业能力变成有所有权、版本和安装契约的可组合资产。

## 先用四层边界阻止依赖倒置

一套可组合方案可以拆成四层：

1. 领域核心包：商品、订单、履约等稳定语义，以及通用指标和数据质量规则。
2. 解决方案包：增长、运营、风控等业务能力，包含 Agent、工作流、策略、界面声明和评测。
3. 平台适配包：特定平台的协议、字段映射、能力矩阵和数据管道。
4. 实例 Overlay：某个部署实例的目标、数据引用、密钥引用、调度、阈值和审批配置。

这四层最重要的不是名称，而是依赖方向。领域核心不能依赖具体平台；平台适配不能夹带经营策略；解决方案不能写入实例配置；实例只能引用精确包版本，不能复制公共包后私自修改。

只要依赖方向被破坏，所谓模块化最终仍会退化成多份难以合并的项目代码。

## Manifest 要描述“能否安装”，不只是“这是什么”

每个资产都需要 Manifest，也就是机器可读的资产清单。它至少应声明不可变版本、内容哈希、依赖与冲突、能力供需、权限要求、迁移计划、界面或接口贡献，以及验证证据。

发布后的同一版本不能修改内容。发现问题时只能发布新版本，或撤销旧版本，不能让同一个版本号在不同时间代表不同物料。

“验证通过”也不能由上传方提交一个布尔值。平台应根据结构校验、签名、物料清单、评测和安全证据计算验证状态，并记录证据版本和有效期。

## 依赖解析必须产生唯一结果

依赖解析器不能只找到一个“能用的组合”。相同安装请求和相同 Registry 快照，无论数据库返回顺序或运行机器如何，都应得到相同结果。

典型规则包括：

• required 依赖全部参与，optional 依赖只在顶层明确选择时加入。
• 多个版本范围对候选逐项求交集，优先稳定版本并采用固定排序。
• 对完整依赖图检查循环、显式冲突、多个能力提供者和贡献位冲突。
• 为节点、边、深度、回溯状态和载荷大小设置确定性的步数预算。

仅依赖运行超时会破坏确定性：同一请求在快机器上可能解析成功，在慢机器上可能提前失败。时间保护可以保留，但决定结果的主要边界应是可复现的 step budget。

## Canonical Lock 冻结审批看到的内容

解析完成后，需要生成 Canonical Lock，也就是规范化版本锁。它不只保存包名和版本，还应冻结：

```text
规范化安装请求
Registry 快照哈希
每个资产的内容哈希与签名指纹
依赖边和能力提供者
权限、迁移与界面贡献差异
当前安装基线引用
```

随后对规范化 JSON 计算 lock hash。时间戳、数据库自增标识和 lock hash 自身不进入哈希载荷；空数组、空对象和 null 的表达也必须统一。

审批人批准的是精确 lock 及其差异，而不是一句模糊的“允许安装某方案”。资产内容、权限需求或迁移计划变化后，旧批准不能继续使用。

## 一个合成案例：同一方案安装到两个实例

假设一个完全合成的行业方案 S1，依赖领域核心 D2 和平台适配 P3。实例甲需要阈值配置 Oa，实例乙需要不同的阈值 Ob。

正确做法不是复制 S1 两次，而是让两个实例都引用同一组公共资产版本，只在各自 Overlay 中保存配置引用。解析器基于同一 Registry 快照分别生成 lock：

```text
实例甲：D2 + S1 + P3 + Oa
实例乙：D2 + S1 + P3 + Ob
```

如果平台适配 P3 后续被撤销，两个实例的旧审计记录仍然保留，但新的安装和激活必须停止。替换为 P4 时，每个实例都生成新 revision，重新展示权限和迁移差异并完成审批。

这样既能共享公共能力，也不会让实例配置污染公共包。

## 安装历史为什么不能覆盖更新

安装流程可以采用以下状态：

```text
draft → submitted → approved → applied → active → rolled_back
                  └→ rejected
```

每次成功变更都插入一个完整的新 revision，旧历史永不覆盖。current 指针指向最新修订，active 指针指向当前生效版本，previous active 为回滚保留基线。

并发修改使用强 ETag 和条件更新。真正 apply 前还要重新检查：依赖版本是否仍可发布，验证证据是否过期，信任根是否仍接受签名。旧 lock 可以用于审计，但不能穿越资产撤销或信任失效继续激活。

回滚也不是删除新记录或把当前行改回旧值。系统应创建一个新的回滚 revision，将 active 指针恢复到 previous active；如果没有上一版本，则回到未安装基线。原安装、审批、失败证据和事件全部保留。

## 三类常见失败

第一类是可选依赖自动加入。解析结果会被仓库新增资产悄悄改变，同一请求不再稳定复现。

第二类是只锁版本号、不锁内容哈希。仓库中的同名版本被替换后，审批记录与实际安装物料失去对应关系。

第三类是回滚覆盖历史。事故发生后只能看到“当前已经恢复”，却无法回答曾经装过什么、谁批准、何时生效以及为什么回退。

还要警惕只做局部依赖检查。单个包的直接依赖都合法，不代表完整图中不存在循环、能力冲突或权限叠加风险。

## 一份可执行的资产平台检查清单

1. 四层资产是否有明确所有权和单向依赖规则。
2. 发布版本是否不可变，并同时保存内容哈希和签名指纹。
3. 验证状态是否由平台根据证据计算，而非客户端自报。
4. 相同请求和 Registry 快照是否始终产生同一 lock hash。
5. 解析器是否检查完整依赖图，并设置确定性的资源预算。
6. 审批是否绑定精确 lock、权限差异和迁移差异。
7. apply 前是否重新检查撤销、证据有效期和信任根。
8. 每次安装、升级和回滚是否创建不可变 revision。
9. 并发变更是否使用强 ETag 和条件更新。
10. 是否测试候选乱序、循环依赖、版本交集为空、并发安装和回滚基线。

可组合交付的本质，是把“装了什么、为什么能装、谁批准、产生什么差异、出了问题怎样恢复”变成一组确定、可验证且不会被事后改写的事实。
