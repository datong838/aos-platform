# 企业Agent为何不能只靠提示词：身份、流程与工具

很多 Agent 项目从一个对话框开始：写系统提示词，接入模型，再配置几个函数。它能快速验证模型是否理解问题，却很难直接进入企业流程。真正上线后，系统必须回答它读取了什么数据、经过哪些步骤、为什么请求某个工具、谁批准了写操作，以及失败后怎样定位和恢复。这些问题不能继续藏在提示词里。

更稳妥的做法，是把 Agent 拆成三层运行契约：Agent Definition 定义“谁在工作”，Logic Pipeline 定义“按什么步骤工作”，Tool Registry 定义“可以请求哪些能力”。

## 第一层：身份契约决定谁能看什么

Agent Definition 不是人格介绍，而是一份可校验的运行契约。它至少包含角色目的、允许读取的对象类型、模型策略、工具策略和写操作安全等级。

```text
角色：订单异常协调员
目标：分析异常并形成处理草案
上下文：订单摘要、履约事件、服务工单
允许工具：读取摘要、创建处理提案
写入模式：必须审批
禁止范围：支付凭据、无关对象数据
```

这里有三个关键原则。

第一，上下文使用白名单。Agent 接收的是经过身份、用途和字段裁剪的业务对象，不是数据库连接和底层表结构。

第二，模型选择是一条策略。分类、摘要和复杂推理可以根据质量、延迟与成本走不同路由，但每次运行都要记录实际模型和版本。

第三，安全等级描述“允许做到哪一步”。只读分析、生成草稿、需人工确认的写操作和有限自动执行，不能共享一套模糊权限。

## 第二层：流程契约把步骤从提示词中拿出来

只用自然语言提示控制流程，模型可能遗漏步骤，流程修改也难以做版本比较。Logic Pipeline 的作用，是把业务过程拆成有类型、有输入输出的节点。

```text
输入事件
  → 读取授权属性
  → 确定性数据变换
  → 模型生成结构化判断
  → 条件分支
      ├─ 信息不足：请求补充
      ├─ 低风险：创建草稿
      └─ 高风险：转人工处理
```

流程层需要守住四个不变式：每个节点都有输入输出 Schema；分支条件可复现；每次运行绑定精确 Pipeline revision；下游只能消费已完成节点的结构化输出。

模型节点也不应只返回一段自由文本。平台可以要求结构化结果，再检查字段、枚举、长度和引用版本。校验失败进入受限重试或人工处理，不能把错误结果继续传给下游工具。

## 第三层：工具注册表隔离推理与执行

Tool Registry 位于模型推理和真实执行之间。每个工具除了名称和参数，还要声明：

• 输入输出 Schema。
• 只读还是存在外部副作用。
• 所需角色、数据范围和业务用途。
• 是否支持幂等、状态查询和补偿。
• 超时、并发、频率与预算限制。
• 是否必须先创建动作提案并人工批准。

模型提交工具调用，语义只能是“提出请求”，不是“获得平台管理员权限”。执行时，平台仍要使用当前用户或服务身份重新校验权限，并读取不可变输入引用。

写操作至少绑定目标对象、载荷哈希、Agent revision、Pipeline revision 和批准记录。网络重试继续使用同一幂等键，避免一次超时变成两次生产动作。

## 一个合成案例：订单异常如何跨三层运行

下面使用一个完全合成、与任何真实项目无关的场景。某个订单出现履约延迟，同时用户反馈商品说明不清楚。

身份层首先限制异常协调 Agent 只能读取订单摘要、履约事件和服务工单，不能读取支付凭据或无关对象。流程层随后执行：

1. 获取带版本的订单和履约摘要。
2. 用确定性规则检查信息是否完整。
3. 让模型输出结构化的原因分类和置信边界。
4. 分成履约核查、内容检查和回复草稿三个分支。
5. 通过 Handoff 节点合并最小必要字段。
6. 为内容修改和用户触达分别创建动作提案。

工具层只开放只读状态查询和创建提案。负责人批准精确内容版本后，执行器才请求外部动作，并记录幂等键和回执。

这条链路里，多 Agent 的价值不是让多个角色同时聊天，而是每个角色拥有独立上下文、工具和验收标准，跨角色协作依赖结构化交接。

## 三类常见失败

第一类是把权限写进提示词。例如告诉模型“不要读取敏感字段”，却仍向它提供完整数据库工具。自然语言约束不能替代服务端裁剪和执行时鉴权。

第二类是把流程全部交给模型自由规划。模型可能跳过校验、改变步骤顺序，团队也无法稳定比较两个流程版本的行为差异。

第三类是把工具调用等同于工具执行。模型一旦生成函数参数，系统就直接产生外部副作用，审批、幂等、频控和补偿都失去插入位置。

还要避免只记录最终答案。没有事件、节点、模型、工具请求、审批和回执的 Trace，出现偏差时就无法区分数据过期、规则错误、模型不稳定还是工具失败。

## 发布门禁和落地顺序

发布前的 Evals 至少要覆盖：正常输入是否符合 Schema，缺字段和冲突数据如何处理，越界字段读取是否被拒绝，未注册工具是否明确失败，高风险分支是否稳定转人工，以及更换模型或提示词后事实性与安全性是否退化。

运行时 Trace 不需要记录模型隐藏推理过程，但应记录输入引用、输出摘要、Agent 和 Pipeline 版本、实际模型、延迟、Token、工具状态和审批结果。

实施时可以按以下顺序逐级推进：

1. 先开放只读查询、结构化输出和运行追踪。
2. 再让 Agent 创建草稿和动作提案。
3. 接入人工批准后的低风险写操作。
4. 用真实运行结果扩充 Evals 和失败样本。
5. 最后才评估小范围、可撤回、有预算的自动执行。

每升一级都要定义通过标准、回退条件和人工接管路径。对不可逆或影响权益的动作，长期保留人工决策可能比追求全自动更合理。

企业 Agent 的核心不是再包装一个聊天窗口，而是把模型放进清晰的工程秩序：身份有边界、流程有版本、工具有权限、发布有评测、运行有追踪、写操作有责任人。当每次运行都能回答“基于什么、经过什么、允许什么、由谁确认”，Agent 才从演示能力变成可治理的业务能力。
