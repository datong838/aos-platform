# 电商多智能体为何越做越乱：用经营闭环替代角色堆叠

内容 Agent、客服 Agent、导购 Agent、数据 Agent，各自接上模型后都能对话，架构图看起来很完整。进入真实经营流程后，问题却会迅速出现：谁决定今天做什么，谁控制预算与风险，一个角色的产物怎样交给下一个角色，任务完成后又如何证明经营结果真的改善。Agent 数量越多，如果缺少统一闭环，协作反而越混乱。

电商多智能体的核心不是角色清单，而是一条连接目标、证据、审批、任务、执行、结果和复盘的经营循环。

## 先建立最小经营循环

一条可落地的最小循环可以表示为：

```text
经营目标与护栏
  → 数据就绪检查
  → 内外部机会研究
  → 形成方案草案
  → 人工批准精确版本
  → 拆解任务 DAG
  → 多角色执行与交接
  → 观察结果并归因
  → 复盘和经验候选
```

数据参谋可以承担总控角色：观察全局、提出方案、拆分任务、跟踪执行和组织复盘。内容、导购、客服、客户运营和活动策划承担专业任务。人类经营负责人仍然拥有目标、预算、风险边界和最终批准权。

这不是把组织岗位机械搬进软件，而是让每个决策和交付物都有清晰责任、版本与验收条件。

## 目标必须是一棵带护栏的指标树

如果所有角色只追求成交额，局部最优很容易伤害整体经营。内容角色可能追求曝光，导购角色追求转化，活动角色追求短期成交，却同时推高优惠成本、退款率和投诉风险。

一棵基本指标树至少同时覆盖：

• 获客：有效互动、线索质量和获客成本。
• 成交：咨询转化、推荐接受、客单和成交周期。
• 客户：复购、流失、退订和长期价值。
• 体验：响应、解决、退款、投诉和履约。
• 经营质量：毛利、库存、优惠成本和渠道投入产出。
• 合规：内容风险、越界承诺、隐私和高风险动作拦截。

每个目标都要带停止条件。例如库存低于安全线就降低获客节奏，退款率越界就暂停扩大投放，外部证据过期就禁止继续据此触达。护栏不是事后报表，而是方案和执行前检查的一部分。

## 用任务 DAG 替代 Agent 自由聊天

自由对话很难稳定表达依赖、验收和失败。任务 DAG 是有向无环任务图，它把批准后的方案拆成可以追踪的工作单元。

每个任务至少包含负责人、输入引用、前置依赖、允许的数据域和工具、预算、风险等级、交付物、验收指标、观察窗口和停止条件。

```text
机会研究
  → 内容草稿与合规审核
  → 人工确认发布
  → 线索识别
  → 需求诊断与商品建议
  → 服务反馈
  → 效果归因
```

后置任务只能消费已交付且通过验收的前置产物。数据缺失、权限不足或连接器不可用时，任务应进入 BLOCKED，并记录原因和责任人，不能让模型生成模拟结果填补空白。

跨角色交接也只传递最小必要字段，例如内容版本、线索信号、推荐草案或服务案例引用，而不是共享整段对话和全部用户上下文。

## 一个合成案例：一次新品任务怎样形成闭环

假设一个完全合成的场景：团队准备评估某类新品是否值得小范围测试。数据参谋首先检查商品、库存、履约和历史反馈的数据版本，发现库存只能支持有限流量，于是把“库存安全线”和“退款率上限”写入方案护栏。

经营负责人批准方案版本 P4 后，系统生成任务图：

1. 内容角色基于已批准卖点生成两份草稿，不得添加未经证实的承诺。
2. 合规检查通过后，由人类选择并发布其中一个版本。
3. 导购角色只对满足条件的咨询生成需求诊断和商品建议草案。
4. 客服角色记录履约、退货和描述一致性问题。
5. 数据参谋在观察窗口结束后，对比测试组与基线组，并检查库存、毛利和投诉护栏。

如果曝光增加但推荐接受率没有变化，且样本不足，复盘结论应是“证据不足”，而不是宣布内容有效。如果退款率触发上限，系统暂停后续任务并把投诉原因反向交给内容与导购角色修订表达。

这个闭环的价值，不是五个 Agent 同时工作，而是目标、交付、审批、停止和学习使用同一条证据链。

## 三类常见失败

第一类是角色先行、目标缺席。团队先设计十个 Agent，再寻找它们能做什么，最终每个角色都有输出，却没有共同经营结果。

第二类是把“任务完成”当成“业务有效”。内容已发布、消息已触达只能证明执行发生，不能证明成交、毛利或体验改善。

第三类是复盘没有对照。价格、库存、节日和平台流量同时变化时，把自然波动全部归功于 Agent，会生成错误经验。

还要避免把一次成功直接写入长期记忆。单次结果只能形成带证据、适用范围和反例的经验候选，经过多次验证和治理后才可能晋升为稳定规则。

## 一份可执行的首版验收清单

1. 方案是否基于有版本的内部数据和可追溯外部证据。
2. 目标是否同时包含增长、成本、体验与合规护栏。
3. 人工批准是否绑定不可变方案版本和适用时间窗。
4. 是否向至少三个专业角色分派有依赖的任务。
5. 每个任务是否有输入引用、交付物、验收和停止条件。
6. 跨角色交接是否只传递最小必要字段。
7. 数据或工具不可用时是否进入 BLOCKED，而不是伪造结果。
8. 执行后是否区分有效、无效、有害、证据不足和未实际执行。
9. 归因是否记录对照方法和价格、库存等干扰因素。
10. 复盘是否只生成经验候选，未经治理不进入长期记忆。

电商多智能体系统的价值，不是让更多角色同时说话，而是把经营判断、人工责任、专业协作和效果验证连成一条不会断的链。
