# 多Agent如何安全共享上下文：同意状态机与用途绑定

多 Agent 系统常见的错误设计，是把“已经登录”或“曾经授权”简化成一个布尔值，然后让所有角色共享同一份用户上下文。这样做虽然方便，却无法回答三个关键问题：授权适用于哪个用途、允许在哪个渠道使用，以及授权发生变化后正在运行的任务该怎样停止。

可靠实现需要把授权判断从提示词中移出，交给确定性的策略层：

```text
任务请求
  -> 身份与角色校验
  -> 用途绑定
  -> 同意状态解析
  -> 字段级最小化
  -> 频率与静默期检查
  -> 允许、拒绝或转人工
```

模型可以解释为什么需要某些信息，却不能自行扩大用途、补全缺失授权或降低策略等级。

## 同意状态不是一个布尔值

`consent=true` 无法支撑真实协作。同一个主体可能允许服务通知，不允许推荐信息；可能允许站内渠道，不允许其他渠道；也可能在任务创建后撤回授权。

一个可执行的同意状态至少需要这些维度：

```yaml
subject_ref: "受保护主体引用"
purpose: "明确的数据用途"
channel: "允许使用的渠道"
scope:
  - "允许读取的字段范围"
status: "active | withdrawn | unknown"
effective_at: "生效时间"
expires_at: "失效时间"
policy_version: "策略版本"
```

这里使用的是不可直接识别个人的主体引用。真实身份数据由专门的数据域管理，普通 Agent 只能获得完成当前任务所需的字段。

`unknown` 也必须是一等状态。无法确认授权时，系统应失败关闭或转人工，而不是把未知解释成允许。

## 用途绑定阻止上下文被二次利用

某个 Agent 为解决服务问题获得了一段上下文，不代表另一个 Agent 可以把它用于内容生成或商品建议。每次交接都要绑定当前任务用途，并检查下游角色是否仍需要这些字段。

```yaml
handoff_id: "交接引用"
from_role: "分析角色"
to_role: "服务角色"
purpose: "解释当前问题"
allowed_fields:
  - "状态摘要"
  - "相关事实引用"
forbidden_fields:
  - "原始身份"
  - "无关历史"
  - "完整会话"
expires_at: "任务截止时间"
```

下游产物也要继承用途和敏感标记。如果服务角色生成了一份问题摘要，这份摘要不能因为已经“脱离原始数据”就自动变成公共知识。

## 策略需要在两个时点重复校验

只在任务创建时检查授权是不够的。一个任务可能排队数分钟，也可能等待上游依赖更长时间；在此期间，同意状态、角色权限和策略版本都可能变化。

因此至少需要两次校验：

1. **创建时校验**：决定任务是否可以进入队列，以及允许装配哪些字段；
2. **执行前校验**：重新读取当前策略快照，确认授权、用途和字段范围仍然有效。

两次结果不一致时，执行前结果优先。系统应撤销临时上下文、把任务标记为阻断，并记录策略变化，而不是沿用创建时的旧结论。

对于持续时间较长的任务，还可以使用短期授权租约。租约到期后必须续验，不能由 Agent 自行延长。

## 频控是跨任务的确定性约束

频率限制不能只写在单个 Agent 的提示词里。多个任务可能在不同队列中同时选择同一主体，每个 Agent 都认为自己只执行一次，合起来却可能超过限制。

频控服务需要使用全局可见的计数和原子预留：

```text
请求执行
  -> 读取用途、渠道与时间窗
  -> 原子预留一次额度
  -> 执行动作
  -> 成功后确认占用
  -> 失败后按规则释放或保留
```

如果外部渠道超时，系统不能立即释放额度并重试。请求可能已经生效，此时应进入“结果未知”状态，先核对外部事实，再决定是否恢复。

## 多 Agent 协作依赖职责分离

安全协作不要求所有角色看到同样的信息。分析角色可以基于聚合数据发现任务条件；关系运营角色负责判断用途、渠道和节奏；内容角色只获得受众约束与事实包；服务角色只读取处理当前问题所需的状态。

```text
分析角色：输出匿名化条件
  -> 策略层：解析用途和同意状态
  -> 关系运营角色：创建受控任务草案
  -> 内容角色：生成不含身份信息的内容版本
  -> 人工批准或受控执行
  -> 服务角色：返回脱敏结果摘要
  -> 分析角色：只读取聚合效果
```

角色职责分离能够阻止两类越权：模型为了完成目标主动索取更多字段，以及上游把“可能有用”的全部信息推给下游。

## 撤回授权必须能够终止在途任务

同意状态变化不能只影响未来任务。策略层还需要定位尚未完成的任务、临时上下文和待执行动作，并根据风险执行取消、清理或人工接管。

系统至少应覆盖以下测试：

- 任务排队期间授权被撤回；
- 多个角色同时申请同一用途的上下文；
- 策略版本更新导致字段范围收紧；
- 频控额度预留后执行结果未知；
- 下游试图把服务用途的数据转交给内容用途；
- 临时上下文到期后仍有任务尝试读取。

这些失败路径需要在策略和存储层实现，不能只依赖模型“记得遵守”。

## 最小上下文是一种系统能力

多 Agent 协作不是共享越多越好。真正可扩展的方案，是让每个角色只获得完成当前任务必需的、用途明确的、会自动失效的上下文，并让授权状态在任务生命周期内持续生效。

同意状态机回答“现在是否允许”，用途绑定回答“允许拿来做什么”，频控回答“即使允许也能做多少次”。三者共同构成跨 Agent 数据交接的确定性边界。
