# 六个Agent为何不能共享全部上下文：同意、用途与频控

多 Agent 系统最省事的设计，是让所有角色共享同一份用户上下文：分析角色发现机会，内容角色读取历史，导购角色生成建议，服务角色继续处理。但“已经登录”或“曾经授权”并不等于所有角色、所有用途和所有渠道都能使用全部信息。上下文共享越宽，越难回答授权用于什么、字段为何必要，以及授权撤回后怎样停止在途任务。

可靠做法是把授权判断移出提示词，交给确定性策略层，让每次交接都经过身份、用途、同意状态、字段最小化和频率检查。

## 同意状态不能只是 true 或 false

同一个主体可能允许服务通知，却不允许推荐信息；允许站内渠道，却不允许其他渠道；也可能在任务创建后撤回授权。

可执行的同意状态至少包含：

```text
主体引用：不可直接识别个人的受保护引用
用途：本次数据为什么被使用
渠道：允许在哪个渠道使用
范围：允许读取哪些字段
状态：active / withdrawn / unknown
生效与失效时间
策略版本
```

真实身份数据应由专门数据域管理，普通 Agent 只获得当前任务所需字段。unknown 必须是一等状态：无法确认授权时，系统拒绝执行或转人工，不能把未知解释成允许。

## 用途绑定阻止上下文被二次利用

服务角色为解决问题获得一段上下文，不代表内容或导购角色可以把它用于营销与推荐。每次 Handoff，也就是角色交接，都要绑定当前任务用途、允许字段、禁止字段和失效时间。

```text
来源角色：分析角色
目标角色：服务角色
用途：解释当前服务问题
允许：状态摘要、相关事实引用
禁止：原始身份、无关历史、完整会话
失效：任务截止时间
```

下游产物仍要继承用途和敏感标记。一份由敏感数据生成的摘要，不会因为脱离原始记录就自动变成公共知识。

策略层还应执行字段必要性检查：下游角色如果不需要某个字段完成任务，就不应仅因为“以后可能有用”而获取它。

## 创建任务和真正执行前都要检查

只在任务创建时检查授权不够。任务可能排队，也可能等待上游依赖；这段时间内，同意状态、角色权限和策略版本都可能改变。

至少要进行两次校验：

1. 创建时校验：决定任务能否进入队列，以及允许装配哪些字段。
2. 执行前校验：重新读取当前策略快照，确认授权、用途和字段范围仍有效。

两次结果不一致时，以执行前结果为准。系统撤销临时上下文，把任务标记为 BLOCKED，并记录策略变化，不能沿用创建时的旧结论。

持续时间较长的任务可以使用短期授权租约。租约到期必须重新验证，不能由 Agent 自行延长。

## 频控必须跨角色统一计算

频率限制不能只写在单个 Agent 的提示词里。多个任务可能在不同队列中同时选择同一主体，每个角色都认为自己只执行一次，合起来却超过限制。

频控服务需要全局可见的计数和原子预留：

```text
请求执行
  → 读取用途、渠道和时间窗
  → 原子预留一次额度
  → 执行动作
  → 成功后确认占用
  → 明确失败后按规则释放
  → 结果未知时继续保留
```

外部渠道超时后不能立即释放额度并重试。请求可能已经生效，应先进入 unknown 并核对外部事实，避免一次不确定触达变成两次真实触达。

## 一个合成案例：复购任务如何安全接力

假设一个完全合成的场景：分析角色在聚合数据中发现某类商品可能进入补充周期。它只能输出匿名化条件，不能直接获得或下发个人联系方式。

策略层针对“复购提醒”用途检查当前同意状态、允许渠道和静默期，生成一条带失效时间的任务草案。关系运营角色只能看到满足条件的主体引用与节奏约束；内容角色只收到受众约束和已核验商品事实，不接触身份数据；导购角色只有在主体主动咨询后，才获得当前咨询所需的商品与偏好字段。

任务排队期间，如果授权被撤回，执行前校验会拒绝继续装配上下文，释放尚未使用的额度并取消待执行动作。服务角色处理后只返回脱敏结果标签，分析角色只能读取聚合效果。

这条链路允许六个角色协作，但没有任何角色因为“参与同一任务”就自动获得全部用户上下文。

## 三类常见失败

第一类是把一次授权扩大到所有用途。服务用途的数据被用于内容生成或商品推荐，授权语义被悄悄改变。

第二类是只在任务创建时校验。授权已经撤回，排队任务仍携带旧上下文继续执行。

第三类是每个 Agent 各自频控。单个角色都没有超限，多个队列合计却造成过度触达。

还要避免把完整会话当成默认交接对象。它既增加隐私暴露，也会让下游模型受到无关历史影响，模糊当前任务的用途边界。

## 一份可执行的安全交接清单

1. 同意状态是否包含用途、渠道、字段范围和有效时间。
2. unknown 是否默认拒绝或转人工，而不是视为允许。
3. 每次交接是否绑定来源、目标、用途和失效时间。
4. 下游是否只获得完成任务必需的最小字段。
5. 派生摘要是否继承原数据的用途和敏感标记。
6. 创建任务和执行前是否重复校验当前策略。
7. 长任务是否使用可到期、需续验的授权租约。
8. 频控是否在跨角色、跨队列的统一服务中原子预留。
9. 授权撤回后能否取消任务、清理上下文和阻断待执行动作。
10. 是否测试策略收紧、并发申请、结果未知和上下文过期。

多 Agent 协作不是共享越多越好。真正可扩展的设计，是让每个角色只获得用途明确、完成当前任务必需、会自动失效的上下文。同意状态回答“现在是否允许”，用途绑定回答“允许拿来做什么”，频控回答“即使允许也能做多少次”。
