# Agent什么时候可以自动执行：动作控制面的五级护栏

当多个 Agent 都能发布内容、发送消息或修改业务数据时，风险不能只靠各自的提示词约束。单个任务看似合理，多个并发任务仍可能造成重复发送、预算叠加和状态冲突。更稳妥的做法，是把所有外部写操作统一送入动作控制面，先分级、审批和预留，再执行、核对与补偿。

## 先按后果分级，不按按钮名称分级

同样是调用一个工具，读取数据与修改价格的后果完全不同。可以先建立五级动作模型：

R0：查询公开或已授权数据，只读并留痕

R1：生成分析、文案或建议，只能保存为草稿

R2：创建待审核任务、保存受控草稿，范围明确且可撤销

R3：发布内容、发送消息、修改普通配置，需要精确审批与限量执行

R4：改价、库存、支付、退款等高影响动作，需要双人复核或更严格控制

风险级别不能由调用者自行填写，而应由服务端根据动作类型、影响范围、金额、受众数量和可逆性计算。否则 Agent 只要把批量触达标成“低风险”，就可能绕过真正的控制。

## 人审批的是精确版本，不是一句“同意”

“同意这个方案”不足以授权真实执行。审批人看到的对象，必须与最终执行对象完全一致。

一份动作提案至少绑定：

• 对应的计划和任务
• 内容、价格或配置的精确版本
• 目标渠道、账户和受众范围
• 允许调用的能力及其边界
• 预算、频率和有效时间窗
• 标准化参数摘要与校验值

审批后只要文案中的关键数字改变、受众从小范围扩大为全量，或者价格参数发生变化，原审批就应失效并重新提交。这叫批准动作版本，而不是批准 Agent 自由发挥。

受控动作可以经过七个状态：

建议 → 草稿 → 动作提案 → 精确审批 → 受控执行 → 结果核对 → 效果复盘

每次变化都记录操作者、输入版本、时间和原因，才能判断问题究竟出在分析、草稿、审批、执行还是外部系统。

## 超时之后最危险的动作是立即重试

设想一个完全虚构的客服场景：系统提交一次权益补偿，连接在返回结果前超时。没有收到成功响应，并不代表动作没有发生。第一次请求可能已经完成，盲目重试会造成重复补偿。

任何有副作用的动作都应使用持久化幂等键：

同一幂等键 + 同一请求 → 返回第一次结果

同一幂等键 + 不同请求 → 拒绝并报告冲突

当结果无法确定时，状态应进入“待核对”，先查询外部事实或执行对账，再决定是否重试。对于并发执行，还要使用租约或栅栏，确保同一任务不会被两个执行者同时领取。

## 自动化必须自带四类刹车

第一类是范围护栏，限定账户、渠道、客群、品类和时间窗。Agent 只能在被授权的最小范围内行动。

第二类是预算与频率护栏，限制金额、优惠成本、触达次数和单位时间内的动作数量。单次合法不代表累计影响也安全。

第三类是异常暂停。当投诉、退订、退款、库存或价格波动触发阈值时，系统暂停后续动作并请求人工判断，而不是坚持完成原计划。

第四类是全局停止开关。当外部平台异常、权限配置错误或效果明显偏离预期时，负责人能够停止某类能力、某个账户或全部执行任务。停止开关本身也要有权限控制，并通过演练证明可用。

## 改价比发布内容多了哪些风险

错误内容通常可以删除或更正，价格变化却可能立即引发订单、承诺与合规问题。改价提案不仅要检查目标价格，还要检查毛利下限、活动叠加、渠道一致性、库存状态和生效时段。

更稳妥的流程是：

1. 在模拟环境计算影响
2. 由审批人确认精确参数和适用范围
3. 先以小范围、短时间窗执行
4. 读取外部系统的真实价格进行核对
5. 若只完成部分渠道，冻结扩展并生成差异清单
6. 按预先批准的方案决定回滚、补齐或保持现状

补偿方案必须在执行前进入提案，而不是出问题后临时想办法。“请求已发送”也不能等同于“价格已生效”。

## 三类常见失败与四级成熟度

第一类失败是把模型置信度当授权。即使 Agent 对建议非常有把握，也不能因此访问新账户、扩大受众或突破预算。能力来自系统授权，不来自模型自信。

第二类失败是审批后允许参数继续变化。这样人看到的是一个版本，机器执行的是另一个版本，审批只剩形式。必须用版本号和参数校验值锁定对象。

第三类失败是把超时当失败、把成功响应当最终事实。前者会导致重复执行，后者会忽略外部系统的部分成功。最终结论应来自结果查询和对账。

自动化可以分四个阶段演进：

• 仅建议：Agent 只分析和生成草稿，外部操作全部由人完成
• 辅助执行：人批准精确版本，系统代为执行并核对
• 监督式自动化：低风险重复动作在额度内自动执行，异常立即升级
• 有限自治：只在长期验证、边界明确和持续监控的场景扩大权限

成熟度不是自动执行比例越高越好，而是错误影响能否被限制、异常能否及时发现、审批是否有效、动作能否解释和复盘。

## 上线动作控制面的检查清单

• 风险等级是否由服务端按后果计算
• 审批是否绑定精确版本、范围、预算和有效期
• 参数变化后是否强制原审批失效
• 所有副作用动作是否使用持久化幂等键
• 超时或部分成功是否进入待核对状态
• 并发执行是否使用租约或栅栏
• 是否具备范围、预算、异常暂停和全局停止四类护栏
• 高影响动作是否要求职责分离或双人复核
• 执行后是否读取外部事实，而不只相信请求响应
• 补偿、回滚和差异处理是否在执行前设计

值得托付的 Agent，不只是能提出好建议或调用更多工具。它还必须知道哪些动作只能生成草稿，哪些必须等待精确审批，结果未知时什么时候停止重试，以及如何把决定交还给人。
