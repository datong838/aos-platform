# 企业AI为什么要分四层：数据、本体、决策与工作台

企业 AI 项目最危险的捷径，不是模型选得不够强，而是工作台直接拼查询、Agent 直接读取原始表、模型生成答案后直接调用外部接口。这样的系统很快能演示，却很难回答四个问题：数据来自哪里、业务含义由谁定义、动作是否被批准、出错后应该回滚哪一版。四层架构正是为这四种责任划清边界。

## 四层不是菜单，而是四种解释权

数据操作系统负责解释“事实能不能用”。它管理外部来源、同步状态、加工过程、数据版本和血缘，但不擅自决定字段在业务中代表什么。

本体数字孪生负责解释“事实代表什么”。它把数据映射成业务对象、属性和关系，并定义哪些受控动作能够改变对象状态。

AIP 决策层负责解释“建议怎样形成”。AIP 可以理解为 AI 决策运行时，它负责选择模型、装配上下文、调用工具、生成草案并记录评测，但不能给自己授予数据或动作权限。

工作台负责解释“人怎样查看与操作”。它管理页面、组件、选择集、事件和审批入口，却不能把一个按钮变成绕过动作治理的数据库写入器。

判断一项能力属于哪层，不看它出现在哪个页面，而看谁拥有最终解释权。

## 用一个合成案例看四层如何协作

设想一个完全虚构的库存异常场景：业务人员在工作台看到某类商品库存变化，希望系统给出处理建议。

第一步，数据层提供一个有来源、时间范围和质量状态的库存快照，而不是让 Agent 直接连接业务数据库。

第二步，本体层把数据映射成商品、仓库和库存事件，明确它们之间的关系，以及哪些状态允许创建调拨建议。

第三步，AIP 读取受权限约束的对象，结合已批准逻辑和工具生成建议草案，并记录所用对象版本、逻辑版本和证据。

第四步，工作台向有权限的人展示差异、证据和影响范围。人工确认后，系统才创建受控动作提案，执行后再核对外部结果。

这条链让一项建议能够追溯到界面选择、决策草案、本体对象、数据快照和批准版本。

## 读链与写链必须分开设计

读链把外部事实变成人和 Agent 可以理解的上下文：

外部来源 → 连接与同步 → 加工与数据集 → 对象与关系 → 受控查询 → AIP 推理或工作台展示

它关注来源可信、版本一致、质量状态和最小披露。

写链把人的意图或模型建议变成真实业务动作：

工作台选择或 AIP 建议 → 动作提案 → 条件与权限检查 → 草稿和人工审批 → 受控执行 → 结果核对 → 审计与补偿

它关注精确授权、幂等执行、结果核对和可补偿。若把两条链压缩成一次模型调用，数据治理和动作治理会一起消失。

## 每一层究竟保存什么状态

数据层需要保存来源版本、同步游标、新鲜度、加工输入与输出版本、失败记录，以及输出回到来源的血缘。上层读取的是一个有范围、有时间、有状态的数据快照。

本体层需要保存对象类型、关系类型、动作类型和只读业务函数。数据库知道一行有哪些列，本体则描述这行数据在业务世界中是谁、与谁有关、处于什么生命周期，以及允许做什么。

AIP 需要保存模型路由、逻辑版本、工具调用、输入对象引用、证据、输出草案和评测结果。涉及外部副作用时，它首先输出草案，而不是用自然语言声称“已经执行成功”。

工作台需要保存页面模块、组件状态、变量、选择集和用户事件。大对象集要分页，批量选择要限量，重复点击也只能产生一个有效动作。

## 跨层只共享稳定引用

四层协作不等于共享全部上下文。更安全的跨层信封只传递必要引用：

organization_ref: 组织引用
workspace_ref: 工作区引用
data_snapshot_ref: 数据快照引用
ontology_version: 本体版本
policy_version: 权限策略版本
trace_ref: 全链路追踪引用

这些引用让每一层能够重新检查权限、定位版本并回放决策。原始数据、完整提示词和界面临时状态不应无条件跨层扩散。

## 四种跨层直连必须禁止

第一，工作台不能直接写数据库。否则动作条件、权限、幂等和审计都会失效。

第二，AIP 不能绕过本体读取全部原始表。否则业务语义、字段敏感标记和对象权限无法保持一致。

第三，本体不能悄悄承担数据清洗。多源关联、结构变化处理和质量修复属于数据层，否则业务语义会与加工逻辑纠缠。

第四，数据层不能根据列名自动决定业务动作与权限。技术结构可以自动发现，业务语义和动作发布仍需治理。

常见失败还包括：四层各自保存一套不一致的权限、审批只绑定自然语言而未绑定版本、执行成功后没有回写实际结果。这些问题会让分层只剩图纸，没有形成运行时边界。

## 四层架构的落地检查清单

• 数据层是否能给出来源、时间、质量和版本状态
• 本体层是否统一表达业务对象、关系和允许动作
• AIP 是否记录模型、逻辑、工具、证据与输出草案
• 工作台是否只通过受控查询和动作提案参与业务
• 读链与写链是否分开设计并分别治理
• 跨层是否使用稳定引用，而不是复制全部上下文
• 数据与对象的敏感标记是否能够贯穿四层
• 审批是否绑定精确动作版本与影响范围
• 执行后是否核对外部真实结果并记录血缘
• 任一层失败时，系统是否能停止、定位和回滚

四层架构的价值不在“层数多”，而在四种责任共同维护同一条证据链。只有当界面上的每次操作都能追到决策草案、本体对象、数据快照、批准版本和外部结果时，企业 AI 才从会回答问题，变成能够在边界内参与业务运行的系统。
