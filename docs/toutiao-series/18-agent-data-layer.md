# Agent为什么不能直连数据库：可信数据链怎么建

让 Agent 直接连接业务数据库，看起来是最短路径，却会马上失去三个关键答案：它读取的是哪个时间点的数据，数据结构变化是否已经影响判断，以及一条结论能否回到原始来源核验。可信数据层不是给模型一个数据库账号，而是把连接、同步、加工、质量、版本和血缘组成一条可回放的资产链。

## 数据进入平台，不等于已经可信

一份数据副本只能证明“数据被搬过来”，不能证明它适合支持决策。来源可能已经断连，字段结构可能变化，同步可能只完成一部分，加工任务也可能混用了不同时间点的输入。

更完整的资产状态链应当是：

连接器已配置 → 数据结构已发现 → 同步已建立检查点 → 加工任务已完成 → 数据资产已物化 → 质量与新鲜度已评估 → 血缘可以回放

只有状态、版本、范围和来源都能被引用的输出，才有资格进入 Agent 的上下文。

## 连接器不是一次性导入脚本

连接器负责适配外部数据协议。它至少应声明配置结构、能力、版本和生命周期，而不是把访问逻辑散落在业务服务中。

connector_id: 连接器类型
version: 适配器版本
kind: 来源或目标
capabilities: 结构发现、增量同步、健康检查
config_schema: 可公开的配置结构
secret_refs: 受控密钥引用

密钥值不能进入普通配置、日志或任务消息；运行时只读取受控引用。新增来源也不应修改连接器宿主的核心代码，而应通过统一协议完成注册、发现、同步、健康检查和卸载。

上层依赖的是“发现、同步、健康检查”等稳定能力，而不是某个数据库或软件服务的私有细节。

## 数据结构变化必须先做影响分析

来源报告了一组表和字段，不代表平台可以立即把它们视为稳定契约。每次结构发现都应形成版本，并与已批准版本比较：

• 新增、删除或重命名了哪些字段
• 类型变化是否兼容
• 主键、游标和分区字段是否仍有效
• 下游加工任务和数据资产会受到什么影响
• 新字段是否需要重新确认敏感标记

设想一个完全虚构的场景：来源把原本的数值字段改成自由文本。正确做法不是继续运行并把错误留给 Agent，而是阻断受影响的构建，保留最后一版可信资产，并向上层暴露具体原因。

处理链可以概括为：发现结构 → 版本差异 → 兼容性检查 → 下游影响分析 → 自动接受、人工批准或阻断。

## 同步任务的核心是检查点和未知态

同步不能只有“成功”和“失败”。长任务可能读取完成但写入未确认，也可能部分分区成功、部分进入重试。

一次运行至少应记录连接器版本、读取范围、上次确认检查点、各阶段状态、错误分类、重试次数、输出版本和校验摘要。

run_ref: 同步运行引用
source_snapshot: 来源范围
checkpoint_before: 上次确认位置
checkpoint_after: 本次候选位置
write_status: 已提交、部分成功或未知
output_version: 产出版本

只有写入被确认后，候选检查点才能升级为正式检查点。连接超时产生的是“未知”，不是可直接重试的“失败”；系统要先对账，再决定继续、回滚或转人工。

## 数据管道是版本化程序，不是静态画布

数据管道是一段需要发布、执行和回放的数据程序。输入引用、节点配置、表达式、运行环境和输出结构都属于版本的一部分。

来源或数据资产 → 过滤、关联、表达式 → 可选解析或模型节点 → 质量检查 → 新的数据资产

画布保存成功，只代表定义已持久化；某次构建成功，才代表一个精确版本在一组精确输入上完成运行。上层应引用构建产物，而不是“当前画布”。

耗时任务还要支持超时、退避、断点恢复和取消。节点失败后，应根据副作用选择重试范围，不能默认从头重复全部写入。

## 血缘要能从结论回到来源

真正有用的数据血缘，不只是记录“谁创建了这张表”，而是让一个输出字段能够回到它的来源、变换和运行：

输出字段 → 数据资产版本 → 管道构建 → 节点与表达式版本 → 输入资产版本 → 连接器同步 → 外部来源范围

这条链既服务故障定位，也服务影响分析。当来源字段即将删除时，平台可以提前找出受影响的管道、本体属性、工作台组件和 Agent 工具，而不是等页面报错后逐层排查。

对于文档、图像或音视频，还要保留原件引用。解析后的结构化字段可以进入数据集，但页码、区域和原始文件仍应可追溯，否则 Agent 无法回到原文核验。

六类失败必须成为正式状态：

• 连接失效：停止新同步，保留最后可信版本并标记新鲜度下降
• 结构漂移：运行兼容与影响检查，破坏性变化默认阻断
• 部分成功：明确成功范围，不把半批结果标成完整快照
• 结果未知：先对账再重试，避免重复写入
• 解析失败：单个文件进入隔离队列，不阻塞整批
• 血缘断裂：禁止资产进入需要受治理证据的上层用途

常见失败之一，是只向 Agent 返回一个“可用”布尔值，掩盖数据只适合趋势观察、不适合精确金额决策的事实。另一个失败是结构变化后继续沿用旧敏感标记。第三个失败是构建完成后覆盖旧版本，导致结论无法回放。

## 数据层的落地检查清单

• 连接器是否有稳定协议、版本和健康状态
• 密钥是否只通过受控引用使用
• 数据结构发现是否形成版本并执行差异分析
• 同步是否记录读取范围、检查点和分阶段状态
• 超时和部分成功是否进入未知或待核对状态
• 上层是否引用精确构建产物，而不是当前定义
• 数据质量是否说明允许用途、阻断用途和原因
• 结构化结果是否能回到原始文档或来源范围
• 字段血缘是否覆盖来源、变换、运行与输出版本
• 连接失效时是否保留最后可信资产并显式降级

数据操作系统向上层交付的应是资产契约，而不是数据库入口。契约包含数据版本、结构版本、质量范围、敏感标记和血缘引用；它既不替业务本体决定对象含义，也不把数据库凭据交给 Agent 或工作台。
