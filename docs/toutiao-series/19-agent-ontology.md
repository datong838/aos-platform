# Agent如何真正理解业务：对象、关系与受控动作

让 Agent 读取数据库表，并不等于让它理解业务。一行记录能告诉模型有哪些字段，却不能稳定说明它代表什么对象、与谁有关、当前处于哪个生命周期，以及允许执行哪些动作。业务本体要解决的，就是在数据资产和 AI 决策之间建立一个有身份、有关系、有权限、可受控行动的数字孪生层。

## 对象不是改了名字的数据库行

业务对象至少要定义稳定身份、属性、显示语义、生命周期和权限标记。对象实例可以来自数据集，但业务含义不能由表名和列名自动决定。

object_type: 业务对象类型
identity_key: 稳定业务标识
properties: 状态、时间和业务属性
backing_asset_ref: 数据资产版本
markings: 对象或字段访问标记

同一数据集可以映射出多个对象类型，一个对象类型也可以通过受治理的合并规则吸收多个来源。重点不是复制多少行，而是为上层提供稳定身份和清晰语义。

若主键不稳定、来源版本不明确或必需属性缺失，对象类型就不应发布。错误身份进入数字孪生后，会造成关系重复、历史断裂，甚至让动作写到错误对象上。

## 关系把孤立记录变成业务世界

Agent 的很多判断依赖关系，而不是单个对象。例如，一次服务事件关联哪项业务对象，一份内容引用哪些商品事实，一个设备属于哪个位置。

一类关系需要声明两端对象类型、方向、基数、来源和有效期：

link_type: 对象关系类型
from_type: 来源对象
to_type: 目标对象
cardinality: 一对多或其他基数
source_ref: 关系来源或计算版本
validity: 生效和失效范围

关系不能只因为两个字段名称相似就自动发布。多源冲突、目标缺失和关系数量异常扩张，都应在进入生产图之前检查。

## 用一个合成案例理解对象与关系

设想一个完全虚构的设备维护场景。数据层提供设备记录、位置记录和服务事件，业务本体将它们映射成“设备”“位置”“服务单”三类对象，再建立“设备位于某位置”“服务单针对某设备”的关系。

此时 Agent 不需要猜测字段含义，也不需要自己拼接多张表。它可以查询某设备当前状态、关联位置和未完成服务单，并得到每项属性的来源与版本。

若某个位置对象缺失，相关关系应进入异常状态，而不是悄悄指向空值。若同一设备出现两个冲突位置，系统应保留冲突证据并阻断高风险动作，不能让模型自行选择一个看起来更合理的答案。

## 数据变化要经过可观察的水合流程

数据资产变化后，本体不能直接覆盖当前对象。一个可观察的对象生成流程至少包含四步：

变化日志 → 身份合并 → 检索与关系索引 → 对象水合

变化日志记录候选变化；身份合并按稳定标识和冲突策略收敛；索引阶段更新查询与关系结构；水合阶段生成上层可读取的对象状态。

每个阶段都应保存输入版本、输出版本和错误范围。索引失败时，合并结果不能冒充完整可查询版本；部分对象失败时，系统也要明确说明可用范围。

模型推理结果也不能因为“有价值”就自动写进长期对象。它必须携带证据和适用范围，通过草稿、评测与受控动作进入本体。

## 动作是改变业务状态的唯一入口

如果工作台按钮、Agent 工具和自动化流程各自拥有写库逻辑，本体很快会失去一致性。动作类型应成为改变业务状态的统一协议。

action_type: 状态变更动作
target_type: 目标对象类型
criteria: 服务端前置条件
parameters: 受类型约束的输入
side_effects: 声明式外部副作用
idempotency: 幂等规则
approval_mode: 直接、单人或多人审批

前置条件必须在服务端重新检查。界面显示按钮可用、模型判断动作合理，都不能替代执行时校验。

涉及外部副作用时，还要区分对象状态更新和外部调用结果。外部超时应进入未知态并先对账，不能为了得到成功响应而无限重试。

## 函数默认只读，不能伪装成动作

函数用于可复用计算，例如根据对象属性计算评分、聚合一组对象或生成结构化比较。它应绑定输入输出类型、运行资源和超时边界，并默认只读。

对象输入 → 函数计算 → 结构化结果 → 可选动作提案 → 审批与执行

需要改变对象或外部系统状态时，函数只能返回候选结果，再由动作执行。如果函数内部隐藏写操作，就会绕过前置条件、审批、幂等和审计。

这条边界让 Agent 工具更容易治理：查询与计算进入只读通道，真正写操作统一进入高风险动作通道。

## 三类失败与落地检查清单

第一类失败是从字段名自动推断业务语义。相似列名可能来自不同生命周期或统计口径，自动发布会把技术结构误当业务事实。

第二类失败是直接修改当前本体版本。属性、关系或动作条件变化后，正在运行的 Agent、工作台和历史记录会失去解释基础。正确做法是创建变更分支、执行差异和影响分析、校验审批后发布新版本。

第三类失败是把文档说明或模型结论直接写成对象属性。说明文本可以关联对象，但修改仍要转成动作提案；模型结论则要携带证据、模型和逻辑版本，并支持过期、撤回与重新评测。

上线前可以检查：

• 对象是否具有稳定身份、来源版本和敏感标记
• 关系是否声明方向、基数、来源和有效期
• 对象水合是否保存每阶段输入、输出和失败范围
• 缺失目标、关系冲突和异常扩张是否会被发现
• 所有写操作是否统一进入受控动作
• 动作执行时是否重新检查前置条件和权限
• 只读函数是否禁止隐藏外部副作用
• 本体变更是否通过分支、影响分析和版本发布
• 模型结论是否先进入草稿和评测，而非直接写入
• 高风险图谱问题是否能够阻断相关工具或动作

业务本体向上层交付的是可行动语义，而不是另一套数据库接口。Agent 只在被允许的对象世界中查询、推理和提出动作；每次输入与结果，都能回到本体版本和底层数据来源。
