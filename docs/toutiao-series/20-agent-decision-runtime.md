# 模型答案如何变成企业决策：Agent运行时五道门

给大模型一段提示词和几个接口，很快就能得到答案，但企业真正关心的是：它使用了哪个模型、读取了哪些业务对象、调用了什么工具、为什么得出这个结论，以及结论是否有资格触发动作。Agent 决策运行时要做的，是把一次生成变成有版本、可评测、可审批、能回放的决策过程。

## 第一扇门：模型路由必须受运行边界约束

业务逻辑若直接依赖某个模型供应商，就会同时绑定认证、参数、错误语义、流式协议和模型名称。统一模型网关将供应商连接与上层决策逻辑分开。

provider_ref: 供应商连接引用
route_id: 模型路由
model_class: 能力类型
limits: 超时、预算和并发限制
fallbacks: 允许的备选路由

路由不是简单换一个模型名称。它还要考虑能力、数据区域、成本、延迟、配额和任务风险。处理敏感对象的任务，不能因主模型不可用就自动切换到不满足数据边界的备选路由。

模型健康状态和容量也应成为运行时事实。网关可以拒绝、排队或降级任务，但不能返回一段看似成功的占位文本，让上层误以为决策已经完成。

## 第二扇门：把提示词拆成可检查逻辑

复杂任务不应全部藏在一段提示词里。决策逻辑可以拆成有类型的步骤：

输入 → 对象查询 → 只读计算 → 模型推理 → 确定性护栏 → 草案 → 输出

每个节点都应声明输入输出类型、超时、允许工具和失败策略。逻辑版本要与运行记录绑定；画布以后发生修改，不能改变历史运行的解释。

关键分支也不能只依赖模型自由文本。模型可以输出风险原因和候选等级，但是否进入高风险动作通道，应由服务端的确定性规则判断。

## 第三扇门：工具注册表定义能力边界

Agent 不应保存数据库连接、外部凭据或任意网络地址。它只能调用注册表中经过描述、版本化和授权的工具。

tool_id: 工具标识
version: 工具版本
purpose: 允许用途
input_schema: 结构化输入
output_schema: 结构化输出
required_roles: 角色要求
required_markings: 数据标记要求
risk_level: 只读、草稿或受控动作

读取工具优先返回业务对象和稳定引用，而不是暴露底层表；计算工具默认只读；有副作用的工具只生成动作提案或进入受控执行服务。

外部内容中的文字不能修改工具权限，模型生成的参数也必须经过结构、范围和策略校验。工具说明本身就是安全边界。

## 第四扇门：建议先进入草案区

设想一个完全虚构的库存建议场景。Agent 根据当前对象和已批准逻辑，建议调整一个补货计划。系统首先创建的应是草案，而不是直接改变生产对象。

draft_ref: 草案引用
target_object_ref: 目标对象版本
proposed_change: 结构化变更
evidence_refs: 证据引用
logic_version: 决策逻辑版本
tool_versions: 工具版本
expires_at: 草案失效时间

草案要与生产状态隔离。审批人看到的对象版本、参数和证据，必须与最终执行版本一致；任何关键内容变化都会让旧批准失效。

只读问答可以直接返回结果，但只要输出准备改变对象或外部系统状态，就应进入风险分级后的草案或动作提案。

## 第五扇门：评测决定能发布到哪一级

Agent 评测不能只比较回答是否流畅，还要检查：

• 事实引用是否正确
• 工具选择和参数是否合法
• 数据缺失时是否愿意阻断
• 草案是否越过允许范围
• 相同输入和版本是否保持可接受一致性
• 对抗性内容能否改变系统权限
• 成本、延迟和失败率是否符合运行边界

一次变更应经过：离线测试集 → 工具与权限回归 → 影子运行 → 小范围发布 → 持续监测 → 扩大、回滚或冻结。

评测未通过时，系统可以停留在只读或仅草案阶段。模型置信度提高，并不意味着自动化权限可以同步扩大。

## 决策谱系要回答“为什么”

普通日志告诉工程师发生了哪些调用，决策谱系还要回答为什么做出这个判断。可回放记录至少关联：

• 任务目的和调用角色
• 输入对象、数据快照和本体版本
• 决策逻辑、提示模板和模型路由版本
• 每次工具的输入摘要、输出引用和耗时
• 护栏判断结果
• 草案、审批和动作结果
• 最终输出与后续效果

原始敏感内容不应无限写入记录。系统可以保存受控引用、校验摘要和脱敏片段，并按任务与合规要求设置保留期限。

运行状态也要显式化：准备中、运行中、等待工具、等待审批、已完成、已阻断、结果未知和已取消。这样工作台才能展示真实下一步，而不是只显示不断旋转的聊天气泡。

## 三类失败与落地检查清单

第一类失败是模型不可用时随意降级。只有满足数据边界和任务要求的路由才能作为备选；没有合规备选时应明确失败。

第二类失败是工具超时后一律重试。只读查询可按策略重试，外部动作结果未知时必须先核对状态，否则可能重复执行。

第三类失败是证据或对象版本变化后仍执行旧草案。证据过期应让未执行草案失效；目标对象不一致时，应重新生成或转人工。

上线前可以检查：

• 模型路由是否同时约束数据区域、成本、延迟和风险
• 复杂任务是否拆成有类型、有版本的逻辑节点
• 关键分支是否由确定性护栏而非自由文本决定
• 工具是否经过版本、用途、角色和数据标记校验
• 有副作用的输出是否先进入草案或动作提案
• 审批是否绑定精确对象版本、参数与证据
• 评测是否覆盖事实、工具、权限、阻断和对抗场景
• 决策记录是否能回到数据、本体、逻辑和工具版本
• 运行失败是否具有明确的降级、阻断和熔断出口
• 工作台是否获得结构化状态，而不只是聊天文本

AIP 决策运行时向上层交付的，不只是一段模型回答，还包括结构化结果、对象引用、决策谱系、草案状态、所需审批和失败原因。它让模型负责生成与推理，让系统负责权限、版本、工具边界和是否允许继续。
