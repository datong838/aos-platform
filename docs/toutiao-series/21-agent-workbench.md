# Agent工作台不只是聊天框：如何组织真实业务操作

企业把 Agent 接进系统后，最常见的界面是聊天框。但进入真实业务时，人还需要看见对象、缩小范围、比较证据、修改参数、审批建议，并确认动作是否真正完成。Agent 工作台不是聊天外壳，也不是报表大屏，而是把页面状态、对象选择和用户事件转换成可验证决策上下文的交互运行时。

## 工作台为何不能只是静态看板

静态看板回答“发生了什么”，工作台还要回答三个问题：当前操作针对哪些对象，这些对象为什么被选中，接下来允许执行什么动作。

如果页面只展示聚合指标，用户仍要去另一个系统重新寻找对象；如果组件直接调用数据库，又会绕过权限重验、幂等和审计。

可靠链路应是：

模块版本 + 页面变量 + 对象查询 + 选择集 → 决策上下文 → Agent 建议 → 草案或动作提案 → 人工确认 → 受控动作 → 执行回执与刷新

其中最重要的边界是：页面只能表达意图，不能绕过业务动作直接修改底层数据。

## 模块、组件和变量分别负责什么

模块是带版本的业务应用单元，不只是一个网址。它声明页面使用哪些对象类型、变量、布局、事件和允许触发的动作。编辑态与发布态应分离，运行中的用户访问固定版本，设计者继续修改下一版，校验发布后才切换。

组件负责表格、指标、关系图、详情面板或对话入口，但不拥有业务真相。组件读取的是对象查询结果，而不是自己拼接底层表；字段是否可见由服务端根据用户、工作区、用途和数据标记裁剪。前端隐藏一列从来不等于权限控制。

变量显式保存日期范围、区域、对象状态和策略版本。它应有类型、默认值、约束和序列化格式，而不是散落在组件中的临时状态。类型化变量让页面可以分享和回放，也让 Agent 得到结构化条件而不是含义模糊的自然语言。

## 选择集把“我看到的”变成“我在处理的”

选择集是工作台与 Agent 之间最关键的桥梁。它不能只保存表格行号，而要保存对象类型、对象引用、查询快照和选择时间。

当用户说“分析这些对象”时，前端应传递受限的选择集引用，由 Agent 按权限读取必要属性，而不是把整页数据塞进提示词。这既减少上下文，也能在决策时重新检查对象是否仍有效。

面对巨大选择集，系统不应传递数万个对象编号。更合理的做法是保存“查询条件 + 快照版本 + 排除项”，并设置最大规模、过期时间和采样预览。

## 事件只描述意图，不承诺结果

筛选变化、选择变化、按钮点击和审批决定都可以表示为事件。一个事件至少包含：

event_id: 事件唯一标识
module_version: 模块版本
actor: 操作者
event_type: 事件类型
selection_ref: 选择集引用
variable_snapshot: 变量快照
occurred_at: 发生时间

事件标识可以作为幂等键。用户连续点击两次“生成方案”，服务端识别为同一请求，而不是创建两份任务。

Agent 基于选择集和变量形成建议后，应先输出草案或动作提案。提案说明目标对象、动作类型、参数、依据、风险、有效期和所需审批。用户确认时，系统还要重新检查对象版本、权限、提案有效期和业务约束。

## 用一个合成案例走完整链路

设想一个完全虚构的异常处理模块：

1. 工作台加载已经发布的模块版本
2. 服务端根据变量生成对象查询
3. 返回经过权限和字段标记裁剪的分页结果
4. 用户勾选若干异常对象，形成选择集引用
5. Agent 读取有限上下文，生成带证据的处理草案
6. 用户修改参数并批准，产生审批事件
7. 业务动作层重新校验并执行，返回执行回执
8. 工作台根据回执刷新对象，而不是乐观假设成功

页面负责交互状态，Agent 负责推理与建议，动作层负责业务不变量和写入。三者职责分开，才能在出错时准确定位。

## 五类失败必须在界面里诚实呈现

第一，选择集已经过期。用户停留太久后，对象可能被别人处理；执行前要比较对象版本，变化后要求重新加载。

第二，权限在审批前变化。能看到建议不代表此刻仍能执行，高影响动作必须提交时重新鉴权。

第三，大表被组件拉成全量。表格只能使用服务端分页、排序和过滤；导出、批量选择和聚合查询应走独立限额。

第四，连续点击造成重复动作。按钮禁用只改善体验，事件和动作仍需幂等键；网络超时后应查询原事件状态，而不是创建新动作。

第五，执行结果处于未知态。外部超时不等于失败，回执应区分成功、失败、未知和对账中。未知时，工作台展示“正在对账”，禁止盲目重试高风险动作。

断网时同样要诚实：可以缓存已授权只读快照，但必须展示数据时间和离线标记；离线生成的内容只能保存为本地草稿，不能伪装成已提交动作。

对话如何安全进入工作台：

对话可以成为模块中的一个组件，自动继承当前模块版本、变量快照和选择集，但只接收策略允许的字段。

反过来，Agent 也不能用一段文本任意控制界面。它可以返回结构化界面意图，例如建议高亮一组对象、打开某个详情区域或生成新筛选条件；工作台验证该意图是否在模块声明范围内，再决定是否执行。

这种双向契约让自然语言具有操作力，又不会让模型获得任意前端控制权。

## 工作台落地检查清单

• 模块编辑态与发布态是否分离并具有版本
• 组件是否只读取对象查询结果，而不直连数据库
• 字段权限是否由服务端裁剪，而不是只靠前端隐藏
• 页面变量是否类型化、可序列化和可回放
• 选择集是否保存对象引用、快照版本和过期时间
• 大选择集是否使用查询条件与排除项，而非传递全量编号
• 每个用户事件是否具有幂等标识
• Agent 输出是否先进入草案或动作提案
• 审批时是否重新检查权限、对象版本和业务条件
• 执行回执是否明确区分成功、失败、未知和对账中

衡量 Agent 工作台的，不是页面和组件数量，而是从发现问题到形成可审批提案的时间、过期选择集被拦截的比例、重复事件被吸收的比例、未知动作完成对账的时间，以及每次决策能否回放到完整证据。
