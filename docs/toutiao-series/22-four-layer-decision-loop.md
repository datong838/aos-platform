# Agent决策如何穿过四层：查询、审批与写回

企业 Agent 最危险的错觉，是把一段连贯的对话当成一条完整的业务链。模型可以在几秒内给出答案，但业务系统还需要回答：它看的是哪一版数据？建议针对哪些对象？谁批准了哪些参数？外部动作是否真正完成？

一条可进入生产流程的 Agent 决策，应当穿过四个职责不同的运行层，并留下七类稳定引用：

```text
SnapshotRef
   ↓
ObjectSetRef
   ↓
DecisionDraft
   ↓
SelectionRef
   ↓
ActionProposal
   ↓ approval
ExecutionReceipt
   ↓
ReconciliationResult
```

这些引用把“模型说了什么”转换为“系统在什么证据、权限和版本条件下做了什么”。它们比一段对话历史更适合审计、重试和复盘。

## 第一站：数据层冻结证据窗口

决策从数据操作系统开始，但 Agent 不直接拿数据库连接。数据层先把外部来源同步为带版本的数据资产，并为这次分析返回 `SnapshotRef`。

一个快照引用至少描述：

```text
dataset_version
source_watermark
schema_version
freshness_at
lineage_ref
quality_status
```

`source_watermark` 表示同步推进到哪个来源位置，`freshness_at` 表示数据新鲜度，`quality_status` 则说明当前快照是否满足决策门槛。

这一步解决的不是“怎样查得快”，而是“同一个结论以后能否重现”。如果分析过程中数据持续变化，却没有快照边界，两次相同查询可能得到不同对象，后续审批就失去稳定依据。

数据不新鲜时，系统不应让模型自行淡化风险。它应该返回明确状态，例如 `STALE`、`PARTIAL` 或 `QUALITY_BLOCKED`。低风险场景可以带警告继续，高风险动作则直接阻断。

## 第二站：本体层生成业务对象集合

数据集只有字段和记录，业务决策需要对象、关系和语义。本体层把查询条件编译成 `ObjectSetRef`，例如某类设备、合同或任务的受限集合。

对象集合引用不必复制全部对象，而可以保存：

```json
{
  "objectType": "BusinessObject",
  "queryHash": "...",
  "snapshotRef": "...",
  "ontologyVersion": "...",
  "count": 128,
  "expiresAt": "..."
}
```

这里的 `ontologyVersion` 很关键。相同字段在不同语义版本中可能拥有不同含义，关系规则和可执行动作也可能变化。决策必须绑定语义版本，而不是只绑定一批主键。

本体服务还会执行对象级和字段级裁剪。Agent 得到的不是“平台知道的一切”，而是当前用户、用途和工作区允许读取的最小对象视图。

## 第三站：决策层形成可检查的草案

Agent 接收 Snapshot 与 ObjectSet 的有限上下文，通过 Logic 和受控 Tool 生成 `DecisionDraft`。草案不是最终动作，至少应包含：

- 结论和建议；
- 使用的对象集合与证据引用；
- 关键假设；
- 置信区间或不确定性；
- 建议调用的 Action 类型；
- 风险等级和所需审批；
- 草案有效期。

模型输出必须先经过结构校验，再经过策略校验。结构校验判断字段、类型和引用是否完整；策略校验判断模型是否调用了允许的工具、是否跨越用途边界、是否把缺失证据描述成确定事实。

模型版本、提示版本、Logic 版本、工具版本和推理 Trace 都应附着在草案上。这样评测系统才能比较：同一证据输入在新版本下是否发生了不可接受的决策漂移。

## 第四站：工作台把草案交给人

工作台读取草案后，不应把它渲染成一个只有“确认”按钮的黑盒。用户需要看见建议对象、证据时间、关键参数、预计影响和失败后果。

人在页面中调整范围或参数时，会产生新的 `SelectionRef` 和变量快照。原始草案仍然保留，但操作对象已经变化，因此系统要生成新的 `ActionProposal`，不能在旧草案上悄悄改值。

一次批准应明确绑定：

```text
proposal_id
proposal_hash
approver
approved_parameters
object_set_version
policy_version
approved_at
expires_at
```

批准的是这份提案的这个哈希，而不是“永远同意 Agent 做此类操作”。当参数、对象集合或策略任一变化时，旧批准自动失效。

## 第五站：本体动作执行写入

Action 执行器收到批准后的提案，仍需做最后一次校验：

1. 提案是否过期；
2. 对象版本是否变化；
3. 操作者当前权限是否仍有效；
4. 业务前置条件是否满足；
5. 幂等键是否已经执行过。

只有全部通过，执行器才调用内部或外部 Connector。工作台和模型都不能直接写数据库，也不能持有外部系统密钥。

执行结果应写成 `ExecutionReceipt`：

```text
action_id
idempotency_key
target_refs
request_digest
executor_version
started_at
finished_at
status
external_receipt_ref
```

回执记录的是技术执行事实，而不是业务效果。接口返回 200，只能说明请求被接受；它不能证明目标对象最终达到了期望状态。

## 第六站：数据层完成结果对账

动作之后，数据层重新同步外部状态，本体层重新水合对象，再由对账逻辑比较预期变化与实际变化，生成 `ReconciliationResult`。

对账结果可以分为：

- `CONFIRMED`：外部状态与预期一致；
- `DIVERGED`：动作完成，但结果与预期不同；
- `NOT_OBSERVED`：在观察窗口内尚未看到变化；
- `UNKNOWN`：外部状态无法确定；
- `ROLLED_BACK`：已执行补偿或撤销。

只有到达这一步，一条决策链才真正闭环。Agent 的“建议正确率”和动作的“接口成功率”都不能替代业务结果对账。

## 四层之间传递引用，不传递特权

一个常见错误是：为了减少调用，把数据库凭证、完整对象和执行能力一起交给 Agent。短期看很方便，长期会让每一次决策都无法解释权限来自哪里。

更稳健的原则是：

- 数据层传递 SnapshotRef，不传数据库连接；
- 本体层传递 ObjectSetRef，不传全量敏感字段；
- 决策层传递 Draft，不传执行凭证；
- 工作台传递 ApprovalEvent，不直接调用外部写接口；
- 动作层返回 Receipt，不把“已接收”包装成“已达成”。

引用可以跨层验证，特权不能跨层继承。

## 四种最棘手的失败路径

### 证据版本与审批版本错位

草案基于快照 A，审批时页面已经刷新到快照 B。系统应展示版本差异，并要求重新生成或重新批准；不能用最新页面掩盖旧证据。

### 批准后权限被撤销

批准是一段带有效期的决策事实，不是永久授权。动作执行时必须重新鉴权；权限撤销后，提案应进入 `AUTH_REJECTED`。

### 外部超时但动作可能已完成

此时不能自动重发。执行器先使用幂等键查询外部回执，状态进入 `UNKNOWN` 或 `RECONCILING`；只有确认未执行后才允许安全重试。

### 动作完成但业务结果偏离

外部操作成功，随后状态却没有按预期变化。系统应把差异反馈给评测和策略层，区分“执行故障”与“决策假设错误”，而不是简单把失败归给模型。

## 如何回放一次决策

审计者不需要复刻整个运行环境，只要沿引用链读取：数据快照、对象语义、模型和 Logic 版本、草案、人的修改、批准哈希、执行回执与对账结果。

如果其中任何一环只有自然语言日志而没有稳定标识，这次回放就是不完整的。真正的可解释性不是让模型多写一段理由，而是让每个结论都能回到证据、版本、责任人与结果。

四层运行时的价值，也不在于层次越多越先进，而在于把查询、推理、批准和写回分配给不同责任主体，再用引用把它们组成闭环。
