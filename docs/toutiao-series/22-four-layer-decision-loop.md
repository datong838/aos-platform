# 一条Agent决策如何闭环：从数据快照到结果对账

企业 Agent 最危险的错觉，是把一段连贯对话当成完整业务链。模型几秒就能给出建议，系统却仍需回答：它看的是哪版数据、针对哪些对象、谁批准了哪些参数、外部动作是否真正完成。一条可进入生产流程的决策，必须穿过数据、本体、决策和工作台四层，并用稳定引用串起证据、审批与结果。

## 第一步：数据层冻结证据窗口

决策从数据操作系统开始，但 Agent 不直接获得数据库连接。数据层先把外部来源同步为带版本的数据资产，再为本次分析返回快照引用。

dataset_version: 数据资产版本
source_watermark: 来源同步位置
schema_version: 数据结构版本
freshness_at: 新鲜度时间
lineage_ref: 血缘引用
quality_status: 质量状态

这一步解决的不是“怎样查得快”，而是“以后能否重现同一结论”。若分析过程中数据持续变化却没有快照边界，两次相同查询可能得到不同对象，后续审批便失去稳定依据。

数据不新鲜时，系统应返回过期、部分可用或质量阻断等明确状态。低风险分析可以带警告继续，高风险动作则直接阻断，不能让模型自行淡化风险。

## 第二步：本体层生成业务对象集合

数据集只有字段和记录，业务决策需要对象、关系和语义。本体层把查询条件编译成对象集合引用，并绑定本体版本、数据快照、对象数量和失效时间。

对象集合引用不必复制全部对象。它可以保存对象类型、查询摘要、快照引用、本体版本、规模和有效期。

本体版本非常关键：相同字段在不同语义版本中可能含义不同，关系规则和可执行动作也可能变化。决策必须绑定语义版本，而不只是绑定一批主键。

本体服务还负责对象级和字段级裁剪。Agent 得到的不是平台掌握的全部信息，而是当前用户、用途和工作区允许读取的最小对象视图。

## 第三步：决策层形成可检查草案

设想一个完全虚构的设备巡检场景。Agent 接收数据快照和受限设备集合，通过版本化逻辑和受控工具生成处理草案。

草案至少应包含结论、对象集合、证据引用、关键假设、不确定性、建议动作、风险等级、所需审批和失效时间。

模型输出先做结构校验，再做策略校验。前者检查字段、类型和引用是否完整；后者检查工具是否允许、用途是否越界、缺失证据是否被描述成确定事实。

模型版本、提示版本、决策逻辑版本、工具版本和推理记录都要绑定到草案。这样才能评估同一证据在新版本下是否发生不可接受的决策漂移。

## 第四步：工作台把建议交给人

工作台不能把草案渲染成只有“确认”按钮的黑盒。用户需要看见建议对象、证据时间、关键参数、预计影响和失败后果。

当人在页面中调整范围或参数时，会产生新的选择集和变量快照。原草案仍然保留，但操作对象已经变化，因此系统要生成新的动作提案，不能在旧草案上悄悄改值。

一次批准应绑定提案标识、提案校验值、审批人、批准参数、对象集合版本、策略版本、批准时间和失效时间。

批准的是这份提案的这个版本，不是永久同意 Agent 做同类操作。参数、对象集合或策略任一变化，旧批准都自动失效。

## 第五步：动作层校验、执行并返回回执

执行器收到批准提案后，仍需最后检查：提案是否过期、对象版本是否变化、操作者权限是否有效、业务前置条件是否满足，以及幂等键是否已经执行过。

全部通过后，执行器才调用内部或外部连接器。工作台与模型都不能直接写数据库，也不能持有外部系统密钥。

执行回执至少记录动作标识、幂等键、目标对象、请求摘要、执行器版本、开始与结束时间、技术状态和外部回执引用。

回执记录的是技术执行事实，不是最终业务效果。接口返回成功，只能说明请求被接受，不能证明目标对象已经达到预期状态。

## 第六步：数据层重新同步并完成对账

动作之后，数据层重新同步外部状态，本体层重新生成对象，再由对账逻辑比较预期变化与实际变化。

结果至少区分：

CONFIRMED：外部状态与预期一致

DIVERGED：动作完成，但结果与预期不同

NOT_OBSERVED：观察窗口内尚未看到变化

UNKNOWN：外部状态无法确定

ROLLED_BACK：已完成补偿或撤销

只有到达对账环节，决策链才真正闭环。Agent 建议正确率和接口成功率，都不能替代业务结果核验。

## 四类失败与闭环检查清单

第一类失败是证据与审批版本错位。草案基于快照 A，审批页面已经刷新到快照 B；系统应展示差异并要求重新生成或重新批准。

第二类失败是批准后权限被撤销。批准是带有效期的决策事实，不是永久授权；执行时必须重新鉴权。

第三类失败是外部超时但动作可能已经完成。此时不能自动重发，应使用幂等键查询回执并进入未知或对账状态。

第四类失败是动作成功但业务结果偏离。系统要区分执行故障与决策假设错误，并把差异反馈给评测和策略层。

上线前可以检查：

• 数据层是否为每次决策提供可回放快照
• 对象集合是否绑定数据快照、本体版本和有效期
• Agent 是否只读取用途允许的最小对象视图
• 决策草案是否记录证据、假设、不确定性和版本
• 人工修改后是否生成新提案，而非覆盖旧草案
• 批准是否绑定精确参数、对象范围和策略版本
• 执行前是否重新检查权限、前置条件和幂等键
• 技术回执是否与业务对账结果明确区分
• 外部超时是否先对账而非直接重试
• 整条链是否能够沿稳定引用回放

四层之间应传递引用，而不是传递特权：数据层传快照，不传数据库连接；本体层传对象集合，不传全量敏感字段；决策层传草案，不传执行凭证；工作台传审批事件，不直接调用写接口；动作层返回回执，不把“已接收”包装成“已达成”。
