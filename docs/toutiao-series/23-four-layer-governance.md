# 四层运行时的治理脊柱：租户、谱系与发布

企业 AI 平台常把治理做成一组分散功能：数据层有权限，模型层有安全过滤，工作台有菜单控制，动作层有审批。每一处看起来都做了防护，组合起来却可能出现空隙。

原因在于，一条 Agent 决策会同时穿过数据资产、业务本体、决策运行时和工作台。如果四层各自解释“谁能看、为什么能用、当前是哪一版”，同一对象就会在跨层传递中不断丢失约束。

因此，治理不应该成为第五个业务层，而应成为四层共享的控制脊柱：

```text
              Governance Spine
  ┌──────────────────────────────────┐
  │ Tenant / Workspace / Purpose     │
  │ Marking / Policy / Approval      │
  │ Lineage / Trace / Audit          │
  │ Version / Release / Rollback     │
  └──────────────────────────────────┘
       ↑          ↑          ↑
Data → Ontology → Decision → Workbench
```

共享不等于所有层共用一张权限表，而是它们使用同一组主体、资源、用途、版本和证据引用，并遵守一致的不变量。

## 第一条不变量：资源不能脱离租户和工作区

组织、租户与工作区解决的是不同边界。组织定义管理归属，租户形成强隔离边界，工作区承载具体项目或业务域。

任何可持久化资源都应带有明确作用域，包括 Dataset、ObjectType、Logic、Agent、Module、Draft 和 Action。一个通用资源标识可以表示为：

```text
ResourceRef = tenant_id
            + workspace_id
            + resource_type
            + resource_id
            + version
```

跨工作区协作不能靠复制 URL 或转发对象 ID。系统需要显式共享关系，说明资源从哪里来、以什么权限共享、是否允许派生、何时失效。

尤其要避免“全局管理员”成为数据面万能钥匙。平台管理权限可以负责配置和运维，但不应自动获得所有业务数据的读取权。管理面与数据面需要分别授权。

## 第二条不变量：用途必须跟随每次访问

角色回答“这个人通常能做什么”，用途回答“这次为什么要做”。同一个用户可能有权查看某类对象，但只允许用于运营分析，不能把数据带入另一个目的的模型训练或外部触达。

一次访问决策可抽象为：

```text
allow = policy(
  subject,
  tenant,
  workspace,
  resource,
  action,
  purpose,
  markings,
  environment
)
```

`environment` 包括时间、网络区域、设备可信度和风险等级。策略结果不只是允许或拒绝，还可以要求字段遮罩、降低精度、只返回聚合结果，或者增加人工审批。

用途不能只存在登录会话里。它需要进入 SnapshotRef、ObjectSetRef、DecisionDraft、Approval 和 Action Trace，避免下游误把为某一目的取得的数据用于另一目的。

## 第三条不变量：Marking 随数据派生传播

Marking 是附着在数据或对象上的安全与使用标记，例如敏感等级、地域限制、保留期限或禁止进入模型上下文。

最容易被忽视的问题是派生数据。当多个字段被汇总成指标、对象被转成摘要、文档被切片并向量化时，原始标记不能凭空消失。

一种保守的传播规则是：

```text
output_marking = join(input_markings)
                 + transform_policy
                 + declared_declassification
```

`join` 默认继承输入中的最严格约束；只有经过明确批准的脱敏或聚合过程，才能执行降级。模型生成的摘要也属于派生物，必须记录输入标记和变换策略。

这意味着向量索引、缓存、搜索片段和导出文件都不是“技术中间产物”，而是治理资源。它们同样需要作用域、保留期和删除传播。

## 第四条不变量：Lineage 要覆盖决策，不只覆盖数据

传统数据谱系描述“某张表来自哪里”。Agent 系统还需要决策谱系：一个建议用了哪些快照和对象，经过哪个 Logic、模型、工具和提示版本，由谁修改和批准，最终触发了哪个动作。

可以把完整链条表示为：

```text
Source → SyncRun → DatasetVersion → ObjectVersion
       → DecisionTrace → DraftVersion → Approval
       → ActionAttempt → ExternalReceipt → Reconciliation
```

谱系节点应使用稳定 ID，边应说明关系类型，例如 `DERIVED_FROM`、`READ_BY`、`APPROVED_AS`、`EXECUTED_BY` 和 `RECONCILED_WITH`。

如果只保存聊天记录，无法证明模型实际读到了哪些对象；如果只保存接口日志，又无法知道哪个人工批准授权了动作。决策谱系必须同时连接数据、模型、人和结果。

## 第五条不变量：所有跨层组合都通过 Release 发布

四层资源各自有版本，但真正运行的是一组兼容版本。例如一个工作台模块依赖特定 ObjectType、Logic、Tool Schema 和 Action Contract。只发布其中一个，就可能出现页面字段已更新、Agent 仍按旧语义推理的情况。

因此需要一个 Release Manifest：

```yaml
release_id: r_xxx
resources:
  datasets: [...]
  ontology: [...]
  logic: [...]
  agents: [...]
  modules: [...]
  actions: [...]
policies: [...]
compatibility_checks: [...]
```

Manifest 固定每个资源版本，并在发布前执行契约兼容、权限覆盖、评测门槛和回滚可用性检查。运行请求绑定 `release_id`，这样问题发生后才能确定当时真正运行的组合。

## 发布不是把草稿改成“已发布”

一条稳健的发布路径至少包含：

```text
DRAFT
  → VALIDATING
  → EVALUATING
  → APPROVAL_REQUIRED
  → CANARY
  → ACTIVE
  → SUPERSEDED / ROLLED_BACK
```

不同资源使用不同验证器：数据管道检查 Schema 和质量，本体检查关系与动作契约，决策层运行 Evals，工作台检查依赖和可访问性。Release 层汇总结果，任何关键门槛失败都不能进入 Active。

金丝雀阶段还应限制工作区、用户组、流量和允许动作范围。扩大范围必须基于线上 Trace 和结果指标，而不是只看模型离线分数。

## 回滚到底回滚什么

页面代码容易回滚，业务动作却可能已经造成外部影响。因此回滚至少分三类：

### 配置回滚

把 Module、Agent、Logic 或 Policy 指针恢复到上一稳定版本。新请求使用旧版本，已有 Trace 仍保持原引用。

### 数据与语义回滚

数据资产通常不能简单覆盖，需要生成修订版本并保留原 Lineage；本体变更要处理新旧对象映射和关系兼容。

### 业务补偿

已执行 Action 不能靠版本指针撤销。动作类型必须声明是否可补偿、由谁批准、补偿窗口多长，以及外部系统不支持撤销时如何人工处置。

把三类回滚混成一个“撤回发布”按钮，会制造虚假的安全感。

## 策略也需要版本和评测

权限策略不是永远正确的静态配置。一次规则修改可能让合法流程全部阻断，也可能意外扩大访问范围。

策略发布前可以使用历史匿名化 Trace 做回放，比较：

- 新增允许与新增拒绝的数量；
- 哪些字段从遮罩变为明文；
- 哪些高风险动作不再要求审批；
- 哪些跨工作区引用发生变化；
- 旧版本批准是否会被错误复用。

策略决策本身也要进入审计记录，包括策略版本、输入属性、命中规则和最终义务。这样才能解释“当时为什么允许”，而不是只记录一个布尔值。

## 四层各自承担什么治理责任

共享脊柱并不会抹平分层边界：

- 数据层负责来源、质量、新鲜度、保留和派生谱系；
- 本体层负责对象级语义、关系约束、字段 Marking 和 Action 不变量；
- 决策层负责模型、Logic、Tool、Draft、Trace 和 Evals 的版本治理；
- 工作台负责最小展示、选择集、人工批准和交互事件；
- 治理脊柱提供统一主体、用途、策略、审计和 Release 引用。

每一层执行最靠近自身资源的检查，但检查所依据的身份和策略语义必须一致。

## 五个应当持续监控的信号

治理是否有效，不能只数权限规则。更有意义的运行信号包括：

1. 跨工作区引用被拒绝或显式授权的比例；
2. 派生数据缺失 Marking 的比例；
3. 决策 Trace 能完整连接到结果对账的比例；
4. Release 依赖不兼容被上线前拦截的比例；
5. 未知态动作和补偿动作的解决时长。

这些指标直接指向跨层断点，比“建立了多少制度”更能反映系统是否真正受控。

## 结语

数据资产、本体、决策运行时和工作台解决的是不同问题；它们能够组成企业级 Agent 平台，靠的不是一个万能模型，而是共同遵守的边界。

租户与工作区界定资源归属，用途和 Marking 约束数据怎样被使用，Lineage 与 Trace 保留从证据到结果的路径，Release 与回滚控制变化如何进入运行环境。

当这条治理脊柱存在时，四层可以独立演进又不会失去共同语义；Agent 也才能从“会回答问题的模型”，成长为一个能够被批准、被限制、被回放并对结果负责的业务参与者。
