# 四层Agent平台如何共用一套治理脊柱

一家虚构零售企业上线智能补货助手：数据层允许读取库存，本体层把库存映射成商品对象，决策层生成补货建议，工作台交给采购审批。每层单独看都“有权限”，系统却无法回答三个问题：这次读取为了什么？建议基于哪一版数据？批准的方案是否就是最终执行的版本？

问题不在于少装了一个权限系统，而在于四层各说各话。企业级 Agent 要稳定运行，需要一条贯穿数据、本体、决策与工作台的治理脊柱，让身份、用途、证据和版本在跨层传递时不丢失。

## 一、治理不是第五层，而是四层共同遵守的协议

四层各自解决不同问题：数据层提供可信资产，本体层表达业务对象，决策层组织模型与工具，工作台承载人工操作。治理脊柱不替代这些能力，而是规定跨层资源如何被引用。

最小治理上下文可以写成：

资源引用 = 租户 + 工作区 + 资源类型 + 资源编号 + 版本

访问上下文 = 主体 + 动作 + 用途 + 安全标记 + 环境

运行证据 = 数据快照 + 对象版本 + 决策轨迹 + 审批记录 + 动作回执

这三组引用必须跟随一次请求走完整条链路。工作台不能只传一个对象编号，决策层不能只保存聊天记录，数据层也不能只记录“某接口被调用”。否则系统只能证明“发生过调用”，无法证明“为什么允许、基于什么、批准了什么”。

## 二、先固定资源边界，再讨论模型能力

组织、租户和工作区不是同一个概念。组织描述管理归属，租户形成强隔离边界，工作区承载一个项目或业务域。任何可持久化资源都应明确属于哪个租户、哪个工作区以及哪个版本。

这里有三个常见失败路径：

• 失败路径一：管理员拥有平台配置权，于是被默认授予全部业务数据读取权。结果是管理面权限意外穿透数据面。

• 失败路径二：团队用复制链接或转发对象编号完成跨工作区共享。对象虽然能打开，原有的用途限制、到期时间和派生约束却没有一起传递。

• 失败路径三：缓存、向量索引和导出文件被当成技术中间产物。原始数据删除后，派生副本仍然存在。

更稳妥的做法是显式建立共享关系，写清来源、授权范围、是否允许派生和何时失效。平台管理员可以维护系统，但不应天然成为业务数据的万能钥匙。

## 三、权限只回答“能不能”，用途还要回答“为什么”

传统角色权限通常判断“这个人能否查看订单”。但在 Agent 场景中，同一个人可能被允许为了经营分析查看聚合数据，却不能把明细带入外部触达或模型训练。

一次策略判断至少需要考虑：

允许结果 = 策略（主体，租户，工作区，资源，动作，用途，安全标记，运行环境）

策略输出也不应只有允许和拒绝，还可以要求字段遮罩、降低数据精度、仅返回聚合值或增加人工审批。

用途必须进入数据快照、对象集合、建议草稿、审批记录和动作轨迹。若用途只存在登录会话中，后续模块拿到数据后就可能换一个目的继续使用，形成“第一次访问合法，第二次使用越界”的漏洞。

## 四、安全标记和决策谱系必须跟着派生物走

安全标记可以表达敏感等级、地域限制、保留期限，或禁止进入模型上下文。难点不在原始字段，而在派生过程：指标汇总、对象摘要、文档切片、向量索引和模型生成内容都可能让标记悄悄消失。

一条保守规则是：输出标记继承所有输入中的最严格约束；只有经过明确批准的脱敏或聚合过程，才允许降低等级。

同样，数据谱系还不够。Agent 平台需要决策谱系，把下面这条链连接起来：

数据源 → 同步批次 → 数据版本 → 对象版本 → 决策轨迹 → 草稿版本 → 人工审批 → 动作尝试 → 外部回执 → 结果对账

只保存聊天记录，无法证明模型真正读取了哪些对象；只保存接口日志，又无法知道哪个人工批准授权了动作。二者必须通过稳定引用连接起来。

## 五、四层组合要作为一个发布单元

生产环境实际运行的不是某个孤立模型，而是一组兼容版本：数据结构、本体对象、决策逻辑、工具参数、工作台模块和动作契约。只更新其中一项，可能出现页面已经展示新字段，Agent 仍按旧语义推理的情况。

因此，每次上线都需要一份发布清单，固定各层资源版本，并在发布前检查：

• 数据结构与质量是否满足要求；

• 本体关系和动作契约是否兼容；

• 决策评测是否达到门槛；

• 工作台依赖和最小权限是否正确；

• 旧版本是否仍可恢复，已执行动作是否可补偿。

发布流程不应只是把状态从“草稿”改成“已发布”，而应经过校验、评测、审批、小范围启用、正式生效等阶段。扩大范围要依据线上轨迹和结果指标，而不是只看离线模型分数。

回滚也要分清三类：配置可以切回旧版本；数据与语义需要生成修订版本并保留谱系；已经产生外部影响的动作，则必须走补偿流程。把三类情况都塞进一个“撤回”按钮，会制造虚假的安全感。

## 六、上线前可直接使用的治理检查清单

一个四层 Agent 应用进入生产前，可以逐项确认：

1. 每个数据集、对象、决策逻辑、工作台模块和动作是否都有租户、工作区与版本引用？

2. 跨工作区共享是否显式授权，并带有范围、用途、派生权和失效时间？

3. 用途和安全标记是否贯穿数据快照、模型上下文、草稿、审批与动作轨迹？

4. 缓存、索引、摘要和导出文件是否被纳入保留、删除与审计策略？

5. 一条建议能否追溯到输入数据、对象版本、模型或逻辑版本、审批人和最终回执？

6. 发布清单是否固定了四层依赖，并完成契约、权限、评测与回滚检查？

7. 高风险动作是否默认停留在草稿或审批状态？执行结果未知时，系统是否会停止重试并交给人工判断？

8. 已执行动作是否声明可补偿性、审批人、补偿窗口和人工处置方式？

治理真正有效的标志，不是规则数量很多，而是发生问题时能快速回答：谁在什么用途下使用了哪一版资源，谁批准了哪个版本，外部系统最终发生了什么。

当租户边界、用途、安全标记、决策谱系与发布版本形成共同协议，四层才能独立演进而不失去一致约束。Agent 也才会从“能给答案的模型”，变成可以被限制、被批准、被回放并对结果负责的业务系统。
