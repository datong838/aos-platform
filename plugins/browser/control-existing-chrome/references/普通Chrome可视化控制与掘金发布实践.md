## 1. 结论

本次成功的关键不是“更强的反检测”，而是选择了正确的浏览器控制面：复用用户已经打开、已经登录的普通 Google Chrome，通过 macOS Computer Use、Accessibility 或等价系统级可视化控制执行点击、输入和状态读取。这条主路径不需要安装 Chrome 扩展。

当前实践和 Skill 仅支持 macOS。Windows UI Automation、Windows Computer Use 以及 Linux 辅助功能控制尚未实现和验证，不得根据“Chrome 本身跨平台”推导本 Skill 也跨平台。

这种方式没有复制 Cookie，没有导出登录凭证，也没有新建自动化 Profile。它直接操作用户授权的真实会话，因此能够继续使用现有标签页和登录上下文。

这不是绕过网站风控的技术。遇到验证码、风险验证或安全挑战仍必须停止，让用户处理或放弃该动作。

## 2. 两种浏览器控制模式

### 2.1 独立自动化浏览器

Kitewright、Playwright、Puppeteer 一类引擎通常自行启动 Chrome/Chromium，创建独立 Profile，并通过 CDP 控制。

优点：

- 会话隔离，适合并发和可重复测试；
- 可抓取网络、控制台和无障碍树；
- 适合批量 E2E、截图、PDF 和 CI。

局限：

- 不拥有用户普通 Chrome 的登录态；
- 浏览器启动方式、临时 Profile 和自动化属性可能被站点识别；
- 登录和强风控站点可能出现不同于普通 Chrome 的兼容行为。

### 2.2 现有普通 Chrome

这一模式不启动新的浏览器，而是操作用户当前运行的普通 Chrome，直接沿用其已登录账号、现有标签页和会话上下文。默认实现不要求 Chrome 扩展。

本文“现有普通 Chrome”专指用户当前 macOS 桌面会话中可见、可由系统辅助功能访问的 Google Chrome。本文流程不适用于 Windows 或 Linux。

可用控制面按优先级排列：

1. macOS Computer Use、Accessibility 或等价系统可视化控制；这是无扩展主路径；
2. 工具已经具备的原生 Chrome 连接；它是可选增强，不是前置条件；
3. 用户明确以 `--remote-debugging-port` 启动时的 CDP Bridge。

优点：

- 直接复用现有登录态和标签页；
- 用户可看到全部操作并随时中止；
- 页面行为最接近日常人工浏览。

局限：

- 操作容易受到用户同时点击、窗口切换和弹窗影响；
- Accessibility 元素索引会变化，必须每步重新读取；
- 不一定具备完整网络/控制台捕获能力；
- 多任务并发写同一 Profile 容易互相干扰。

## 3. 本次掘金现场

### 3.1 失败链路

Kitewright 启动了独立可视 Chrome。访问掘金创作者中心后，页面长期停留在 `Please wait...`。

只读环境检查观察到 `navigator.webdriver=true`。Kitewright 源码同时证明：引擎每次启动都会建立独立临时 `user_data_dir`，自行启动 Chrome/Chromium，并加入多个自动化/隔离相关参数。

这里必须严格区分：

- 源码事实：独立 Profile、自行启动 Chrome、具体启动参数；
- 现场观察：当前页面中 `navigator.webdriver=true`；
- 有限推断：这些特征可能参与了掘金前置挑战的触发；
- 未知：掘金的官方判定逻辑和每个信号的权重。

我们没有修改指纹、隐藏 webdriver、破解挑战或自动处理验证码。

### 3.2 成功链路

随后切换到用户已经登录的普通 Chrome，通过 macOS 可视化/无障碍控制：

1. 打开创作者中心文章管理页；
2. 确认账号和文章列表；
3. 进入编辑器；
4. 写入已脱敏正文；
5. 核对字符数、标题、分类、标签和摘要；
6. 点击提交；
7. 回文章管理页刷新；
8. 只以“已发布/审核中/未通过”列表状态作为结论。

文章能够正常提交并在文章管理页显示真实状态。

## 4. 普通 Chrome 的成功优势

### 4.1 已登录会话可直接复用

普通 Chrome 已由用户完成登录。工具只是操作现有页面，不需要读取或搬运认证数据。

### 4.2 用户可见、可中止

每一次点击和输入都发生在可见窗口。用户可以随时观察、停止或接管。

### 4.3 不新建自动化 Profile

不会因为独立临时 Profile 而丢失登录状态、站点偏好和正常会话上下文。

### 4.4 保持日常浏览器表面

工具没有主动向页面注入隐藏 webdriver、修改指纹或绕过挑战的脚本。是否暴露其他自动化特征取决于具体控制实现，因此不能承诺“绝对不可检测”。

## 5. 可复制操作流程

### 5.1 启动检查

```text
1. 确认当前主机是 macOS；Windows/Linux 立即停止并报告不支持
2. 用户打开普通 Chrome 并登录目标站点
3. 用户明确授权目标操作
4. 工具通过 macOS 可视化控制、Computer Use 或 Accessibility 读取并操作普通 Chrome，无需安装扩展
5. 只读列出当前窗口、标签页、URL 和页面标题
6. 确认目标账号、目标文章和操作范围
```

### 5.2 每步操作循环

```text
读取最新页面状态
    ↓
寻找语义元素或可视坐标
    ↓
执行一个小动作
    ↓
重新读取页面状态
    ↓
验证动作结果
```

不要缓存旧元素索引连续点击。现代 SPA 每次渲染都可能改变 Accessibility Tree。

### 5.3 并发纪律

- 一个发布任务使用一个独立 Chrome 窗口或 Profile。
- 不让两个 Agent 同时写同一个标签页。
- 需要并发时，使用不同浏览器 Profile；不要复制认证数据。
- 用户操作窗口时，Agent 暂停并重新读取状态。

## 6. 编辑器故障恢复

本次在掘金 Markdown 双栏编辑器中观察到两个重要问题。

### 6.1 set-value 与预览不同步

源输入区显示新内容，但右侧预览和底部字数仍保留旧稿。这说明“输入框可读到新值”不等于编辑器内部状态已经更新。

处理：

1. 不点击提交；
2. 核对源区、预览区和字数；
3. 用编辑器支持的语义输入重新触发变更；
4. 三处一致后才继续。

### 6.2 键盘模拟破坏中文

批量 `type_text` 可能受输入法影响，出现中文丢失、只留下标点或英文词。

可靠恢复法：

```text
全选正文
  → 写入短 ASCII 标记 TEMP_CLEAR_MARKER
  → 确认字符数约为标记长度
  → 使用 Unicode-safe set_value 写入完整正文
  → 点击标题使编辑器失焦并保存
  → 核对首段、末段、字符数和旧文关键字不存在
```

这个两阶段方法同时解决旧文叠加和中文输入法损坏问题。

## 7. 发布状态核验

掘金的“发布成功”页面只证明表单提交成功。平台审核结论必须从创作者中心文章管理页读取。

状态术语：

- `审核中`：已经提交，尚未完成审核；
- `已发布`：文章管理页确认审核通过并公开；
- `未通过`：审核失败；优先编辑原失败稿，不重复新建；
- `草稿箱`：尚未提交或更新未完成。

每次提交后应刷新文章管理页，记录：标题、时间、全部/已发布/审核中/未通过计数和文章状态。

## 8. 安全与证据边界

禁止：

- 读取或导出 Cookie、Token、密码、浏览器 Profile；
- 将认证数据复制到 Kitewright/Playwright Profile；
- 隐藏或修改 `navigator.webdriver`；
- 绕过 CAPTCHA、前置挑战、风险验证或浏览器安全警告；
- 把小样本审核结果描述成平台官方规则。

允许：

- 操作用户已经授权且已经登录的普通浏览器；
- 读取可见页面和 Accessibility Tree；
- 在用户授权范围内编辑、提交和核验内容；
- 遇到风控时停止独立自动化浏览器，改用用户正常会话，但不规避仍然出现的安全挑战。

## 9. 其他工具接入合同

不同工具不必共享相同实现，但应提供以下抽象能力：

```text
list_windows_and_tabs()       # 只读发现普通 Chrome
read_visible_state()          # 截图 + Accessibility/DOM 语义
click_semantic_or_coordinate()
set_unicode_value()           # 能安全写入中文
press_key()
wait_and_reread()
stop_on_security_challenge()
```

使用该合同的工具还必须做到：

- 不访问浏览器凭据存储；
- 每次动作后回读；
- 保持用户可见；
- 支持用户随时接管；
- 对发布、删除、付款和权限等动作遵循所属平台的确认策略。

只有满足这些条件，其他开发工具才能复制“操作普通 Chrome”的成功，而不是复制一个新的自动化浏览器。
